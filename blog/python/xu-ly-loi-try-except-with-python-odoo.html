Python xử lý lỗi: try/except, raise, with và ValidationError

Dữ liệu luôn có thể sai và file luôn có thể thiếu. Bài này dạy try/except/finally, raise, exception tự định nghĩa và câu lệnh with, rồi đối chiếu với ValidationError, UserError mà Odoo dùng để báo lỗi cho người dùng.

Cập nhật: 16/10/2026 15 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Lỗi trong Python là các ngoại lệ (exception). try bọc đoạn có thể lỗi, except xử lý đúng loại lỗi đó, finally luôn chạy để dọn dẹp, và raise chủ động báo lỗi khi dữ liệu không hợp lệ. Câu lệnh with đảm bảo tài nguyên (như file) luôn được đóng. Trong Odoo, bạn báo lỗi cho người dùng bằng raise ValidationError(...) hoặc raise UserError(...), và trong test bắt chúng bằng with self.assertRaises(...).

try, except, else, finally

Khi một lệnh gặp lỗi, Python ngừng chạy và "ném" một ngoại lệ lên các tầng gọi cho tới khi có except bắt được; nếu không ai bắt, chương trình dừng và in traceback. Bốn khối của lệnh try:

def to_hours(text):
    try:
        hours = int(text)             # đoạn có thể lỗi
    except ValueError:
        print("Không phải số:", text) # chỉ chạy khi có ValueError
        return None
    else:
        print("chuyển xong")          # chạy khi KHÔNG có lỗi
        return hours
    finally:
        print("luôn chạy")            # luôn chạy, dù có lỗi hay không

print(to_hours("24"))
# chuyển xong
# luôn chạy
# 24
print(to_hours("abc"))
# Không phải số: abc
# luôn chạy
# None

Bắt đúng loại lỗi

try:
    {"a": 1}["b"]
except (KeyError, IndexError) as e:   # bắt nhiều loại, lấy đối tượng lỗi qua "as e"
    print(type(e).__name__, e)        # KeyError 'b'

try:
    open("khong_co.csv")
except FileNotFoundError as e:
    print("FileNotFoundError:", e)
# FileNotFoundError: [Errno 2] No such file or directory: 'khong_co.csv'

def safe_div(a, b):
    try:
        return a / b
    except ZeroDivisionError as e:
        print("ZeroDivisionError:", e)   # division by zero
        return 0.0

Hãy bắt loại lỗi cụ thể nhất mà bạn biết cách xử lý. Một tuple trong except bắt nhiều loại cùng lúc; as e cho bạn đối tượng lỗi để in thông điệp hay đọc thuộc tính. Các lỗi hay gặp nhất khi làm việc với dữ liệu:

Đọc traceback: kỹ năng quan trọng nhất

Khi một ngoại lệ không được bắt, Python in traceback: chuỗi các lời gọi hàm dẫn tới lỗi. Hãy học cách đọc nó từ dưới lên: dòng cuối cùng cho biết loại lỗi và thông điệp, các dòng phía trên là "đường đi" bạn đã qua. Ví dụ một script đọc danh sách khóa học, trong đó dòng thứ hai có số giờ viết bằng chữ:

def parse_hours(text):
    return int(text)

def load_course(row):
    return {"name": row["name"], "hours": parse_hours(row["hours"])}

rows = [{"name": "Odoo", "hours": "24"}, {"name": "Git", "hours": "tám"}]
for row in rows:
    print(load_course(row))

Khi chạy, kết quả là:

{'name': 'Odoo', 'hours': 24}
Traceback (most recent call last):
  File "tb.py", line 9, in <module>
    print(load_course(row))
  File "tb.py", line 5, in load_course
    return {"name": row["name"], "hours": parse_hours(row["hours"])}
  File "tb.py", line 2, in parse_hours
    return int(text)
ValueError: invalid literal for int() with base 10: 'tám'
  • Dòng cuối (ValueError: invalid literal for int() ... 'tám') nói rõ: lỗi là ValueError và giá trị gây lỗi là 'tám'.
  • Khung gần cuối nhất (parse_hours, dòng 2) là nơi lỗi xảy ra, dòng int(text).
  • Các khung phía trên cho biết ai đã gọi nó: load_course rồi vòng for ở mức module. Bạn lần theo để tìm ra dòng dữ liệu nào ("Git") gây vấn đề.

Thói quen tốt: đọc dòng cuối trước, rồi khung cuối của code của bạn (bỏ qua các khung thuộc thư viện nếu có). Trong Odoo, traceback xuất hiện trong log của server và các khung đi qua odoo/... chỉ là bộ khung; hãy tìm khung đầu tiên thuộc module của bạn.

EAFP và LBYL: hai phong cách xử lý lỗi

Có hai cách tiếp cận: LBYL ("look before you leap", kiểm tra điều kiện trước rồi mới làm) và EAFP ("easier to ask forgiveness than permission", cứ làm rồi bắt lỗi nếu có). Python thiên về EAFP vì nó tránh được tình huống dữ liệu đổi giữa lúc kiểm tra và lúc dùng, nhưng không có cách nào đúng tuyệt đối. Khi thiếu một khóa là chuyện bình thường, d.get() hoặc in thường rõ ràng hơn; khi lỗi thực sự bất thường, dùng try/except:

d = {"a": 1}

# LBYL: nhìn trước khi nhảy (kiểm tra điều kiện trước)
value = d["b"] if "b" in d else "none"

# EAFP: xin lỗi sau còn hơn xin phép trước (cứ làm, bắt lỗi nếu có)
try:
    value = d["b"]
except KeyError:
    value = "none"

# thường gọn nhất với dict
value = d.get("b", "none")

assert value == "none", "tính sai"     # assert: kiểm tra giả định của lập trình viên
# AssertionError: tính sai  (nếu điều kiện sai)

Từ khóa assert dành cho giả định của lập trình viên ("chỗ này chắc chắn đúng"), không phải để kiểm tra dữ liệu người dùng nhập, vì nó có thể bị tắt khi chạy Python với tùy chọn tối ưu hóa. Dữ liệu từ bên ngoài luôn cần raise lỗi thật.

raise: chủ động báo lỗi

def check(hours):
    if hours <= 0:
        raise ValueError(f"Số giờ không hợp lệ: {hours}")
    return hours

try:
    check(0)
except ValueError as e:
    print("Bắt được:", e)               # Bắt được: Số giờ không hợp lệ: 0

try:
    try:
        1 / 0
    except ZeroDivisionError:
        print("ghi log rồi ném lại")
        raise                           # raise trống: ném lại đúng lỗi đang xử lý
except ZeroDivisionError:
    print("nơi gọi vẫn nhận được lỗi")

Dùng raise khi dữ liệu đầu vào phá vỡ quy tắc nghiệp vụ, thay vì để chương trình chạy tiếp với dữ liệu sai. raise trống bên trong except ném lại đúng lỗi đang xử lý, hữu ích khi bạn muốn ghi log rồi để tầng trên quyết định.

Exception tự định nghĩa

class CourseError(Exception):
    """Lỗi nghiệp vụ khóa học."""

class InvalidHours(CourseError):
    def __init__(self, hours):
        super().__init__(f"Số giờ không hợp lệ: {hours}")
        self.hours = hours

def convert(text):
    try:
        return int(text)
    except ValueError as e:
        raise InvalidHours(text) from e     # giữ lại nguyên nhân gốc

try:
    convert("x")
except CourseError as e:                    # bắt cả lớp cha lẫn lớp con
    print(e)                                # Số giờ không hợp lệ: x
    print(repr(e.__cause__))
    # ValueError("invalid literal for int() with base 10: 'x'")

Tạo class kế thừa Exception để đặt tên cho lỗi nghiệp vụ của dự án. Bắt lớp cha (CourseError) sẽ bắt luôn mọi lớp con. Cú pháp raise ... from e giữ lại nguyên nhân gốc trong __cause__, rất hữu ích khi debug. Cả cây ngoại lệ đều bắt nguồn từ BaseException; hầu hết lỗi bạn gặp kế thừa Exception, còn KeyboardInterrupt (Ctrl+C) thì không, nên except Exception không nuốt nó.

with: dọn dẹp tự động

Câu lệnh with làm việc với context manager: đối tượng biết cách "mở" và "đóng". Ví dụ kinh điển là file, tự đóng khi ra khỏi khối with dù có lỗi hay không, nên bạn không cần nhớ gọi close():

import tempfile, os
path = os.path.join(tempfile.mkdtemp(), "a.txt")

with open(path, "w", encoding="utf-8") as f:    # tự đóng file khi ra khỏi khối with
    f.write("ODO-F\n")
print(f.closed)                                  # True

with open(path, encoding="utf-8") as f:
    print(f.read().strip())                      # ODO-F

Bạn có thể tự viết context manager bằng decorator contextlib.contextmanager: phần trước yield chạy khi vào khối, phần finally sau đó chạy khi ra, kể cả khi thân khối gặp lỗi:

from contextlib import contextmanager

@contextmanager
def section(name):
    print("bắt đầu", name)
    try:
        yield                                    # phần thân khối with chạy ở đây
    finally:
        print("kết thúc", name)                  # luôn chạy, kể cả khi thân bị lỗi

with section("nhập"):
    print("đang làm")
# bắt đầu nhập
# đang làm
# kết thúc nhập

try:
    with section("lỗi"):
        raise ValueError("hỏng")
except ValueError:
    print("đã bắt")
# bắt đầu lỗi
# kết thúc lỗi      <- finally vẫn chạy
# đã bắt

Báo lỗi trong Odoo: ValidationError và UserError

from odoo.exceptions import UserError, ValidationError

@api.constrains('duration_hours')
def _check_duration(self):
    for course in self:
        if course.duration_hours <= 0:
            raise ValidationError("Số giờ học phải lớn hơn 0.")   # hiện thành thông báo lỗi

@api.ondelete(at_uninstall=False)
def _unlink_except_published(self):
    if any(course.is_published for course in self):
        raise UserError("Không thể xóa khóa học đã xuất bản.")

# trong test
with self.assertRaises(ValidationError):
    self.course.duration_hours = 0
Ngoại lệ OdooDùng khiGặp ở
ValidationErrorDữ liệu vi phạm ràng buộcMethod @api.constrains phải ném lỗi này khi điều kiện không thỏa
UserErrorChặn một thao tác vì lý do nghiệp vụVí dụ trong @api.ondelete khi không được xóa
AccessErrorNgười dùng không có quyềncreate, write, search ném khi vi phạm quyền (bài 5 series Odoo)
ValueErrorTên field không tồn tạicreate ném khi giá trị truyền vào có tên field sai

Thông điệp bạn truyền vào ValidationError/UserError chính là nội dung người dùng nhìn thấy, nên hãy viết rõ ràng, nói họ phải làm gì. Trong test, with self.assertRaises(ValidationError): kiểm tra rằng ràng buộc của bạn thực sự chặn dữ liệu sai (bài 13 series Odoo).

Thực hành: chuyển dòng CSV an toàn

def parse_row(row):
    """Chuyển dict chuỗi thành dict đúng kiểu; ném InvalidHours nếu lỗi."""
    try:
        hours = int(row["hours"])
    except (KeyError, ValueError) as e:
        raise InvalidHours(row.get("hours")) from e
    if hours <= 0:
        raise InvalidHours(hours)
    return {"code": row["code"].strip().upper(), "hours": hours}

rows = [{"code": " odo-f ", "hours": "24"}, {"code": "x", "hours": "abc"}, {"code": "y", "hours": "-1"}]
ok, errors = [], []
for row in rows:
    try:
        ok.append(parse_row(row))
    except CourseError as e:
        errors.append(str(e))
print(ok)       # [{'code': 'ODO-F', 'hours': 24}]
print(errors)   # ['Số giờ không hợp lệ: abc', 'Số giờ không hợp lệ: -1']

Đây là mẫu xử lý dữ liệu nhập từ file rất thực tế (bài 11 và 14): gom dòng tốt vào một danh sách, dòng lỗi vào danh sách khác, chương trình không dừng giữa chừng.

Lỗi hay gặp khi mới học

try:
    risky()
except:                      # BẮT MỌI THỨ, kể cả KeyboardInterrupt
    pass                     # và nuốt lỗi: không còn dấu vết nào

# tốt hơn: bắt đúng loại lỗi và ghi lại
try:
    risky()
except ValueError as e:
    logging.warning("bỏ qua dòng lỗi: %s", e)
  • except: trống hoặc except Exception: pass. Nuốt mọi lỗi, kể cả lỗi lập trình, khiến chương trình sai âm thầm. Hãy bắt đúng loại và ghi log (logging.exception(...) ghi cả traceback).
  • Bọc cả hàm dài trong một try. Bạn không biết lỗi đến từ dòng nào. Chỉ bọc những dòng thực sự có thể lỗi.
  • Dùng lỗi thay cho điều kiện thông thường. Kiểm tra if key in d: hoặc d.get() thường rõ ràng hơn bắt KeyError khi thiếu khóa là chuyện bình thường.
  • Nhầm loại ngoại lệ trong Odoo. Ràng buộc dữ liệu dùng ValidationError; chặn thao tác dùng UserError. Nên thông điệp dành cho người dùng cuối, không phải lập trình viên.

Tổng kết

  • try/except/else/finally xử lý lỗi; bắt đúng loại cụ thể, tránh except: trống.
  • raise báo lỗi khi dữ liệu không hợp lệ; raise X from e giữ nguyên nhân gốc; exception tự định nghĩa đặt tên cho lỗi nghiệp vụ.
  • with đảm bảo dọn dẹp tài nguyên (file, kết nối) dù có lỗi hay không.
  • Odoo: ValidationError cho ràng buộc, UserError cho chặn thao tác, thông điệp viết cho người dùng.

Bài tiếp theo là cách đọc và ghi dữ liệu thật: file, pathlib, JSON và CSV.

Nên bắt lỗi chung chung bằng except Exception không? ▾
Chỉ nên bắt loại lỗi cụ thể mà bạn biết cách xử lý. Except trống hoặc except Exception kèm pass nuốt mọi lỗi, kể cả lỗi lập trình, khiến chương trình sai âm thầm. Nếu bắt rộng, hãy ghi log kèm traceback.
finally dùng để làm gì? ▾
Khối finally luôn chạy, dù có lỗi hay không và kể cả khi có return, nên dùng để dọn dẹp như đóng file hay giải phóng tài nguyên. Câu lệnh with làm việc này tự động cho file.
ValidationError và UserError khác nhau thế nào trong Odoo? ▾
ValidationError dùng cho ràng buộc dữ liệu, method @api.constrains phải ném nó khi điều kiện không thỏa. UserError dùng để chặn một thao tác vì lý do nghiệp vụ, ví dụ không cho xóa trong @api.ondelete. Cả hai hiển thị thông điệp cho người dùng.
raise ... from e dùng để làm gì? ▾
Nó ném một lỗi mới nhưng giữ lại lỗi gốc trong thuộc tính __cause__, giúp truy ngược nguyên nhân khi debug.
