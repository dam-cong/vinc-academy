Merge request GitLab: quy trình review code cho nhóm

Bài 5 đi trọn một vòng merge request trên GitLab với module vinc_course: nhánh theo issue, push, mô tả MR, sửa theo góp ý bằng commit mới, merge, dọn nhánh và hiểu vì sao main được bảo vệ.

Cập nhật: 16/10/2026 12 phút đọc – lượt xem Đội ngũ Vinc Academy

Tóm tắt nhanh

Merge request (MR) là nơi cả nhóm xem, bàn luận và duyệt thay đổi trước khi nó vào nhánh chính. Bài này đi trọn một vòng trên GitLab với module vinc_course: tạo nhánh theo issue, push, mở MR với mô tả tốt và Closes #12, sửa theo góp ý của reviewer bằng cách push thêm commit, merge, dọn nhánh, và hiểu vì sao main thường bị bảo vệ không cho push thẳng. Các lệnh chạy thật trên repo giả lập; phần thao tác giao diện lấy theo tài liệu GitLab.

Merge request là gì và vì sao doanh nghiệp bắt buộc dùng

Ở bài 3 bạn tự gõ git merge trên máy mình. Làm vậy trong nhóm sẽ có rủi ro: code chưa ai xem đã vào nhánh chính, và nếu hỏng thì cả nhóm cùng chịu. Merge request giải quyết bằng một bước chặn ở giữa. Theo tài liệu GitLab, MR là nơi tập trung để nhóm review code, thảo luận và theo dõi thay đổi; trong một MR bạn thấy mô tả, các thay đổi code kèm góp ý ngay tại dòng, thông tin pipeline CI/CD, báo cáo khả năng merge, bình luận và danh sách commit.

Một MR có hai vai: assignee (người sở hữu, thường là tác giả, chịu trách nhiệm tiến độ) và reviewer (người xem code, góp ý, và nếu đủ điều kiện thì approve). GitLab gọi tính năng này là merge request; GitHub gọi là pull request, nhưng quy trình gần như giống hệt.

Một vòng đầy đủ: từ issue đến main

Giả sử issue #12 trên GitLab yêu cầu “thêm học phí cho khóa học”. Bước đầu là chắc chắn bạn bắt đầu từ main mới nhất, rồi tạo nhánh. Tài liệu GitLab cho biết nhánh có tiền tố là mã issue (ví dụ 12-course-price) giúp GitLab điền sẵn tiêu đề và liên kết issue khi mở MR. Dòng thứ hai của commit (-m lần hai) ghi Closes #12 để issue tự đóng khi MR được merge:

$ git switch main
Your branch is up to date with 'origin/main'.
Already on 'main'
$ git pull

$ git switch -c 12-course-price
Switched to a new branch '12-course-price'
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường học phí" -m "Closes #12"
[12-course-price 25ea246] [IMP] vinc_course: thêm trường học phí

Closes #12

Sau khi push, mở GitLab, vào Code → Merge requests và chọn tạo MR mới cho nhánh vừa đẩy (nhiều bản GitLab còn hiện sẵn nút gợi ý ngay trên trang dự án). Điền tiêu đề, mô tả, chọn assignee là bạn và một hoặc hai reviewer; tick Delete source branch when merge request accepted để nhánh nguồn tự xóa sau khi merge. Phần mô tả là chỗ đáng đầu tư nhất, ví dụ:

## Mục đích
Thêm trường học phí cho khóa học để bộ phận kinh doanh báo giá.

## Thay đổi
- models/course.py: thêm trường price (Float)
- views/course_views.xml: hiển thị price trên form và list

## Cách kiểm tra
1. Nâng cấp module: odoo-bin -u vinc_course -d vinc_test
2. Mở Khóa học, nhập học phí, lưu

Closes #12

Reviewer sẽ để lại góp ý trên từng dòng. Theo tài liệu, các thread chưa resolve sẽ chặn việc merge, còn bình luận đơn thì không. Để sửa theo góp ý, bạn không tạo MR mới: chỉ cần commit và push thêm lên cùng nhánh, MR tự cập nhật. Lệnh git log origin/main..HEAD liệt kê đúng những commit mà MR đang chứa:

$ sed -i "s/Học phí/Học phí (VND)/" models/course.py
$ git commit -am "[IMP] vinc_course: ghi rõ đơn vị học phí theo review"
[12-course-price b190c76] [IMP] vinc_course: ghi rõ đơn vị học phí theo review
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   25ea246..b190c76  12-course-price -> 12-course-price
$ git log --oneline origin/main..HEAD
b190c76 [IMP] vinc_course: ghi rõ đơn vị học phí theo review
25ea246 [IMP] vinc_course: thêm trường học phí

Khi reviewer hài lòng và pipeline xanh, một người có quyền bấm Merge. Quy tắc mặc định theo tài liệu: nhánh mặc định (thường là main) được bảo vệ, chỉ Maintainer trở lên được merge vào đó; Developer merge được MR nhắm vào nhánh không bảo vệ. Đồ thị cho thấy merge commit ghép nhánh 12-course-price vào main, kèm hai commit của MR. Với thiết lập thật, GitLab còn cho chọn squash (gộp các commit của MR thành một) khi merge; bài 8 giải thích squash.

Một thói quen nhỏ nhưng giá trị: ngay sau khi MR của bạn được merge, hãy chuyển về main, git pull rồi mới tạo nhánh kế tiếp. Nếu bỏ qua, nhánh mới sẽ tách từ main cũ và MR sau dễ xung đột hoặc kéo theo commit đã merge. Tương tự, đừng để nhánh đã merge nằm lại: xóa cả bản cục bộ lẫn bản trên GitLab như ở bài 4.

Approve, auto-merge và vai trò của từng gói GitLab

Cách duyệt khác nhau tùy gói GitLab. Theo tài liệu, trên gói Free mọi người từ vai trò Developer trở lên đều có thể approve MR nhưng việc approve chỉ mang tính tùy chọn, không ngăn được merge. Gói Premium và Ultimate cho phép đặt quy tắc bắt buộc: số người duyệt tối thiểu, loại reviewer (backend, frontend, QA...) hoặc dùng file CODEOWNERS để chỉ định người duyệt theo từng thư mục; chưa đủ approval thì không merge được. Khi reviewer đã hài lòng mà pipeline vẫn đang chạy, họ có thể đặt MR ở chế độ auto-merge: khi mọi điều kiện đạt, GitLab tự merge mà bạn không phải làm gì thêm.

Vì sao không push thẳng được vào main

Theo tài liệu GitLab, nhánh mặc định của repo được bảo vệ sẵn. Nhánh bảo vệ kiểm soát ai được merge và push, ngăn xóa nhầm và có thể bắt buộc review. Maintainer cấu hình ở Settings → Repository → Branch rules. Để bạn thấy hiệu ứng, ví dụ này dùng một hook trên “GitLab” giả để từ chối push vào main; thông báo remote: do chính ta viết, còn GitLab thật sẽ in lời nhắn của riêng nó, nhưng dòng cuối remote rejected thì giống nhau:

$ echo "# thử đẩy thẳng" >> README.md
$ git add README.md
$ git commit -m "[ADD] vinc_course: README"
[main a5b2c69] [ADD] vinc_course: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git push
remote: Nhánh main được bảo vệ: hãy push nhánh riêng và mở merge request.        
To git@gitlab.example.com:vinc/vinc_course.git
 ! [remote rejected] main -> main (pre-receive hook declined)
error: failed to push some refs to 'git@gitlab.example.com:vinc/vinc_course.git'

Commit đã nằm trên main cục bộ. Cách xử lý chuẩn: giữ commit bằng cách tạo nhánh từ đây rồi push nhánh đó, sau đó đưa main cục bộ về lại đúng origin/main (lệnh git reset --hard sẽ được giải thích ở bài 7; hãy chắc chắn commit đã nằm an toàn trên nhánh mới trước khi chạy):

$ git switch -c fix/readme
Switched to a new branch 'fix/readme'
$ git push -u origin fix/readme
branch 'fix/readme' set up to track 'origin/fix/readme'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      fix/readme -> fix/readme
$ git switch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)
Switched to branch 'main'
$ git reset --hard origin/main
HEAD is now at 828392e Merge branch '12-course-price' into 'main'
$ git status -sb
## main...origin/main

Mô tả rõ lý do, thay đổi, cách kiểm traNgười duyệt không phải đoán bạn muốn gì
Liên kết issue bằng Closes #12Theo tài liệu, các từ như Close/Closes, Fix/Fixes, Resolve/Resolves, Implement/Implements đứng trước tham chiếu issue sẽ tự đóng issue khi merge

Tự đọc lại diff trước khi gửiBắt được print quên xóa, file thừa, mật khẩu lỡ commit

Reviewer nhìn gì trong một MR của module Odoo

  • Quyền truy cập: model mới đã có dòng trong ir.model.access.csv chưa (bài 8 series Odoo).
  • Manifest: file XML mới đã nằm trong data của __manifest__.py và đúng thứ tự phụ thuộc chưa.
  • Nâng cấp module: đã chạy -u vinc_course trên một CSDL thử và không báo lỗi chưa.
  • Phạm vi: MR có sửa nhầm module khác hoặc kéo theo file không liên quan không; Odoo cũng khuyên tránh một commit đụng nhiều module cùng lúc.
  • Bí mật: không có mật khẩu, API key hay odoo.conf thật trong diff.

Lỗi hay gặp khi mới học

  • Push thẳng lên main bị chặn. Đừng cố ép. Tạo nhánh từ commit hiện tại, push nhánh đó và mở MR như ở phần trên.
  • Tạo MR mới mỗi lần sửa theo góp ý. Chỉ cần push thêm commit lên cùng nhánh; MR cũ tự cập nhật và giữ nguyên toàn bộ thảo luận.
  • MR báo xung đột với nhánh đích. Có người đã sửa cùng dòng trên main trong lúc bạn làm. Hãy lấy main mới về nhánh của bạn và giải quyết xung đột ở máy (bài 6), rồi push lại.
  • MR to như một dự án. Hàng chục file và nhiều mục đích khiến reviewer duyệt qua loa. Tách thành nhiều MR nối tiếp nhau; GitLab còn tự chuyển đích của MR phụ thuộc khi MR trước được merge.

Tổng kết

  • MR là cổng review: code chỉ vào nhánh chính sau khi có người xem và pipeline đạt.
  • Quy trình: nhánh theo issue → commit → push → mở MR → sửa theo góp ý bằng commit mới → merge → dọn nhánh.
  • Closes #12 trong commit hoặc mô tả tự đóng issue khi merge.
  • Nhánh mặc định được bảo vệ: push thẳng bị từ chối, hãy đi qua MR.

Khi hai MR cùng sửa một chỗ, bạn sẽ gặp xung đột. Đó là điều đáng sợ nhất với người mới, và cũng dễ hơn bạn nghĩ. Bài 6 hướng dẫn đọc các dấu <<<<<<<, sửa tay và hoàn tất merge.

Câu hỏi thường gặp

Merge request và pull request khác nhau không? ▾
Cùng một khái niệm: đề nghị gộp một nhánh vào nhánh khác kèm review. GitLab gọi là merge request, GitHub gọi là pull request. Lệnh Git phía bạn giống hệt, chỉ khác giao diện web.
Sửa theo góp ý của reviewer có phải tạo merge request mới không? ▾
Không. Bạn commit thêm rồi push lên cùng nhánh, merge request tự cập nhật và giữ nguyên toàn bộ thảo luận. Khi xong, bạn đánh dấu các thread là đã resolve.
Làm sao để issue tự đóng khi merge request được merge? ▾
Ghi một từ khóa kèm tham chiếu issue trong mô tả MR hoặc commit, ví dụ Closes #12. Theo tài liệu GitLab, các từ như Close, Fix, Resolve, Implement (và biến thể) đứng trước tham chiếu sẽ đóng issue khi MR merge.
Vì sao tôi không push trực tiếp lên main được? ▾
Nhánh mặc định của repo trên GitLab được bảo vệ mặc định: chỉ vai trò được cấp quyền mới merge hoặc push vào đó. Hãy push nhánh riêng và mở merge request; Maintainer chỉnh quy tắc tại Settings > Repository > Branch rules.
