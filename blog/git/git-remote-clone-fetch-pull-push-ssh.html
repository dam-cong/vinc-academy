Git remote: clone, fetch, pull, push và SSH key GitLab

Bài 4 nối repo vinc_course với GitLab: tạo SSH key, clone, push nhánh, fetch để xem trước, pull để gộp, và xử lý lỗi push bị rejected hay pull báo divergent branches mà ai làm nhóm cũng gặp.

Cập nhật: 16/10/2026 12 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Remote là bản repo đặt trên máy chủ (thường là GitLab) để cả nhóm cùng đẩy và lấy commit. Bài này nối repo vinc_course với GitLab: tạo SSH key và đăng ký lên GitLab, clone repo về, push nhánh lên, fetch để xem công việc của đồng nghiệp mà chưa gộp, pull để lấy và gộp, và xử lý lỗi rejected cùng divergent branches mà ai cũng gặp. Để chạy thật, ví dụ dùng một repo bare cục bộ đóng vai GitLab; các lệnh y hệt khi dùng GitLab thật.

Remote, origin và nhánh theo dõi

Đến giờ mọi commit chỉ nằm trên máy bạn. Để cộng tác, nhóm đặt một repo trung tâm trên GitLab; mỗi người có repo riêng trên máy và đồng bộ qua repo trung tâm đó. Git gọi repo ở xa là remote, và tên mặc định của remote bạn clone về là origin. Một repo có thể có nhiều remote (ví dụ origin của công ty và upstream của dự án gốc).

Điểm hay gây hiểu nhầm là origin/main: đó không phải nhánh bạn làm việc, mà là bản ghi nhớ trên máy bạn về nơi main của GitLab đã đứng ở lần liên lạc gần nhất. Nó chỉ được cập nhật khi bạn fetch, pull hoặc push. Vì vậy “remote đã có commit mới chưa?” là câu hỏi mà Git chỉ trả lời đúng sau khi bạn fetch.

LệnhTác dụng
git remote -vLiệt kê remote và URL
git remote add origin <url>Gắn repo cục bộ có sẵn với một remote
git clone <url>Sao chép repo về máy, tự đặt origin
git fetchTải commit mới về, không sửa nhánh của bạn
git pullfetch rồi gộp vào nhánh hiện tại
git pushĐẩy commit của nhánh hiện tại lên remote
git push -u origin <nhánh>Đẩy lần đầu và ghi nhớ nhánh theo dõi

Kết nối GitLab bằng SSH key

Có hai cách xác thực khi clone: HTTPS (hỏi tài khoản) hoặc SSH. Theo tài liệu GitLab, SSH dùng một cặp khóa gồm khóa công khai (đưa cho GitLab) và khóa riêng (giữ kín trên máy bạn), nhờ đó bạn không phải nhập tên đăng nhập và mật khẩu mỗi lần push hay pull. Một khóa dùng được cho mọi dự án mà tài khoản có quyền, bạn không cần khóa riêng cho từng dự án. Loại khóa được ưu tiên là ED25519. Làm một lần trên mỗi máy:

# 1. Tạo cặp khóa (comment là email để nhận diện khóa)
ssh-keygen -t ed25519 -C "an.nguyen@example.com"
# Nhấn Enter để nhận tên file mặc định ~/.ssh/id_ed25519, nên đặt passphrase

# 2. Nạp khóa riêng vào ssh-agent
ssh-add ~/.ssh/id_ed25519

# 3. In khóa CÔNG KHAI để copy (file .pub, không phải file không đuôi)
cat ~/.ssh/id_ed25519.pub

# 4. Sau khi dán khóa vào GitLab, kiểm tra kết nối
ssh -T git@gitlab.example.com
# Welcome to GitLab, @tên-bạn!
  • Trong GitLab: bấm avatar → Edit profile → Access → SSH keys → Add new key, dán khóa công khai, đặt tiêu đề như “Laptop công ty” rồi Add key.
  • Thay gitlab.example.com bằng địa chỉ GitLab của công ty (với GitLab.com là gitlab.com). Lần kết nối đầu ssh hỏi xác nhận máy chủ; hãy đối chiếu dấu vân tay với trang tài liệu của GitLab trước khi gõ yes.
  • Không bao giờ dán hay gửi khóa riêng (file id_ed25519). Chỉ file .pub mới được chia sẻ.
KiểuURL ví dụXác thực
SSHgit@gitlab.example.com:vinc/vinc_course.gitCặp khóa SSH, không hỏi mật khẩu mỗi lần
HTTPShttps://gitlab.example.com/vinc/vinc_course.gitHỏi thông tin đăng nhập khi kết nối

Cả hai URL trỏ cùng một repo; khác nhau chỉ ở cách chứng minh bạn là ai. Đã clone bằng URL nào mà muốn đổi, dùng git remote set-url origin <url-mới>. Trang dự án trên GitLab có sẵn nút Code để sao chép cả hai dạng URL.

Nối repo với GitLab: push lần đầu và clone

Nếu repo đã có sẵn trên máy (như vinc_course của chúng ta), hãy tạo một dự án trống trên GitLab, thêm remote rồi đẩy lên. Cờ -u (--set-upstream) ghi nhớ rằng main theo dõi origin/main, nhờ đó từ nay chỉ cần gõ git push và git pull trơn.

$ git remote add origin git@gitlab.example.com:vinc/vinc_course.git
$ git remote -v
origin	git@gitlab.example.com:vinc/vinc_course.git (fetch)
origin	git@gitlab.example.com:vinc/vinc_course.git (push)
$ git push -u origin main
branch 'main' set up to track 'origin/main'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      main -> main
$ git branch -vv
* main 47905cb [origin/main] [IMP] vinc_course: thêm trường số giờ
$ git status -sb
## main...origin/main

git status -sb giờ in ## main...origin/main: nhánh của bạn và bản ghi nhớ đang khớp nhau. Đồng nghiệp là Bình, ở máy khác, lấy repo về bằng git clone; lệnh này tạo thư mục, trỏ origin và checkout nhánh mặc định:

$ cd ..
$ git clone git@gitlab.example.com:vinc/vinc_course.git vinc_course_binh
Cloning into 'vinc_course_binh'...
done.
$ cd vinc_course_binh

Làm việc song song: push nhánh, fetch để xem

Bình tạo nhánh cấp độ, commit và đẩy lên GitLab. Đây là nhánh mới nên remote chưa biết, và cờ -u lại hữu ích:

$ git switch -c feature/course-level
Switched to a new branch 'feature/course-level'
$ echo "    level = fields.Selection([('basic', 'Cơ bản'), ('adv', 'Nâng cao')])" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường cấp độ"
[feature/course-level 6c73d41] [IMP] vinc_course: thêm trường cấp độ
 1 file changed, 1 insertion(+)
$ git push -u origin feature/course-level
branch 'feature/course-level' set up to track 'origin/feature/course-level'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      feature/course-level -> feature/course-level

Trên máy An chưa có gì thay đổi cho tới khi An fetch. Sau fetch, nhánh của Bình xuất hiện dưới dạng origin/feature/course-level để An xem hoặc review mà chưa đụng vào nhánh nào của mình. Chuyển sang tên nhánh đó, Git tự tạo nhánh cục bộ cùng tên và nối theo dõi:

$ cd ../vinc_course
$ git fetch
From git@gitlab.example.com:vinc/vinc_course
 * [new branch]      feature/course-level -> origin/feature/course-level
$ git branch -a
* main
  remotes/origin/feature/course-level
  remotes/origin/main
$ git switch feature/course-level
branch 'feature/course-level' set up to track 'origin/feature/course-level'.
Switched to a new branch 'feature/course-level'
$ git log --oneline -n 2
6c73d41 [IMP] vinc_course: thêm trường cấp độ
47905cb [IMP] vinc_course: thêm trường số giờ
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'

fetch và pull: khác nhau ở chỗ nào

git pull thực chất là git fetch cộng thêm git merge vào nhánh hiện tại. Thói quen an toàn là fetch trước, xem rồi mới gộp: bạn thấy được commit nào sắp về. Ví dụ Bình đẩy một commit README lên main; An fetch, thấy mình đang behind 1, rồi pull và Git chỉ việc fast-forward:

$ cd ../vinc_course_binh
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ echo "# vinc_course" > README.md
$ git add README.md
$ git commit -m "[ADD] vinc_course: README"
[main 518a39d] [ADD] vinc_course: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   47905cb..518a39d  main -> main
$ cd ../vinc_course
$ git fetch
From git@gitlab.example.com:vinc/vinc_course
   47905cb..518a39d  main       -> origin/main
$ git status -sb
## main...origin/main [behind 1]
$ git pull
Updating 47905cb..518a39d
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git log --oneline -n 2
518a39d [ADD] vinc_course: README
47905cb [IMP] vinc_course: thêm trường số giờ

Khi push bị từ chối và pull báo “divergent”

Tình huống kinh điển trong nhóm: An commit trên máy mình, trong lúc đó Bình đã đẩy commit khác lên cùng nhánh. Lịch sử của hai người đã rẽ, nên GitLab không cho An đẩy đè lên. Hãy tái hiện:

$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường học phí"
[main 7b05493] [IMP] vinc_course: thêm trường học phí
 1 file changed, 1 insertion(+)
$ cd ../vinc_course_binh
$ echo "Module quản lý khóa học." >> README.md
$ git commit -am "[IMP] vinc_course: mô tả README"
[main b6a59e9] [IMP] vinc_course: mô tả README
 1 file changed, 1 insertion(+)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   518a39d..b6a59e9  main -> main
$ cd ../vinc_course
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'git@gitlab.example.com:vinc/vinc_course.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

Thông báo rejected … (fetch first) nghĩa là remote có commit mà máy bạn chưa có. Hãy lấy chúng về trước. Nhưng lần này git pull không chịu chạy vì Git không biết nên gộp bằng merge hay rebase:

$ git pull
From git@gitlab.example.com:vinc/vinc_course
   518a39d..b6a59e9  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

Git liệt kê ba lựa chọn cấu hình. Tạm thời hãy chọn merge bằng cờ --no-rebase; bài 8 sẽ so sánh với rebase. Vì hai commit sửa file khác nhau nên Git tự gộp được, rồi bạn đẩy lên:

$ git pull --no-rebase
Merge made by the 'ort' strategy.
 README.md | 1 +
 1 file changed, 1 insertion(+)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   b6a59e9..bfdc341  main -> main
$ git log --oneline --graph -n 4
*   bfdc341 Merge branch 'main' of git@gitlab.example.com:vinc/vinc_course
|\  
| * b6a59e9 [IMP] vinc_course: mô tả README
* | 7b05493 [IMP] vinc_course: thêm trường học phí
|/  
* 518a39d [ADD] vinc_course: README

Để khỏi bị hỏi mỗi lần, bạn có thể đặt mặc định: git config --global pull.rebase false (merge), pull.rebase true (rebase) hoặc pull.ff only (chỉ chấp nhận fast-forward, thận trọng nhất). Hãy thống nhất với nhóm.

Dọn nhánh remote

Sau khi nhánh được merge, xóa luôn cả bản trên GitLab. git push origin --delete <nhánh> xóa nhánh trên remote; máy của đồng nghiệp vẫn còn bản ghi nhớ cũ nên họ chạy git fetch --prune để dọn. Nhánh cục bộ cùng tên vẫn còn và phải xóa riêng bằng git branch -d.

$ cd ../vinc_course_binh
$ git push origin --delete feature/course-level
To git@gitlab.example.com:vinc/vinc_course.git
 - [deleted]         feature/course-level
$ cd ../vinc_course
$ git fetch --prune
From git@gitlab.example.com:vinc/vinc_course
 - [deleted]         (none)     -> origin/feature/course-level
$ git branch -a
  feature/course-level
* main
  remotes/origin/main

Lỗi hay gặp khi mới học

  • Push bị rejected. Đừng vội ép. Hãy git pull (hoặc fetch rồi xem), xử lý rồi push lại như ở trên.
  • Dùng git push --force cho nhanh. Ép đẩy sẽ ghi đè commit của đồng nghiệp trên remote. Nếu thật sự phải ép (ví dụ sau khi rebase nhánh riêng), hãy dùng --force-with-lease: nó từ chối khi remote có commit mà bạn chưa thấy. Không bao giờ ép lên nhánh chung như main.
  • Dán nhầm khóa riêng lên GitLab. Chỉ dán nội dung file .pub (bắt đầu bằng ssh-ed25519). Nếu lỡ lộ khóa riêng, hãy tạo cặp khóa mới và xóa khóa cũ khỏi GitLab.
  • Tưởng origin/main luôn mới nhất. Nó chỉ mới tới lần fetch gần nhất; hãy fetch trước khi so sánh hay quyết định gộp.

Tổng kết

  • Remote (origin) là repo trung tâm; origin/main là bản ghi nhớ trên máy bạn, chỉ mới sau fetch.
  • SSH key ED25519: khóa công khai cho GitLab, khóa riêng ở lại máy bạn.
  • clone lấy repo về; push -u đẩy nhánh lần đầu; fetch xem trước; pull = fetch + merge.
  • Rejected và divergent nghĩa là lịch sử đã rẽ: lấy commit về, gộp, rồi đẩy; tránh --force.

Giờ bạn đã có nhánh trên GitLab. Nhưng trong doanh nghiệp, hiếm khi ai merge thẳng bằng lệnh: họ mở một merge request để đồng nghiệp xem code trước khi vào nhánh chính. Đó là chủ đề của bài 5.

Câu hỏi thường gặp

git fetch và git pull khác nhau thế nào? ▾
git fetch chỉ tải commit mới từ remote về và cập nhật các nhánh origin/..., không đổi nhánh bạn đang làm. git pull là git fetch cộng với git merge (hoặc rebase) vào nhánh hiện tại. Fetch trước để xem sẽ có gì, rồi gộp.
Vì sao push bị rejected (fetch first)? ▾
Vì remote đã có commit mà máy bạn chưa có, thường do đồng nghiệp vừa push lên cùng nhánh. Hãy git pull (hoặc fetch rồi merge), xử lý nếu có xung đột, rồi push lại. Không dùng --force để vượt qua.
Nên dùng SSH hay HTTPS với GitLab? ▾
Cả hai đều dùng được. SSH dùng cặp khóa nên không phải nhập tài khoản mỗi lần push hay pull; HTTPS hỏi thông tin đăng nhập khi kết nối. Phần lớn nhóm chọn SSH với khóa ED25519 cho máy làm việc cố định.
Tham số -u trong git push -u origin main có tác dụng gì? ▾
-u (--set-upstream) ghi nhớ rằng nhánh cục bộ theo dõi nhánh trên origin. Sau đó bạn chỉ cần gõ git push và git pull trơn, và git status cho biết bạn đi trước hay đi sau remote bao nhiêu commit.
