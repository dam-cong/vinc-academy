Git hook và GitLab CI: tự kiểm tra module Odoo

Bài 11 biến quy ước thành kiểm tra tự động: hook pre-commit và commit-msg chặn bí mật, code lỗi, lời nhắn sai mẫu ngay trên máy, rồi .gitlab-ci.yml chạy lint và test của module Odoo trong từng merge request.

Cập nhật: 16/10/2026 13 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Hook là kịch bản Git tự chạy ở những thời điểm cố định (trước khi commit, khi nhập lời nhắn...) và chặn thao tác nếu kịch bản thoát với mã khác 0. Bài này viết hai hook thật cho vinc_course: pre-commit chặn file bí mật và Python sai cú pháp, commit-msg bắt buộc tiêu đề dạng [TAG] module: mô tả; chia sẻ chúng cho cả nhóm bằng core.hooksPath. Sau đó là lớp kiểm tra thứ hai chạy trên server: GitLab CI với file .gitlab-ci.yml kiểm tra từng merge request, gồm cả bước chạy test của Odoo.

Git hook là gì

Quy ước ở bài 10 chỉ có giá trị khi mọi người tuân theo, mà con người thì hay quên lúc gấp. Hook để máy nhắc thay bạn. Theo tài liệu githooks, hook là chương trình nằm trong thư mục hooks của Git (hoặc thư mục bạn chỉ định bằng core.hooksPath) và phải có quyền thực thi; tên file chính là tên sự kiện. Nếu hook thoát với mã khác 0, thao tác tương ứng bị hủy.

HookChạy khi nàoDùng để
pre-commitTrước khi tạo commit, chưa có lời nhắnSoát file: cú pháp, bí mật, dấu xung đột
commit-msgSau khi có lời nhắn, nhận file chứa lời nhắnKiểm tra hoặc chuẩn hóa tiêu đề
pre-pushTrước khi đẩy lên remoteChạy test nhanh trước khi lên GitLab

Hai điểm cần nhớ từ tài liệu: pre-commit và commit-msg đều có thể bị bỏ qua bằng git commit --no-verify, và thư mục .git/hooks không được commit nên không tự theo repo tới máy đồng nghiệp. Cách chia sẻ: đặt hook trong thư mục của repo (ví dụ .githooks/) rồi mỗi người chạy một lần git config core.hooksPath .githooks.

Hook pre-commit: chặn bí mật và code lỗi

Hook dưới đây duyệt từng file đã staging. Gặp odoo.conf hay .env nó từ chối; gặp file .py nó kiểm tra cú pháp bằng Python; cuối cùng git diff --cached --check bắt các dấu xung đột còn sót (bài 6). Lưu thành .githooks/pre-commit và cấp quyền thực thi:

#!/bin/sh
# Chặn commit chứa file bí mật, dấu xung đột hoặc Python sai cú pháp
for f in $(git diff --cached --name-only --diff-filter=ACM); do
  case "$f" in
    odoo.conf|.env) echo "pre-commit: không được commit $f" >&2; exit 1 ;;
    *.py)
      err=$(python3 -c "import ast,sys; ast.parse(open(sys.argv[1], encoding='utf-8').read())" "$f" 2>&1) || {
        echo "pre-commit: lỗi cú pháp trong $f" >&2; echo "$err" | tail -n 1 >&2; exit 1; } ;;
  esac
done
git diff --cached --check || exit 1

Hook thứ hai kiểm tra tiêu đề commit theo mẫu Odoo của bài 10. Git đưa cho nó đường dẫn file chứa lời nhắn ($1); ta chỉ đọc dòng đầu. Các merge commit và revert do Git tự sinh được cho qua:

#!/bin/sh
# Tiêu đề phải dạng [TAG] module: mô tả (cho phép Merge/Revert tự sinh)
head -n 1 "$1" | grep -Eq '^(\[(ADD|IMP|FIX|REF|REM|REV|MOV|MERGE|REL|I18N|PERF|CLN|LINT)\] [a-z0-9_]+: .+|Merge |Revert )' || {
  echo "commit-msg: tiêu đề phải có dạng [TAG] module: mô tả" >&2
  echo "            ví dụ: [FIX] vinc_course: sửa nhãn số giờ" >&2
  exit 1; }

Bật hook cho repo và thử ngay. Lệnh commit đầu tiên chính là commit thêm hai hook, và nó đã phải qua cả hai kiểm tra:

$ git config core.hooksPath .githooks
$ git add .githooks
$ git commit -m "[ADD] vinc_course: hook kiểm tra commit"
[main 8bf05a8] [ADD] vinc_course: hook kiểm tra commit
 2 files changed, 17 insertions(+)
 create mode 100755 .githooks/commit-msg
 create mode 100755 .githooks/pre-commit

Thử cho hook chặn

Python sai cú pháp bị chặn trước khi thành commit; commit không được tạo và file vẫn nằm trong staging để bạn sửa:

$ echo "def broken(:" > models/bad.py
$ git add models/bad.py
$ git commit -m "[ADD] vinc_course: file lỗi"
pre-commit: lỗi cú pháp trong models/bad.py
SyntaxError: invalid syntax
$ git restore --staged models/bad.py
$ rm models/bad.py

Thử commit file cấu hình chứa mật khẩu (đã phải add -f vì .gitignore thường chặn nó):

$ echo "admin_passwd = secret" > odoo.conf
$ git add -f odoo.conf
$ git commit -m "[ADD] vinc_course: cấu hình"
pre-commit: không được commit odoo.conf
$ git restore --staged odoo.conf
$ rm odoo.conf

Rồi đến lời nhắn sai mẫu. Hook commit-msg từ chối, in ví dụ đúng, và khi bạn viết lại cho đúng thì commit đi qua:

$ echo "# ghi chú" >> models/course.py
$ git commit -am "update"
commit-msg: tiêu đề phải có dạng [TAG] module: mô tả
            ví dụ: [FIX] vinc_course: sửa nhãn số giờ
$ git commit -am "[IMP] vinc_course: ghi chú trong model"
[main 4062c7d] [IMP] vinc_course: ghi chú trong model
 1 file changed, 1 insertion(+)

Hai cách hook không chạy: --no-verify và quyền thực thi

Cờ --no-verify cho phép bỏ qua hook, hợp lý khi bạn cần commit khẩn cấp hay commit tạm trên nhánh riêng. Nhưng chính vì ai cũng làm được, hook không thể là chốt chặn duy nhất:

$ echo "# thêm" >> models/course.py
$ git commit --no-verify -am "update"
[main 0f50aa1] update
 1 file changed, 1 insertion(+)

Lỗi thứ hai tinh vi hơn: nếu file hook mất quyền thực thi, Git âm thầm bỏ qua nó và chỉ để lại một dòng gợi ý (hint) ở cuối. Commit vẫn thành công dù kiểm tra không hề chạy:

$ chmod -x .githooks/pre-commit
$ echo "# lần nữa" >> models/course.py
$ git add models/course.py
$ git commit -m "[IMP] vinc_course: thêm ghi chú"
[main 1f8b27e] [IMP] vinc_course: thêm ghi chú
 1 file changed, 1 insertion(+)
hint: The '.githooks/pre-commit' hook was ignored because it's not set as executable.
hint: You can disable this warning with `git config advice.ignoredHook false`.

Lớp kiểm tra thứ hai: GitLab CI

Theo tài liệu GitLab, để chạy CI/CD bạn cần hai thứ: một runner (tác nhân thực thi job; GitLab.com cung cấp sẵn, còn GitLab nội bộ thì quản trị viên đăng ký) và file .gitlab-ci.yml ở thư mục gốc repo mô tả các job. Khi bạn push, GitLab tạo một pipeline gồm các job chạy theo thứ tự stage; kết quả hiện ngay trong merge request. File cho vinc_course gồm ba job: kiểm tra cú pháp Python, kiểm tra không lọt bí mật, và chạy test của Odoo:

stages: [lint, test]

lint-python:
  stage: lint
  image: python:3.12
  script:
    - python -m compileall -q .
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

no-secrets:
  stage: lint
  image: alpine:3
  script:
    - test ! -e odoo.conf
    - '! grep -rIn "admin_passwd" --include="*.py" --include="*.xml" .'
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

odoo-tests:
  stage: test
  image: registry.example.com/vinc/odoo-ci:20.0   # image nội bộ có sẵn Odoo 20 và PostgreSQL
  script:
    - odoo-bin -d ci_db -i vinc_course --test-tags /vinc_course --stop-after-init
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
Từ khóaÝ nghĩa (theo tài liệu GitLab)
stagesTên và thứ tự các stage; job cùng stage chạy song song
imageDocker image dùng để chạy job
scriptLệnh shell mà runner thực thi; một lệnh thoát khác 0 làm job thất bại
rulesĐiều kiện để job được tạo; ở đây chỉ chạy cho pipeline của merge request

Hai job đầu dùng đúng những lệnh bạn có thể chạy thử trên máy trước khi push, và kết quả như dưới đây (không in gì và mã thoát 0 nghĩa là qua):

$ python3 -m compileall -q . ; echo "exit=$?"
exit=0
$ test ! -e odoo.conf && echo "không có odoo.conf"
không có odoo.conf
$ ! grep -rIn "admin_passwd" --include="*.py" --include="*.xml" . ; echo "exit=$?"
exit=0

Job thứ ba dùng cờ -i để cài module vào CSDL ci_db, --test-tags /vinc_course để chỉ chạy test của module này (cú pháp [-][tag][/module][:class][.method] trong tài liệu test Odoo) và --stop-after-init để tiến trình thoát sau khi xong; test thất bại làm job thất bại. Tên image ở trên là ví dụ: nhóm bạn tự dựng một image có Odoo 20 và PostgreSQL rồi thay vào.

Khi quen, bạn sẽ gặp thêm vài từ khóa hữu ích khác trong tài liệu tham chiếu của GitLab:

Từ khóaDùng để
before_scriptLệnh chạy trước script của mỗi job, ví dụ cài thư viện
cacheGiữ lại thư mục (như .venv) giữa các lần chạy để pipeline nhanh hơn
artifactsĐính kèm file kết quả của job, ví dụ báo cáo test
allow_failureCho phép job lỗi mà không làm hỏng cả pipeline (hợp với kiểm tra cảnh báo)
variablesKhai báo biến môi trường cho job, ví dụ tên CSDL kiểm thử

Một mẹo giữ mọi thứ đồng nhất: đưa các lệnh kiểm tra vào một file trong repo (ví dụ scripts/check.sh) rồi cho cả hook lẫn job CI gọi cùng file đó. Khi muốn thêm một quy tắc, bạn sửa ở một chỗ, và kết quả trên máy bạn khớp với kết quả trên GitLab.

Đưa vào quy trình nhóm

BướcCách làm
Cài hook cho người mớiThêm dòng git config core.hooksPath .githooks vào mục “Bắt đầu” của README
Bảo vệ mainChỉ merge qua MR (bài 5) và yêu cầu pipeline xanh trước khi merge
Test của moduleViết test bằng TransactionCase của Odoo (bài 13 series Odoo) để job odoo-tests có gì để chạy
Tăng dầnBắt đầu với lint và kiểm tra bí mật, thêm test và triển khai khi nhóm đã quen

Lỗi hay gặp khi mới học

  • Hook không chạy mà không ai biết. Thiếu quyền thực thi, hoặc đồng nghiệp chưa đặt core.hooksPath. Ví dụ ở trên cho thấy Git chỉ in một dòng hint. Hãy ghi bước cài hook vào README và dùng pipeline làm lớp bảo vệ chính.
  • Dùng --no-verify thành thói quen. Mỗi lần bỏ qua là một lần quy ước bị phá. Chỉ dùng cho trường hợp khẩn, và để pipeline bắt lại.
  • Hook quá chậm. Chạy cả bộ test trong pre-commit khiến mọi người né nó. Giữ hook dưới vài giây (cú pháp, bí mật), dồn việc nặng sang CI.
  • Job CI treo ở trạng thái chờ. Thường là chưa có runner hoạt động cho dự án; tài liệu GitLab hướng dẫn kiểm tra runner ở Settings → CI/CD. Hãy hỏi quản trị viên GitLab của công ty.
  • Sai thụt lề hoặc dấu nháy trong YAML. YAML nhạy cảm với khoảng trắng; dòng lệnh bắt đầu bằng ! như trong job no-secrets phải đặt trong dấu nháy. Hãy kiểm tra file bằng công cụ lint YAML hoặc trình soạn pipeline trong GitLab trước khi push.

Tổng kết

  • Hook là kịch bản chạy tự động; thoát mã khác 0 thì Git hủy thao tác. Cần quyền thực thi.
  • pre-commit soát file, commit-msg soát lời nhắn; chia sẻ qua thư mục trong repo và core.hooksPath.
  • Hook bỏ qua được bằng --no-verify nên cần CI làm lớp bảo vệ chung.
  • .gitlab-ci.yml khai báo stages, job, image, script, rules; runner thực thi và kết quả hiện trong merge request.

Bài cuối ghép mọi thứ lại. Bạn sẽ dùng git blame và git bisect để truy ra commit gây lỗi, rồi chạy trọn một chu kỳ làm việc: tính năng, merge request, hotfix và phát hành.

Câu hỏi thường gặp

Git hook là gì và nằm ở đâu? ▾
Hook là chương trình Git tự chạy ở những thời điểm cố định như trước khi commit. Mặc định chúng nằm trong .git/hooks và phải có quyền thực thi; bạn đổi thư mục bằng core.hooksPath. Hook thoát với mã khác 0 thì thao tác bị hủy.
Làm sao chia sẻ hook cho cả nhóm? ▾
Thư mục .git/hooks không được commit. Hãy để hook trong thư mục của repo, ví dụ .githooks/, commit nó, rồi mỗi người chạy một lần git config core.hooksPath .githooks, tốt nhất ghi vào README.
Có bỏ qua được hook không? ▾
Có. git commit --no-verify bỏ qua pre-commit và commit-msg. Vì vậy hook chỉ là lớp bảo vệ trên máy; nhóm cần pipeline CI trên GitLab làm chốt chặn chung.
GitLab CI cần những gì để chạy? ▾
Cần ít nhất một runner hoạt động (GitLab.com cung cấp sẵn) và file .gitlab-ci.yml ở thư mục gốc repo khai báo các job. Khi bạn push, GitLab tạo pipeline và hiển thị kết quả trong merge request.
