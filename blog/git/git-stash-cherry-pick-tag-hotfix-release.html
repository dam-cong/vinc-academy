Git stash, cherry-pick và tag: hotfix và phát hành bản mới

Bài 9 chạy một kịch bản hotfix thật: cất việc dở bằng git stash, tách nhánh từ tag đang chạy, gắn tag bản vá, cherry-pick -x về main rồi lấy lại việc dở, áp dụng cho module vinc_course.

Cập nhật: 16/10/2026 13 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Ba công cụ cho ba tình huống “giữa chừng”: stash cất việc dang dở để đổi sang việc khác, cherry-pick mang đúng một commit sang nhánh khác, tag đánh dấu một bản phát hành. Bài này chạy một kịch bản hotfix thật: đang làm dở nhánh học phí thì có lỗi ở bản 1.0.0 đang chạy; ta cất việc dở, tách nhánh hotfix từ tag, gắn tag 1.0.1, cherry-pick bản sửa về main, rồi lấy lại việc dở.

Câu chuyện hotfix chiều thứ Sáu

Bản vinc_course 1.0.0 đã chạy ở khách hàng. Bạn đang viết dở trường học phí trên nhánh riêng thì được báo: nhãn “Số giờ” gây hiểu nhầm, cần sửa gấp. Bạn không thể commit nửa vời, cũng không muốn mang tính năng chưa xong vào bản sửa. Ba công cụ của bài này xử lý lần lượt từng việc:

Việc cần làmCông cụ
Cất việc dang dở, quay lại saugit stash
Biết chính xác bản đang chạy là commit nàogit tag
Sửa lỗi từ đúng bản đã phát hànhTách nhánh từ tag
Đưa bản sửa về main mà không kéo theo thứ khácgit cherry-pick

Tag: đánh dấu bản phát hành

Tag là cái tên cố định gắn vào một commit, thường dùng cho số phiên bản. Khác nhánh, tag không di chuyển khi bạn commit thêm. Theo tài liệu Git có hai loại: tag annotated (tạo bằng -a) lưu ngày, người tạo và lời nhắn, dành cho phát hành; tag lightweight chỉ là một cái tên, dành cho đánh dấu tạm. Nên đặt tên theo số phiên bản mà manifest khai báo (tài liệu Odoo khuyên dùng semantic versioning cho trường version). Lưu ý git push thường không đẩy tag; bạn phải đẩy tường minh, và có thể kiểm tra remote bằng ls-remote:

$ git tag -a v1.0.0 -m "Phát hành 1.0.0"
$ git tag
v1.0.0
$ git show v1.0.0 --no-patch
tag v1.0.0
Tagger: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 10:17:00 2026 +0700

Phát hành 1.0.0

commit 47905cb280043ef4405171ee158d3e8967dd309a
Author: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 09:49:00 2026 +0700

    [IMP] vinc_course: thêm trường số giờ
$ git ls-remote --tags origin
$ git push origin v1.0.0
To git@gitlab.example.com:vinc/vinc_course.git
 * [new tag]         v1.0.0 -> v1.0.0
$ git ls-remote --tags origin
5b6f223733af3ab0cae1c9c3d5de7d98aa06f970	refs/tags/v1.0.0
47905cb280043ef4405171ee158d3e8967dd309a	refs/tags/v1.0.0^{}

Stash: cất việc dang dở

git stash lấy các thay đổi chưa commit ra khỏi thư mục làm việc, cất vào một ngăn xếp riêng và trả file về đúng như commit gần nhất. Bạn có thể chuyển nhánh sạch sẽ, rồi quay lại lấy ra. Mặc định nó chỉ cất file đã theo dõi: NOTE.md mới tạo vẫn nằm lại (muốn cất cả file mới, thêm -u):

$ git switch -c feature/course-price
Switched to a new branch 'feature/course-price'
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ echo "ghi chú" > NOTE.md
$ git status -s
 M models/course.py
?? NOTE.md
$ git stash push -m "dở học phí"
Saved working directory and index state On feature/course-price: dở học phí
$ git status -s
?? NOTE.md
$ git stash list
stash@{0}: On feature/course-price: dở học phí
LệnhTác dụng
git stash push -m "mô tả"Cất, kèm tên dễ nhận
git stash push -uCất cả file chưa theo dõi
git stash listXem các lần cất
git stash show -pXem nội dung lần cất gần nhất
git stash popLấy ra và xóa khỏi ngăn xếp
git stash applyLấy ra nhưng giữ lại bản cất
git stash dropXóa một lần cất

Stash phù hợp cho khoảng cách ngắn: vài phút tới vài giờ. Nếu việc dở sẽ kéo dài sang ngày hôm sau, hãy commit tạm lên nhánh riêng ([WIP]) rồi sau này gộp bằng rebase tương tác như bài 8; commit có tên và nằm trong lịch sử, còn stash dễ bị quên. Khi bản cất xung đột với thay đổi mới, git stash branch <tên> tạo nhánh mới từ đúng commit lúc cất rồi áp dụng bản cất lên đó, một lối thoát gọn.

Hotfix: tách nhánh từ tag

Nhờ tag, bạn tách nhánh đúng từ bản đang chạy chứ không phải từ main (đã có thêm commit khác). Sửa lỗi, commit, gắn tag 1.0.1 và đẩy lên; người phụ trách triển khai chỉ việc lấy tag đó:

$ git switch -c hotfix/1.0.1 v1.0.0
Switched to a new branch 'hotfix/1.0.1'
$ sed -i "s/Số giờ/Số giờ (giờ)/" models/course.py
$ git commit -qam "[FIX] vinc_course: ghi rõ đơn vị số giờ"
$ git tag -a v1.0.1 -m "Hotfix 1.0.1"
$ git push origin v1.0.1
To git@gitlab.example.com:vinc/vinc_course.git
 * [new tag]         v1.0.1 -> v1.0.1
$ git log --oneline -n 3 --decorate
1f85d3e (HEAD -> hotfix/1.0.1, tag: v1.0.1) [FIX] vinc_course: ghi rõ đơn vị số giờ
47905cb (tag: v1.0.0) [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course

Cherry-pick: mang đúng một commit sang nơi khác

Bản sửa phải có cả ở main để lần phát hành sau không lặp lại lỗi. Merge nhánh hotfix vào main cũng được, nhưng nếu nhánh có nhiều thứ khác bạn chỉ muốn đúng một commit. git cherry-pick <commit> áp dụng thay đổi của commit đó lên nhánh hiện tại thành một commit mới. Cờ -x thêm dòng “(cherry picked from commit …)” để người sau lần ngược được nguồn; tài liệu khuyên dùng khi cherry-pick giữa hai nhánh công khai (như backport sửa lỗi sang nhánh bảo trì):

$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ git cherry-pick -x hotfix/1.0.1
[main 938fa6a] [FIX] vinc_course: ghi rõ đơn vị số giờ
 Date: Mon Oct 12 12:09:00 2026 +0700
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline -n 3
938fa6a [FIX] vinc_course: ghi rõ đơn vị số giờ
6305374 [ADD] vinc_course: thêm extra
47905cb [IMP] vinc_course: thêm trường số giờ
$ git log -1 --format=%B
[FIX] vinc_course: ghi rõ đơn vị số giờ

(cherry picked from commit 1f85d3e6f42ba67551050559c96ab62364d8feed)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   6305374..938fa6a  main -> main

Cherry-pick tạo commit mới (mã băm khác), nên dòng -x là mối liên kết duy nhất với bản gốc. Nếu thay đổi đụng nhau, bạn gặp xung đột như bài 6 và hoàn tất bằng git cherry-pick --continue, hoặc hủy bằng --abort. Có thể chọn một dải: git cherry-pick A..B.

Giờ quay lại việc dở. git stash pop đưa thay đổi trở lại và xóa bản cất khỏi danh sách, nhưng theo tài liệu, nếu việc áp dụng gặp xung đột thì bản cất không bị xóa để bạn không mất gì:

$ git switch feature/course-price
Switched to branch 'feature/course-price'
$ git stash pop
On branch feature/course-price
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   models/course.py

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	NOTE.md

no changes added to commit (use "git add" and/or "git commit -a")
Dropped refs/stash@{0} (8e6da6bf2eefeff625ca4a09a60da21474acd05b)
$ git stash list

Xem, chuyển tới và xóa tag

$ git tag -l "v1.*"
v1.0.0
v1.0.1
$ git describe
v1.0.0-2-g938fa6a
$ git switch --detach v1.0.0
HEAD is now at 47905cb [IMP] vinc_course: thêm trường số giờ
$ git switch -
Your branch is up to date with 'origin/main'.
Previous HEAD position was 47905cb [IMP] vinc_course: thêm trường số giờ
Switched to branch 'main'
$ git tag -d v1.0.0
Deleted tag 'v1.0.0' (was 5b6f223)
$ git push origin --delete v1.0.0
To git@gitlab.example.com:vinc/vinc_course.git
 - [deleted]         v1.0.0
$ git tag
v1.0.1

git describe in ra tên tag gần nhất (chỉ tính tag annotated theo mặc định), hữu ích để hiển thị phiên bản đang chạy. git switch --detach v1.0.0 cho bạn xem code đúng ở bản đó mà không tạo nhánh; git switch - quay lại. Xóa tag cần làm hai nơi: cục bộ với -d, remote với git push origin --delete. Tránh xóa rồi tạo lại tag đã công bố, vì người khác đã có tag cũ. Trên GitLab, quản trị có thể bảo vệ tag theo mẫu tên (protected tags) để chỉ một số vai trò mới được tạo.

Đặt số phiên bản cho tag

Tài liệu manifest của Odoo yêu cầu version tuân theo semantic versioning: ba số MAJOR.MINOR.PATCH. Quy ước này giúp cả khách hàng lẫn đồng nghiệp đoán được mức độ thay đổi chỉ qua con số:

Thay đổiSố mớiVí dụ trên vinc_course
PATCH1.0.0 → 1.0.1Sửa nhãn hay lỗi nhỏ, không đổi cấu trúc dữ liệu
MINOR1.0.1 → 1.1.0Thêm trường học phí, tương thích ngược
MAJOR1.1.0 → 2.0.0Đổi tên model hoặc bỏ trường, cần di chuyển dữ liệu

Checklist phát hành gọn

  • git switch main và git pull: chắc chắn đang ở bản mới nhất đã review.
  • Cập nhật version trong __manifest__.py, chạy test và nâng cấp thử trên CSDL thử.
  • Commit số phiên bản, rồi git tag -a vX.Y.Z -m "..." và git push origin vX.Y.Z.
  • Triển khai bằng cách chuyển sang đúng tag, không chuyển sang một nhánh còn đang chạy.
  • Ghi lại điều đã thay đổi cho khách hàng (changelog) kèm tên tag.

Lỗi hay gặp khi mới học

  • Tưởng git push đã đẩy tag. Ví dụ ở phần tag cho thấy ls-remote rỗng cho tới khi bạn git push origin <tag> (hoặc --tags để đẩy mọi tag).
  • Quên mình đã stash. Việc cất đi nằm im trong git stash list cả tuần rồi bị bỏ quên. Luôn đặt -m mô tả và dọn bằng pop hoặc drop sớm.
  • Stash không có file mới. Như ví dụ, NOTE.md không vào stash. Muốn cất cả file chưa theo dõi hãy dùng git stash push -u.
  • Sửa lỗi trên main rồi mới biết bản đang chạy không có nó. Hãy luôn tách hotfix từ tag của bản đang chạy, rồi mới đưa về main bằng cherry-pick hoặc merge.
  • Cherry-pick bừa nhiều commit. Mỗi bản sao tạo ra mã băm riêng nên sau này merge hai nhánh có thể thấy thay đổi “trùng”. Chỉ cherry-pick khi thực sự cần mang riêng một thay đổi.

Tổng kết

  • stash push -m / pop: cất và lấy lại việc dở; thêm -u để cất cả file mới.
  • Tag annotated cho bản phát hành; nhớ đẩy tag tường minh.
  • Hotfix: tách nhánh từ tag đang chạy, gắn tag mới, rồi cherry-pick -x về main.
  • Gặp xung đột khi cherry-pick: sửa, add, --continue (hoặc --abort).

Bạn đã có đủ công cụ kỹ thuật. Điều còn thiếu để cả nhóm làm việc ăn khớp là quy ước: đặt tên nhánh, viết commit message và chọn chiến lược nhánh nào. Đó là chủ đề bài 10.

Câu hỏi thường gặp

git stash dùng khi nào? ▾
Khi bạn đang làm dở, chưa muốn commit nhưng cần chuyển nhánh ngay (ví dụ sửa lỗi gấp). git stash push -m cất thay đổi chưa commit, git stash pop lấy lại. Thêm -u nếu muốn cất cả file chưa theo dõi.
Cherry-pick khác merge ở điểm nào? ▾
Merge đưa toàn bộ lịch sử của một nhánh vào nhánh hiện tại. Cherry-pick chỉ áp dụng thay đổi của một hoặc vài commit đã chọn thành commit mới (mã băm khác). Cờ -x ghi lại commit gốc trong lời nhắn.
Tag annotated và lightweight khác nhau thế nào? ▾
Tag annotated (git tag -a) lưu ngày, người tạo và lời nhắn, dành cho bản phát hành. Tag lightweight chỉ là một cái tên trỏ tới commit, dành cho đánh dấu tạm. Một số lệnh như git describe mặc định bỏ qua tag lightweight.
Vì sao tag của tôi không thấy trên GitLab? ▾
git push thường không đẩy tag. Bạn phải đẩy tường minh bằng git push origin tên-tag, hoặc git push --tags để đẩy mọi tag. Kiểm tra bằng git ls-remote --tags origin.
