Quy ước commit và chiến lược nhánh Git cho nhóm Odoo

Bài 10 chốt ba quy ước giúp cả nhóm đọc được lịch sử: lời nhắn commit theo mẫu [TAG] module của Odoo, cách đặt tên nhánh và một chiến lược nhánh gọn với main được bảo vệ, merge request và tag phát hành.

Cập nhật: 16/10/2026 13 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Công cụ Git ai cũng như nhau; thứ làm nên nhóm làm việc trơn tru là quy ước chung. Bài này chốt ba quy ước: lời nhắn commit theo mẫu [TAG] module: mô tả của Odoo (giải thích vì sao), tên nhánh (feature/, fix/, hotfix/, mã issue) và chiến lược nhánh gọn cho module khách hàng (main được bảo vệ, nhánh ngắn hạn, merge request, tag phát hành). Có kèm lệnh git log --grep để thấy quy ước giúp tìm kiếm thế nào.

Vì sao cần quy ước

Thử hình dung lịch sử repo toàn các dòng “update”, “fix”, “sửa lại”, “final”. Ba tháng sau khách hàng hỏi “từ khi nào trường mã khóa học bắt buộc nhập?”, và không ai trả lời được. Lịch sử Git chỉ có giá trị khi đọc được: nó là nhật ký mà git log, git blame và git bisect (bài 12) dựa vào. Tài liệu gitworkflows của Git tóm lại bằng quy tắc đầu tiên: chia thay đổi thành những bước logic nhỏ, mỗi bước là một commit nhất quán, chạy được độc lập và qua được bộ test. Điều đó làm review dễ hơn và lịch sử hữu ích hơn cho việc truy vết sau này.

Quy ước lời nhắn commit theo Odoo

Hướng dẫn Git của Odoo mô tả lời nhắn gồm bốn phần: thẻ (tag), tên module, tiêu đề ngắn và mô tả đầy đủ. Mẫu là [TAG] module: mô tả một câu ngắn, tiêu đề lý tưởng dưới 50 ký tự, rồi một dòng trống và phần mô tả dài hơn, kết thúc bằng tham chiếu như Closes #14 hay Fixes #14. Dùng tên kỹ thuật của module (vinc_course), vì tên hiển thị có thể đổi theo thời gian. Các thẻ theo tài liệu:

ThẻDùng cho
[ADD]Thêm module hay thành phần mới
[IMP]Cải tiến, thay đổi tăng dần
[FIX]Sửa lỗi
[REF]Tái cấu trúc, viết lại lớn
[REM]Xóa code, view hoặc module không dùng
[REV]Revert một commit
[MOV]Di chuyển file (không đổi nội dung)
[MERGE]Merge commit
[REL]Commit phát hành phiên bản mới
[I18N]Thay đổi file dịch
[PERF] / [CLN] / [LINT]Tối ưu hiệu năng / dọn code / lint

Điểm tinh tế nhất là tiêu đề nên ghép được thành một câu hợp lệ sau cụm “nếu áp dụng, commit này sẽ…”: [IMP] vinc_course: thêm mã khóa học đọc là “nếu áp dụng, commit này sẽ thêm mã khóa học”. Phần mô tả giải thích vì sao, vì “cái gì” đã nằm trong diff. Hãy tạo một commit như vậy:

$ echo "    code = fields.Char(string='Mã khóa')" >> models/course.py
$ git commit -aq -m "[IMP] vinc_course: thêm mã khóa học" -m "Phòng đào tạo tra cứu khóa theo mã nên mỗi khóa cần một trường mã riêng." -m "Closes #14"
$ git log -1
commit ca324bbdd38a5a698d7573fc962ebddea73a1975
Author: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 10:10:00 2026 +0700

    [IMP] vinc_course: thêm mã khóa học
    
    Phòng đào tạo tra cứu khóa theo mã nên mỗi khóa cần một trường mã riêng.
    
    Closes #14

Mỗi -m thêm một đoạn, nên lệnh trên tạo tiêu đề, một đoạn lý do và dòng Closes #14 (GitLab dùng nó để đóng issue khi merge, bài 5). Để tiện, bạn có thể cho Git mở sẵn một mẫu mỗi khi commit không có -m, bằng cấu hình commit.template:

$ git config --global commit.template ~/.gitmessage
$ git config --get commit.template
~/.gitmessage
$ cat ~/.gitmessage
[TAG] module: tóm tắt thay đổi

Vì sao cần thay đổi (WHY).

Closes #

Quy ước có lợi ích thấy ngay khi tìm kiếm. Vì tiêu đề bắt đầu bằng thẻ, bạn lọc được mọi bản sửa lỗi bằng --grep, xem lịch sử của riêng thư mục models/, hay đếm đóng góp mỗi người:

$ git log --oneline
4fa042a [REF] vinc_course: tách hàm tiện ích
3609b42 [ADD] vinc_course: README
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
47905cb [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git log --oneline --grep='^\[FIX\]'
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
$ git log --oneline -- models/
4fa042a [REF] vinc_course: tách hàm tiện ích
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
47905cb [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git shortlog -sn --no-merges HEAD
     6	Nguyễn Văn An

Hai lời khuyên nữa từ tài liệu Odoo: tránh một commit đụng nhiều module cùng lúc (khó revert từng module), và tránh tiêu đề chung chung như “bugfix” hay “improvements”.

Một lợi ích nữa: viết changelog gần như miễn phí. Giả sử bản v1.0.0 đã phát hành ở commit thứ hai trong lịch sử trên; mọi thứ sau đó là nội dung cho bản kế tiếp, và nhờ thẻ bạn tách riêng được các bản sửa lỗi để báo khách hàng:

$ git tag -a v1.0.0 -m "Phát hành 1.0.0" HEAD~4
$ git log --oneline v1.0.0..HEAD
4fa042a [REF] vinc_course: tách hàm tiện ích
3609b42 [ADD] vinc_course: README
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
$ git log --oneline v1.0.0..HEAD --grep='^\[FIX\]'
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm

Cú pháp v1.0.0..HEAD nghĩa là “các commit có trong HEAD mà không có trong v1.0.0”. Kết hợp với tag phát hành (bài 9), đây là cách nhóm trả lời câu hỏi “bản này khác bản trước ở đâu?” trong vài giây.

Để mỗi commit làm đúng một việc ngay cả khi bạn lỡ sửa nhiều thứ trong cùng một file, hãy dùng git add -p (--patch): Git đưa từng đoạn thay đổi (hunk) ra và hỏi bạn có đưa vào staging không, nhờ vậy bạn tách “thêm trường” khỏi “dọn comment” thành hai commit riêng.

Quy ước đặt tên nhánh

Tiền tốDùng choVí dụ
feature/Tính năng mớifeature/course-price
fix/Sửa lỗi không khẩnfix/duplicate-code
hotfix/Sửa gấp bản đang chạyhotfix/1.0.1
release/Chuẩn bị hoặc duy trì một bản phát hànhrelease/1.0
experiment/Thử nghiệm có thể bỏexperiment/video
mã issueTheo tài liệu GitLab, tiền tố mã issue giúp điền sẵn tiêu đề và đóng issue12-course-price

Hãy viết chữ thường, nối bằng dấu gạch ngang và tránh ký tự đặc biệt. Git từ chối vài tên không hợp lệ; lệnh git check-ref-format --branch cho bạn kiểm tra trước:

$ git check-ref-format --branch feature/course-price
feature/course-price
$ git check-ref-format --branch "feature/course price"
fatal: 'feature/course price' is not a valid branch name
$ git check-ref-format --branch 12-course-price
12-course-price

Chiến lược nhánh gọn cho module khách hàng

Tài liệu gitworkflows mô tả quy trình đầy đủ của chính dự án Git, với bốn nhánh tích hợp (maint, master, next, seen) và chính nó nhắc rằng với dự án nhỏ, ít người thì không cần quy trình đầy đủ. Với một nhóm làm module Odoo cho khách hàng, một phiên bản đơn giản là đủ và dễ giữ kỷ luật:

Chiến lượcCách hoạt độngHợp với
Trunk-based / GitLab-style đơn giảnMột nhánh main được bảo vệ; nhánh tính năng ngắn hạn merge qua MR; tag cho mỗi bản phát hànhNhóm nhỏ–vừa, phát hành thường xuyên (khuyến nghị)
Thêm nhánh releaseTách release/x.y khi cần duy trì nhiều bản cùng lúc; chỉ nhận hotfixKhách hàng giữ bản cũ lâu
Nhánh theo phiên bản OdooMỗi phiên bản Odoo có nhánh riêng (ví dụ 20.0), tính năng tách từ đóModule phải hỗ trợ nhiều bản Odoo
Nhánh develop dài hạnCó thêm tầng tích hợp giữa tính năng và mainChỉ khi thật cần; dễ sinh xung đột lớn

GitLab cho phép chọn cách merge của dự án, trong đó có fast-forward (không tạo merge commit), nên thống nhất với nhóm: merge commit để thấy rõ từng MR, hay lịch sử thẳng bằng squash hoặc fast-forward. Dù chọn gì, hãy ghi lại trong README hoặc tài liệu đóng góp để người mới không phải đoán.

Bộ quy tắc nhóm một trang

  • Không commit thẳng lên main; mọi thay đổi đi qua merge request có ít nhất một người xem.
  • Một nhánh, một mục đích; sống tối đa vài ngày; xóa sau khi merge (cả cục bộ và remote).
  • Lời nhắn commit theo [TAG] module: mô tả và nêu lý do ở phần thân.
  • Chỉ rebase nhánh riêng; không viết lại lịch sử đã chia sẻ (bài 8).
  • Mỗi bản phát hành có tag annotated vX.Y.Z khớp với version trong manifest (bài 9).
  • Không commit bí mật; .gitignore có sẵn từ commit đầu (bài 2).

Lỗi hay gặp khi mới học

  • Lời nhắn vô nghĩa. “update”, “fix bug”, “sửa lại” không cho ai biết gì. Hãy viết tiêu đề đọc được như một câu và thêm lý do ở thân.
  • Một commit khổng lồ. Gom tính năng, sửa lỗi và dọn code vào một commit khiến review khó và không thể revert riêng từng phần. Chia nhỏ bằng git add từng file hoặc git add -p.
  • Nhánh sống quá lâu. Nhánh tồn tại hàng tuần lệch xa main và gây xung đột lớn khi merge. Hãy cắt việc nhỏ hơn và kéo main về thường xuyên.
  • Mỗi người một quy ước. Người viết “Feature:”, người viết “feat:”, người viết “[IMP]”: tìm kiếm trở nên vô nghĩa. Hãy chọn một mẫu, ghi vào tài liệu nhóm và để công cụ kiểm tra (bài 11).
  • Tên nhánh có dấu cách hoặc ký tự lạ. Git từ chối với “is not a valid branch name” như kết quả check-ref-format ở trên; dùng dấu gạch ngang.

Tổng kết

  • Commit: [TAG] module: mô tả, tiêu đề ngắn, thân giải thích vì sao, kết thúc bằng Closes #n.
  • Nhánh: tiền tố feature/, fix/, hotfix/, release/; chữ thường nối bằng gạch ngang.
  • Chiến lược: main được bảo vệ, nhánh ngắn hạn, merge request, tag phát hành, nhánh release khi cần.
  • Quy ước chỉ có tác dụng khi được viết ra và có công cụ kiểm tra.

Quy ước viết trong tài liệu dễ bị quên lúc gấp. Bài tiếp theo biến chúng thành thứ máy kiểm tra giúp bạn: Git hook chặn commit sai mẫu hay lọt mật khẩu ngay trên máy, và GitLab CI chạy kiểm tra tự động cho module Odoo trong mỗi merge request.

Câu hỏi thường gặp

Commit message tốt trông như thế nào? ▾
Theo hướng dẫn Git của Odoo: [TAG] module: tiêu đề một câu ngắn (lý tưởng dưới 50 ký tự), dòng trống, rồi phần mô tả giải thích vì sao thay đổi, kết thúc bằng tham chiếu như Closes #14. Tiêu đề nên nối được vào câu “commit này sẽ…”.
Các thẻ [ADD], [IMP], [FIX], [REF] khác nhau thế nào? ▾
[ADD] thêm module hay thành phần mới, [IMP] là cải tiến tăng dần, [FIX] sửa lỗi, [REF] tái cấu trúc lớn. Ngoài ra có [REM] xóa, [REV] revert, [MOV] di chuyển file, [MERGE] cho merge commit, [REL] phát hành và [I18N] cho file dịch.
Nên chọn chiến lược nhánh nào cho dự án Odoo của khách hàng? ▾
Với nhóm nhỏ đến vừa, hãy bắt đầu đơn giản: một nhánh main được bảo vệ, nhánh tính năng ngắn hạn merge qua merge request, và tag cho mỗi bản phát hành. Chỉ thêm nhánh release hoặc nhánh theo phiên bản Odoo khi phải duy trì nhiều bản song song.
Làm sao biết bản phát hành mới khác bản cũ ở đâu? ▾
Dùng git log --oneline v1.0.0..HEAD để liệt kê các commit chưa có trong tag cũ; thêm --grep="^\[FIX\]" để lọc riêng các bản sửa lỗi. Việc này dễ khi commit message theo quy ước có thẻ.
