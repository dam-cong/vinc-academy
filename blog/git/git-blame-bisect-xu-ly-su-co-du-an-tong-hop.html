Git blame, bisect và dự án tổng hợp cho nhóm Odoo

Bài cuối của series Git: dùng git blame, git log -S và git bisect run để tìm commit gây lỗi, rồi chạy trọn chu kỳ từ issue, merge request, tag đến hotfix và cherry-pick, kèm bảng tra cứu cả 12 bài.

Cập nhật: 16/10/2026 14 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Bài cuối giúp bạn tìm ra “ai và commit nào làm hỏng”, rồi ghép toàn bộ series thành một chu kỳ làm việc trọn vẹn. git blame cho biết mỗi dòng do commit nào sửa lần cuối, git log -S tìm commit đã thêm hay bớt một đoạn chữ, git bisect run tự dò nhị phân commit gây lỗi. Phần tổng hợp chạy thật quy trình: nhận issue, nhánh, commit, rebase, push, merge request, tag, hotfix và cherry-pick về main, kèm bảng tra cứu 12 bài.

Truy dấu từng dòng: git blame và git log -S

Khi một hàm trả kết quả sai, câu hỏi đầu tiên là “dòng này thêm vào từ khi nào, vì lý do gì?”. git blame in từng dòng kèm mã commit, tác giả và thời gian của lần sửa gần nhất; -L giới hạn phạm vi dòng hoặc theo tên hàm. Ở repo mẫu này hàm price_per_hour ban đầu chia giá cho số giờ, nhưng đồng nghiệp đã “tối ưu” nó. Blame chỉ ra thủ phạm ngay: dòng return thuộc commit của Bình, còn dòng def vẫn của An.

Nếu chưa biết dòng nằm ở đâu, hãy tìm theo nội dung. git log -S"chuỗi" (kiểu “pickaxe”) liệt kê các commit làm số lần xuất hiện của chuỗi đó thay đổi, tức là thêm hoặc xóa nó:

$ git log --oneline

4acd6a9 [ADD] vinc_course: changelog
fa33586 [IMP] vinc_course: thêm tổng số giờ

Blame cho biết commit cuối cùng đụng vào dòng, không phải lúc nào cũng là gốc của vấn đề: nếu ai đó chỉ sửa định dạng thì blame trỏ tới họ. Các cờ -M và -C theo dõi dòng được di chuyển hoặc sao chép giữa các file, còn --ignore-rev cho phép bỏ qua một commit định dạng hàng loạt. Dùng blame để hiểu bối cảnh và hỏi đúng người, không phải để đổ lỗi.

Dò nhị phân commit gây lỗi: git bisect

Khi bạn biết bản cũ chạy đúng (tag v1.0.0) và bản hiện tại sai, nhưng giữa chúng có hàng chục commit, git bisect giúp tìm ra commit đầu tiên gây lỗi bằng tìm kiếm nhị phân: mỗi bước nó chuyển bạn tới commit ở giữa khoảng còn nghi ngờ, bạn báo “tốt” hay “xấu”, và khoảng thu hẹp một nửa. Với 1.000 commit chỉ cần khoảng 10 bước. Bạn có thể tự bấm good/bad, hoặc giao cho một script: theo tài liệu, git bisect run gọi script ở mỗi bước và hiểu mã thoát 0 là tốt, 1–127 (trừ 125) là xấu, 125 là bỏ qua commit không kiểm tra được, còn mã khác sẽ hủy quá trình.

Script kiểm tra của chúng ta chỉ kiểm tra đúng một điều: giá 4.500.000 chia 24 giờ phải bằng 187.500. Nó nằm ngoài repo (để bisect đổi commit mà không làm mất nó):

python3 -c "import sys;sys.path.insert(0,'models');from utils import price_per_hour;sys.exit(0 if price_per_hour(4500000, 24) == 187500 else 1)"
$ git bisect start
status: waiting for both good and bad commits
$ git bisect bad
status: waiting for good commit(s), bad commit known
$ git bisect good v1.0.0
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[c7d5e2b0dbab2a4db579d1efc11cb7a69e32b386] [IMP] vinc_course: thêm kiểm tra khóa miễn phí
$ git bisect run sh $HOME/check.sh

Chỉ ba bước kiểm tra trên bảy commit, Git kết luận 8cff483 là commit đầu tiên gây lỗi, và ta xem nội dung của nó bằng git show. Nhớ chạy git bisect reset để quay về nhánh đang làm việc:

$ git show --stat --oneline 8cff483
8cff483 [IMP] vinc_course: tối ưu price_per_hour
 models/utils.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

Điều kiện để bisect hiệu quả là mỗi commit đều chạy được độc lập, đúng lời khuyên “chia thành các bước nhỏ, nhất quán” của tài liệu gitworkflows ở bài 10. Một lịch sử đầy commit hỏng giữa chừng sẽ làm bisect phải bỏ qua nhiều bước.

Dự án tổng hợp: một chu kỳ làm việc trọn vẹn

Giờ ghép các bài thành một ngày làm việc. An nhận issue #21 “thêm mã khóa học”, làm trên nhánh riêng, đẩy lên GitLab, MR được duyệt và merge, nhóm gắn tag 1.1.0; sau đó phát hiện nhãn chưa đẹp ở bản đang chạy nên làm hotfix 1.1.1 và đưa về main. Mỗi bước tương ứng một bài của series:

Bước 1–2. Lấy repo, tạo nhánh theo issue, commit đúng quy ước (bài 2, 3, 4, 10):

$ git commit -am "[IMP] vinc_course: thêm mã khóa học" -m "Closes #21"
[21-course-code 6802e7d] [IMP] vinc_course: thêm mã khóa học

Cách học nhanh nhất là tự dựng lại kịch bản trên một repo thử. Năm bài tập gợi ý:

  • Tạo một repo bare làm “GitLab” (git init --bare) và clone hai bản để tự đóng vai An và Bình.
  • Cố tình tạo một xung đột trong __manifest__.py rồi giải quyết bằng cả merge lẫn rebase.
  • Viết hook commit-msg của riêng bạn và thử bỏ qua nó bằng --no-verify.
  • Gắn tag, tách hotfix từ tag và cherry-pick về nhánh chính.
  • Gài một lỗi vào giữa lịch sử rồi dùng git bisect run tự tìm ra nó.

Khi Git báo lỗi lạ: bình tĩnh theo bốn bước

  • Đọc hết thông báo, nhất là các dòng hint:. Git thường ghi sẵn lệnh nên chạy, như bạn đã thấy ở các bài trước.
  • git status cho biết bạn đang ở đâu: nhánh nào, có đang merge/rebase dở không, file nào chờ xử lý.
  • git log --oneline --graph --all cho bức tranh lịch sử; kết hợp --decorate để thấy nhánh và tag.
  • Dừng lại trước khi dùng lệnh hủy diệt (reset --hard, clean -f, push --force). Tạo nhánh sao lưu, rồi nếu lỡ tay hãy nhờ git reflog.

Lỗi hay gặp khi mới học

  • Script bisect không chạy được ở một số commit. Ví dụ import cả package models sẽ kéo theo odoo và lỗi ngay. Nếu script thoát với mã lỗi chung, Git coi commit đó là “xấu” và cho kết luận sai. Hãy kiểm tra script trên một commit tốt và một commit xấu trước, và trả mã 125 khi không thể kiểm tra.
  • Quên git bisect reset. Bạn vẫn đang ở trạng thái bisect (HEAD tách rời). Chạy git bisect reset trước khi làm việc tiếp.
  • Dùng blame để đổ lỗi. Commit cuối cùng đụng vào dòng chưa chắc là nguyên nhân; hãy đọc git show của nó và hỏi người viết thay vì kết luận vội.
  • Đổi bản trong lúc bisect mà còn sửa dở. Hãy commit hoặc stash (bài 9) trước khi git bisect start để không mất việc.

Tổng kết cả series

  • Nền tảng: ba vùng làm việc, commit nhỏ có lời nhắn tốt, .gitignore ngay từ đầu.
  • Cộng tác: nhánh ngắn hạn, GitLab, merge request, xung đột và rebase đúng quy tắc.
  • An toàn: biết chọn lệnh hoàn tác, luôn có lưới reflog và nhánh sao lưu.
  • Phát hành: tag, hotfix từ tag, cherry-pick; hook và CI để máy kiểm tra thay con người.
  • Truy vết: blame, log -S, bisect để tìm nguyên nhân thay vì đoán.

Bước tiếp theo tự nhiên là áp dụng ngay vào dự án thật: tạo repo GitLab cho module của bạn, bật nhánh bảo vệ và thêm file .gitlab-ci.yml đầu tiên. Câu hỏi thường gặp

git blame dùng để làm gì? ▾
git blame in từng dòng của file kèm commit, tác giả và thời gian của lần sửa gần nhất, giúp bạn hiểu dòng đó xuất hiện khi nào và vì sao. Dùng -L để giới hạn dòng hoặc hàm, -M và -C để theo dõi dòng được di chuyển hay sao chép.
git bisect hoạt động thế nào? ▾
Bạn đánh dấu một commit tốt và một commit xấu; Git tìm nhị phân trong khoảng giữa, mỗi bước chuyển tới commit ở giữa để bạn kiểm tra rồi thu hẹp một nửa. Với git bisect run script, Git tự chạy script ở mỗi bước và dùng mã thoát để biết tốt hay xấu.
Mã thoát nào của script bisect có ý nghĩa đặc biệt? ▾
Theo tài liệu Git: 0 là commit tốt, 1 đến 127 (trừ 125) là commit xấu, 125 nghĩa là bỏ qua commit không kiểm tra được, các mã khác hủy quá trình bisect.
Làm sao tìm commit đã thêm hay xóa một đoạn chữ? ▾
Dùng git log -S"chuỗi" (pickaxe) để liệt kê các commit làm thay đổi số lần xuất hiện của chuỗi đó; git log -G dùng biểu thức chính quy. Sau đó git show mã-commit để xem nội dung.
