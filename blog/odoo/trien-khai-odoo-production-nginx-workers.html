Triển khai Odoo 20 production: Nginx, HTTPS, workers

Từ máy phát triển sang server thật cần nhiều hơn là chạy odoo-bin. Bài này tổng hợp cấu hình production: odoo.conf, dbfilter, PostgreSQL, workers, Nginx với HTTPS và checklist bảo mật trước khi mở ra Internet.

Cập nhật: 16/10/2026 17 phút đọc Đội ngũ Vinc Academy

Tóm tắt nhanh

Để triển khai Odoo 20 lên production, hãy chuyển từ chế độ multi-thread sang multi-process (workers), đặt Odoo sau reverse proxy như Nginx có HTTPS và bật proxy_mode, giới hạn database bằng dbfilter, đặt admin_passwd mạnh, tắt danh sách database và không cài dữ liệu demo. PostgreSQL dùng user riêng không phải superuser.

Production khác môi trường phát triển ở đâu?

Máy phát triển chỉ cần chạy được. Server hướng ra Internet thì cần thêm cấu hình hệ thống: chọn database nào được phục vụ, kết nối PostgreSQL ra sao, bao nhiêu tiến trình xử lý request, mã hóa đường truyền bằng HTTPS và những thiết lập bảo mật cơ bản. Tài liệu Odoo mô tả các bước này ở trang cấu hình hệ thống, áp dụng sau khi bạn đã cài xong như ở bài 2. Phần dưới đây tóm tắt trình tự nên làm.

File cấu hình odoo.conf

Thay vì gõ nhiều tham số dòng lệnh, đặt cấu hình trong file. Đây là mẫu cho một server có kết nối PostgreSQL riêng:

[options]
admin_passwd = <chuỗi ngẫu nhiên, dài>
db_host = 127.0.0.1
db_port = 5432
db_user = odoo
db_password = <mật khẩu>
dbfilter = ^mycompany$
list_db = False
proxy_mode = True
workers = 5
max_cron_threads = 1
limit_memory_soft = 629145600
limit_memory_hard = 1677721600
limit_time_cpu = 600
limit_time_real = 1200

Các mục quan trọng sẽ được giải thích bên dưới.

dbfilter: chọn database theo tên miền

Odoo là hệ thống đa khách thuê (multi-tenant): một server có thể phục vụ nhiều database. Với người dùng đã đăng nhập backend thì chọn database lúc đăng nhập, nhưng với khách chưa đăng nhập (website, portal) Odoo cần quy tắc để biết dùng database nào. dbfilter là một biểu thức chính quy quyết định điều đó dựa trên tên miền được yêu cầu, có thể chứa %h (hostname) hoặc %d (subdomain đầu tiên). Với server có nhiều database, đặc biệt khi dùng website, bắt buộc phải đặt dbfilter.

Khi mỗi tên miền chỉ khớp một database, hãy đặt thêm list_db = False (tương đương tham số --no-database-list) để không liệt kê database và chặn các màn hình quản lý database.

PostgreSQL cho production

  • Mặc định PostgreSQL chỉ cho kết nối qua UNIX socket và loopback. Nếu Odoo và PostgreSQL chạy khác máy, PostgreSQL phải lắng nghe qua mạng (hoặc dùng SSH tunnel), và bạn cấu hình db_host, db_port, db_user, db_password trong Odoo.
  • User PostgreSQL của Odoo không được là superuser. Nên để database thuộc một user khác user mà Odoo dùng để kết nối.
  • Có thể bắt buộc kết nối SSL giữa Odoo và PostgreSQL bằng db_sslmode (các giá trị: disable, allow, prefer, require, verify-ca, verify-full).
  • Màn hình quản lý database được bảo vệ bằng admin_passwd, chỉ đặt được trong file cấu hình. Hãy đặt giá trị ngẫu nhiên, dài.

Workers: multi-process thay cho multi-thread

Odoo có hai kiểu server tích hợp. Multi-thread đơn giản, dùng cho phát triển và demo, chạy được trên cả Windows, nhưng không tận dụng tốt phần cứng do giới hạn GIL của Python; đây là chế độ mặc định (khi bỏ --workers hoặc đặt bằng 0). Multi-process dành cho production: tạo một nhóm worker lúc khởi động, request mới xếp hàng chờ worker rảnh, có worker cron riêng và một bộ giám sát tài nguyên có thể kill/khởi động lại worker lỗi. Chế độ này bật bằng cách đặt workers là một số nguyên khác 0 và không chạy được trên Windows.

Ước lượng số worker và RAM

  • Quy tắc tham khảo: số worker tối đa = (số CPU × 2) + 1; worker cron cũng tốn CPU.
  • Khoảng 1 worker phục vụ ~6 người dùng đồng thời.
  • Giả định 20% request nặng và 80% nhẹ; worker nặng dùng khoảng 1GB RAM, worker nhẹ khoảng 150MB (khi computed field và truy vấn SQL được thiết kế tốt). RAM cần = số worker × (0,8 × 150MB + 0,2 × 1GB).

Ví dụ trong tài liệu: server 4 CPU, 60 người dùng đồng thời. Lý thuyết cần 10 worker (60/6), tối đa 9 theo quy tắc CPU; chọn 8 worker + 1 cho cron, cần khoảng 3GB RAM cho Odoo, và dùng hệ thống giám sát để theo dõi tải CPU.

Giới hạn và tái chế worker

Bộ giám sát tiến trình của chế độ multi-process dựa trên các giới hạn sau (đơn vị bộ nhớ là byte, mẫu cấu hình ở trên dùng giá trị khác mặc định để phù hợp một server nhỏ):

Tham sốMặc địnhTác dụng
limit_memory_soft2048 MiBBộ nhớ ảo tối đa mỗi worker; vượt thì worker bị kill và tái chế vào cuối request hiện tại
limit_memory_hard2560 MiBGiới hạn cứng; worker vượt sẽ bị kill ngay, không chờ hết request
limit_time_cpu60Số giây CPU tối đa cho mỗi request; vượt thì worker bị kill
limit_time_real120Giới hạn "thời gian thực" (kể cả chờ truy vấn SQL) cho mỗi request; vượt thì worker bị kill
limit_request8196Số request một worker xử lý trước khi được tái chế và khởi động lại
max_cron_threads2Số worker dành cho cron; ở multi-process là thêm vào các worker HTTP

Cổng live chat --gevent-port mặc định là 8072 và chỉ dùng ở chế độ multi-process hoặc gevent.

HTTPS với Nginx và proxy_mode

Odoo truyền thông tin đăng nhập dạng bản rõ, vì vậy triển khai an toàn bắt buộc dùng HTTPS. Cách phổ biến là đặt Odoo sau một reverse proxy kết thúc SSL như Nginx, kèm ba việc: bật proxy_mode (chỉ khi Odoo thật sự đứng sau proxy), cấu hình proxy kết thúc SSL, cấu hình chuyển tiếp request, và tự chuyển hướng HTTP sang HTTPS. Mẫu rút gọn:

upstream odoo     { server 127.0.0.1:8069; }
upstream odoochat { server 127.0.0.1:8072; }

map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 80;
    server_name odoo.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name odoo.example.com;
    ssl_certificate     /etc/ssl/nginx/server.crt;
    ssl_certificate_key /etc/ssl/nginx/server.key;
    proxy_read_timeout 720s;

    location /websocket {
        proxy_pass http://odoochat;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location / {
        proxy_pass http://odoo;
        proxy_redirect off;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";
    }
}
  • Ở chế độ multi-process có một worker live chat riêng lắng nghe cổng --gevent-port (mẫu trên là 8072). Proxy phải chuyển các request có đường dẫn bắt đầu bằng /websocket/ tới worker này.
  • Header Strict-Transport-Security ép trình duyệt luôn dùng HTTPS; từ đó bạn phải duy trì HTTPS hợp lệ liên tục, nếu không người dùng sẽ gặp cảnh báo hoặc không truy cập được.
  • Có thể phục vụ file tĩnh (đường dẫn /<module>/static/...) trực tiếp bằng Nginx để giảm tải cho Odoo; root và try_files phụ thuộc vào --addons-path của bạn.

proxy_mode hoạt động thế nào?

proxy_mode cho phép dùng các header X-Forwarded-* qua hỗ trợ proxy của Werkzeug. Có hai điểm dễ bỏ sót: Odoo bỏ qua mọi header X-Forwarded-* nếu request thiếu X-Forwarded-Host, và IP thật luôn lấy từ phần tử cuối của chuỗi X-Forwarded-For. Vì vậy cấu hình web server phải gửi đủ các header như mẫu Nginx ở trên. Nếu bạn vô tình truy cập Odoo trực tiếp (không qua Nginx) khi đã bật proxy_mode, Odoo ghi cảnh báo kèm cấu hình cần thiết.

Chạy Odoo như ứng dụng WSGI

Có thể gắn Odoo như một ứng dụng WSGI chuẩn. Odoo cung cấp script mẫu odoo-wsgi.example.py để bạn tùy chỉnh, và cấu hình đặt trực tiếp trong odoo.tools.config thay vì dòng lệnh hoặc file cấu hình. Lưu ý máy chủ WSGI chỉ phục vụ endpoint HTTP chính (web client, website, web service); vì Odoo không còn kiểm soát việc tạo worker nên không tự dựng được worker cron hay live chat:

  • Cron: phải chạy thêm một server tích hợp của Odoo cạnh server WSGI, cấu hình chỉ xử lý cron bằng --no-http (hoặc http_enable = False). Trên Linux nên dùng multi-process, ví dụ --workers=-1 cùng --max-cron-threads=n.
  • Live chat: cần một server WSGI tương thích gevent, xử lý được nhiều kết nối dài đồng thời nhưng không cần nhiều sức mạnh tính toán. Mọi request có đường dẫn bắt đầu bằng /websocket/ phải chuyển tới server này, còn request khác đi vào server WSGI thông thường. Cũng có thể dùng chính server cron cho live chat bằng cách bỏ --no-http.

Checklist bảo mật khi mở ra Internet

  • Đặt admin_passwd mạnh và khóa các trang quản lý database ngay sau khi dựng hệ thống.
  • Không dùng admin làm tên đăng nhập, và không dùng tài khoản quản trị cho công việc hằng ngày. Không bao giờ dùng mật khẩu mặc định như admin/admin, kể cả database test hoặc staging.
  • Không cài dữ liệu demo trên server công khai: database demo chứa tài khoản và mật khẩu mặc định có thể bị lợi dụng.
  • Dùng dbfilter, đặt list_db = False; user PostgreSQL không phải superuser.
  • Cập nhật bản build mới thường xuyên; chạy chế độ multi-process với giới hạn phù hợp (bộ nhớ, CPU, thời gian).
  • Chạy sau web server có HTTPS với chứng chỉ hợp lệ, giới hạn kích thước request, đặt timeout rồi bật proxy mode.
  • SSH chỉ dùng khóa công khai, cân nhắc VPN, firewall chỉ cho IP tin cậy và công cụ chống brute-force như fail2ban; đặt giới hạn tần suất ở proxy hoặc firewall.
  • Đặt server demo, test, staging ở máy khác production và áp dụng cùng biện pháp bảo mật.

Về sao lưu

Dữ liệu Odoo gồm database PostgreSQL và filestore (với image Docker chính thức là thư mục /var/lib/odoo, như volume ở bài 2). Bài này chưa đi sâu phương án sao lưu và giám sát vì chúng phụ thuộc hạ tầng của bạn; hãy lập kế hoạch cho cả hai thành phần trước khi go-live và thử khôi phục định kỳ.

Lỗi hay gặp khi triển khai

  • Đặt Nginx phía trước nhưng quên bật proxy_mode. Khi đó Odoo dùng thông tin của proxy thay vì của người dùng thật (hostname, scheme, IP). Cần khởi động Odoo với proxy mode để nó đọc các header X-Forwarded-* mà proxy gửi. Chỉ bật khi Odoo thật sự nằm sau reverse proxy.
  • Đưa server lên Internet với database có dữ liệu demo hoặc mật khẩu admin/admin. Tài liệu cảnh báo đây là mật khẩu mặc định có thể bị khai thác ngay cả trên staging. Tạo database mới không có demo, đổi tên đăng nhập và mật khẩu quản trị.
  • Quên chuyển request /websocket/ tới worker live chat. Ở chế độ multi-process, theo mặc định các request vẫn đi vào worker HTTP thông thường. Bạn phải cấu hình proxy chuyển đường dẫn bắt đầu bằng /websocket/ sang cổng --gevent-port và chạy Odoo với proxy mode.

Tổng kết

  • Production: multi-process (workers), Nginx + HTTPS, proxy_mode, dbfilter, list_db = False.
  • PostgreSQL dùng user riêng không phải superuser; không cài dữ liệu demo; không dùng mật khẩu mặc định.
  • Ước lượng worker bằng (CPU × 2) + 1 và ~6 người dùng mỗi worker; đặt giới hạn bộ nhớ và thời gian.
  • Chuyển /websocket/ tới worker live chat; thử khôi phục sao lưu trước khi go-live.

Đến đây bạn đã đi qua toàn bộ vòng đời của một module Odoo 20, từ khái niệm, cài đặt, viết code, giao diện, tích hợp, kiểm thử cho tới triển khai thật. Hãy chọn khóa học phù hợp để tiếp tục thực hành cùng mentor.

Câu hỏi thường gặp

Odoo production nên chạy multi-thread hay multi-process? ▾
Nên chạy multi-process bằng cách đặt workers là một số nguyên khác 0. Chế độ multi-thread là mặc định, đơn giản và phù hợp phát triển hoặc demo nhưng không tận dụng tốt phần cứng do giới hạn GIL của Python.
Công thức ước lượng số worker như thế nào? ▾
Số worker tối đa theo quy tắc tham khảo là số CPU nhân 2 cộng 1, và khoảng 1 worker phục vụ 6 người dùng đồng thời. Worker cron cũng tốn CPU nên cần tính thêm.
proxy_mode dùng để làm gì? ▾
Khi Odoo chạy sau reverse proxy như Nginx, bật proxy_mode để Odoo dùng các header thật của người dùng như hostname, scheme và IP thay vì của proxy. Chỉ bật khi Odoo thực sự đứng sau proxy.
Vì sao phải đặt dbfilter và list_db? ▾
dbfilter cho Odoo biết database nào phục vụ cho tên miền nào, bắt buộc khi một server chứa nhiều database. Khi mỗi tên miền chỉ khớp một database, đặt list_db bằng False để không liệt kê database và chặn các màn hình quản lý database.
