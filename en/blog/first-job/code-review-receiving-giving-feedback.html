Code Review for Newcomers: Giving and Receiving Feedback

Your first merge request just came back with twenty comments. That's not bad news: code review is where newcomers learn fastest. This guide shows how to prepare a change that's easy to review, read and handle feedback calmly, and comment on other people's code with confidence.

Updated: October 16, 2026 10 min read – views Vinc Academy Team

Quick answer

Code review exists to make the code better, not to grade the person who wrote it. Send small changes that do one thing, with tests and a clear "what and why". When receiving feedback: don't take it personally, clarify the code instead of only explaining in comments, and back disagreements with facts. When reviewing others: comment on the code, explain why and label the severity.

What is code review for?

In Google's public engineering practices documentation, code review exists to keep improving the overall health of the codebase. That leads to a key principle: reviewers should approve a change once it makes the code better, even if it isn't perfect, because there is no perfect code, only better code.

The same guide stresses that code review is a channel for sharing knowledge about languages, frameworks and design. For newcomers this is the biggest benefit: every review is a free one-to-one lesson on the team's conventions and on mistakes you didn't know you were making.

On GitLab the unit of review is a merge request; on GitHub it's a pull request; Google's documentation says CL (changelist). In this article we call it a merge request (MR).

Preparing a merge request that's easy to review

1. Small and focused on one thing

Google recommends small changes because they're reviewed faster, more thoroughly and with fewer bugs slipping through; if the direction is rejected, less work is wasted. The main criterion is a self-contained change: it solves one thing, includes related tests, and a reviewer can understand it without outside context. The guide suggests around 100 lines is usually reasonable and around 1,000 lines usually too large, but that's only a reference.

  • Put refactoring in its own MR: renames and reorganising code should be separate from feature work or bug fixes.
  • Tests travel with the code: tests for new code live in the same MR.
  • No MR breaks the system: after merging, the project still runs and tests still pass.

2. Describe "what" and "why"

According to Google, the first line of a description is a short, specific summary that makes sense on its own; the body explains the problem, why this approach was chosen and any limitations. Descriptions like "Fix bug" or "Update" tell the reader nothing.

Weak description

Fix VC-128

Better description

Add a "Needs attention" tab listing students with more than 3 absences (VC-128)

Lecturers need early warning about students at risk of dropping out.

Common mistake: one giant merge request that "does all of VC-128"

Situation: you work on the ticket for a week, rename variables and reorganise a few files along the way, then send a 1,500-line MR across 30 files. Three days later nobody has finished reviewing it, and when they do, a permission bug still slips through.

Cause: large changes are hard to read carefully, so they're both slow and bug-prone; mixing refactoring with features means the reviewer can't tell which lines change behaviour.

Prevention: split it into several small MRs in order (for example, model and tests first, UI next), put refactoring in its own MR, and send the first MR early instead of waiting until everything is done.

Reading and handling feedback

Google's documentation has a section just for authors receiving comments. The key principles:

  • Don't take it personally: ask yourself what constructive point the reviewer is making.
  • Don't reply while annoyed: step away, do something else, come back when you're calm.
  • Fix the code rather than only explaining: if a reviewer doesn't understand some code, rewrite it to be clearer or add a comment in the code. Explanations that only live in review comments are invisible to future readers.
  • When you disagree: make sure you understood the comment, explain your reasoning and trade-offs, ask what they suggest, and seek consensus based on technical facts.

Many teams label comments by severity. Reading the labels helps you prioritise:

Common mistake: arguing in comments instead of making the code clearer

Situation: the reviewer asks "what does this part do?" and you reply with a long explanation that the code works correctly. Five back-and-forths later, the MR still isn't approved.

Cause: the reviewer's question signals that the code doesn't explain itself. Google's guidance is to make the code clearer (rename, extract a function, add an in-code comment), because future readers will have the same question without the review thread to look at.

Prevention: for "what does this do" questions, fix the code first and reply "I renamed the function and added a comment, could you take another look?". For genuine disagreements about approach, a few minutes of direct conversation is usually faster than ten comments.

When you're the reviewer

Many teams let newcomers join reviews early, because reading others' code is the fastest way to learn the codebase. Google's guidance for reviewers:

  • Be courteous and comment on the code, not the person.
  • Explain your reasoning instead of just giving orders.
  • Label severity (Nit, Optional, FYI) so the author knows what must be fixed now.
  • Praise what's done well and say why.
  • Respond quickly: within one business day at most. Google stresses that slow reviews slow the whole team, not just one person.

When you're not sure your comment is right, phrase it as a question: "I'm not sure, how does this handle an empty list?". Questions help you learn and don't pressure the author.

AI in code review

Many teams use AI tools to catch obvious issues first. For newcomers, a sensible use is asking AI to check your own MR before sending it, then judging each suggestion yourself. The two rules from Your first week still apply: only use tools your company allows, and you remain responsible for the code you submit.

Summary

  • Code review improves the codebase over time and is a newcomer's fastest learning channel.
  • Send small MRs that do one thing, with tests, refactoring split out; describe what, why and how it was tested.
  • Review your own diff before asking others, and in particular check you're not leaking passwords.
  • Take feedback calmly, clarify the code instead of only explaining, and read Nit/Optional/FYI labels to prioritise.
  • When reviewing: comment on the code, explain why, label severity, praise good work and reply within one business day.

Frequently asked questions

How many lines should a merge request be? ▾
There's no hard number. Google's code review guide suggests about 100 lines is usually reasonable and about 1,000 lines is usually too big; the main criterion, though, is that each change does one complete thing with its related tests. When in doubt, split it smaller.
Does getting lots of review comments mean my code is bad? ▾
No. For newcomers, many comments are normal and the fastest way to learn the team's conventions. Code review is about keeping the codebase healthy, not judging people; what matters is fixing things systematically and not repeating the same mistake.
What should I do if I disagree with a comment? ▾
First make sure you understand what the reviewer means, and ask if you don't. Then explain your reasoning and the trade-offs of your approach, and ask what they suggest. Look for consensus based on technical facts rather than arguing; if you still disagree, ask the team lead for input.
Should newcomers review other people's code? ▾
Yes, if the team allows it. Reading others' code is a very fast way to learn the codebase. Start with questions to understand, comment on readability and tests, and label your comments by severity; the final approval usually still rests with someone more experienced.
What does Nit mean in code review? ▾
A Nit is a minor comment, usually about formatting or naming, that doesn't have to be fixed for approval. Labels like Nit, Optional or FYI tell the author which comments need fixing now and which are just for reference.
