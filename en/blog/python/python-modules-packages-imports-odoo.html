Python Modules, Packages and Imports: Understanding Odoo __init__.py

Every time you add a model or controller to an Odoo module you must edit an __init__.py file. This guide explains modules, packages, relative imports and how Python finds code, so you understand why one missing import line makes a model vanish.

Updated: October 16, 2026 13 min read – views Vinc Academy Team

Quick summary

A .py file is a module and a folder with __init__.py is a package. You use import to pull code from another module. In an Odoo module, the __init__.py at the root and in models/ form the import chain that brings model files into the system: miss one from . import course line and the model does not exist. Python looks modules up through sys.path, and a file with an if __name__ == "__main__": block can both run directly and be imported.

Modules: one Python file is a small library

Any .py file can be loaded by another. There are three ways to write an import:

import math                         # load the whole module, use math.sqrt(...)
import math as m                    # give it an alias
from math import sqrt, pi           # pull in specific names

print(math.sqrt(16), m.sqrt(25), sqrt(9), round(pi, 2))
# 4.0 5.0 3.0 3.14
  • import math loads the whole module; you call through the module name (math.sqrt), making the origin obvious.
  • import math as m gives a short name; common with long library names.
  • from math import sqrt brings one name straight into use; short but prone to name clashes if you import many.

The standard library ships hundreds of modules (math, json, datetime, csv, re...), and you will use many in later parts. Third-party libraries (such as requests) are installed with pip as in part 1 and imported the same way.

Packages: a folder holding several modules

As a project grows you gather related files into a folder and add an __init__.py so Python treats it as a package. This is how you would organize a small toolkit for the course project:

vinc-tools/
├── main.py
└── vinc_tools/
    ├── __init__.py
    ├── courses.py
    └── report.py
# vinc_tools/courses.py
PREFIX = "ODO"

def make_code(seq):
    return f"{PREFIX}-{seq:03d}"

if __name__ == "__main__":
    print("run directly:", make_code(1))
# vinc_tools/__init__.py
from .courses import make_code
# vinc_tools/report.py
from . import courses
from .courses import make_code as mk

def line(seq):
    return courses.PREFIX + ":" + mk(seq)
# main.py (next to the vinc_tools folder)
import vinc_tools
from vinc_tools import report
from vinc_tools.courses import PREFIX
import vinc_tools.courses as vc

print(vinc_tools.make_code(7), report.line(2), PREFIX, vc.PREFIX)
print(__name__)
$ python3 main.py
ODO-007 ODO:ODO-002 ODO ODO
__main__

$ python3 vinc_tools/courses.py
run directly: ODO-001
  • from .courses import make_code in __init__.py is a relative import: the dot means "inside this same package". Thanks to it users can call vinc_tools.make_code without knowing which file holds it.
  • from . import courses loads the package's own courses module, while from .courses import make_code as mk takes one name and renames it.
  • __init__.py runs once, right when the package is loaded.

The if __name__ == "__main__" block

Every module has a __name__ variable. When a file is run directly with python file.py, __name__ equals "__main__"; when it is imported, __name__ is the module's name. The if __name__ == "__main__": block therefore runs only when you run the file as a script, ideal for a quick trial or a program's entry point (you will use it in part 14). Compare the two commands above: main.py prints __main__, while importing vinc_tools.courses does not show the "run directly" line.

Where does Python look for modules?

On import x Python searches the sys.path list in order: the folder of the running script (or the current directory in interactive mode, shown as an empty-string entry), then the standard library and your environment's library location. That is why running python3 main.py from the project folder lets import vinc_tools succeed, while running from elsewhere may fail to find it. The virtual environment from part 1 also changes the search: pip install inside a venv puts packages in the venv's own folder.

Odoo uses a different mechanism with the same spirit: the list of module folders is declared with --addons-path (part 2 of the Odoo series), and Odoo looks for directories containing __manifest__.py in them.

Exploring a module: dir, help and __file__

When you meet an unfamiliar module you need not open the docs straight away. Three built-in tools answer most questions: dir(module) lists the names inside, help(module.func) or the __doc__ attribute prints the description, and module.__file__ shows where the source lives (very handy when you want to read Odoo's or a library's code). Python also keeps loaded modules in sys.modules, so a second import costs almost nothing and a module's code runs only once.

import math
print([n for n in dir(math) if n in ("sqrt", "pi", "floor", "ceil")])
# ['ceil', 'floor', 'pi', 'sqrt']
print(math.sqrt.__doc__.splitlines()[0])
# Return the square root of x.

import sys
print("math" in sys.modules, "requests" in sys.modules)
# True False   (an imported module is cached, so the second import is very fast)

A common convention is to group the import lines at the top of a file: standard library first, third-party libraries next, your project's own modules last, with a blank line between groups. Glancing at the top of a file tells a reader what it depends on, which is also why the from odoo import ... lines always sit up there.

The import chain in an Odoo module

# vinc_course/__init__.py
from . import models

# vinc_course/models/__init__.py
from . import course
from . import course_category

# vinc_course/models/course.py
from odoo import api, fields, models
from odoo.exceptions import ValidationError

These two __init__.py files are where many newcomers get hurt. Create models/course.py but forget from . import course and Python never runs the VincCourse class, Odoo does not know the model vinc.course exists, and no table is created on upgrade. Odoo's official tutorial describes exactly this chain: the model sits in models/, its file is imported in models/__init__.py, and the models folder is imported in the root __init__.py. The from odoo import api, fields, models lines at the top of a file are imports from Odoo's own library.

You want toWrite
Add a new modelCreate models/name.py + from . import name in models/__init__.py
Add a controllerCreate controllers/main.py + from . import main in controllers/__init__.py
Add a testFile tests/test_x.py + from . import test_x in tests/__init__.py
Use an external libraryimport requests and declare it in the manifest's external_dependencies

The pattern "each sub-folder's __init__.py imports its files" repeats for controllers and tests; tests also follow the test_*.py file-name convention (part 13 of the Odoo series).

Practice: build a small package

  1. Create the vinc-tools/vinc_tools/ structure above with its three files.
  2. From the vinc-tools folder run python3 main.py and check the first output line is ODO-007 ODO:ODO-002 ODO ODO.
  3. Run python3 vinc_tools/courses.py and see the "run directly" line.
  4. Try removing the import line in __init__.py and watch the error when main.py calls vinc_tools.make_code.

Common mistakes when starting out

import nonexistent_mod
# ModuleNotFoundError: No module named 'nonexistent_mod'

from vinc_tools import nothing
# ImportError: cannot import name 'nothing' from 'vinc_tools' (.../vinc_tools/__init__.py)

# running a file with relative imports directly:
# $ python3 vinc_tools/report.py
# ImportError: attempted relative import with no known parent package
  • ModuleNotFoundError. Python cannot find the module: it was not installed with pip (or you are in the wrong virtual environment), the name is wrong, or you run from a folder that leaves the project off sys.path.
  • Running a file with relative imports directly. python3 vinc_tools/report.py fails with "attempted relative import with no known parent package" because the file is not loaded as part of the package. Run through a file outside the package (like main.py).
  • Circular imports. Two modules importing each other cause ImportError: cannot import name ... (most likely due to a circular import):
# circ/a.py
from circ.b import fb
def fa(): return "a"

# circ/b.py
from circ.a import fa
def fb(): return "b"

# import circ.a  ->
# ImportError: cannot import name 'fa' from partially initialized module 'circ.a'
#   (most likely due to a circular import)

# Fix: move the import inside the function
# circ/b.py
def fb():
    from circ.a import fa      # imported only when the function runs
    return "b" + fa()

The best cure is restructuring so dependencies run one way (move shared pieces to a third module); moving an import into a function is only a quick patch.

Summary

  • A .py file = a module; a folder with __init__.py = a package; import pulls code from elsewhere.
  • Use relative imports (from . import x) inside one package.
  • if __name__ == "__main__": runs only when the file is run directly.
  • Odoo modules: every __init__.py must import its child files, and a missing line means a missing model.

FAQ

Why does an Odoo module need an __init__.py file? ▾
__init__.py turns a folder into a package and holds the import lines (such as from . import models) that make Python load model and controller files. Without the import line the model class never runs, so Odoo does not know the model exists.
What is if __name__ == "__main__" for? ▾
That block runs only when the file is run directly with python file.py, and not when the file is imported. It usually holds a quick trial or a script's entry point.
What is the difference between relative and absolute imports? ▾
A relative import uses dots to point inside the same package, for example from . import course. An absolute import spells the full path from the top, for example from vinc_tools.courses import make_code.
How do I fix a circular import error? ▾
Restructure so modules depend in one direction, for example by moving shared code into a third module. A quick patch is to move the import statement inside the function that needs it.
