Python Debugging, Logging and Testing: a Small Project

The final part assembles everything into a command-line tool: debug with breakpoint() and pdb, write levelled logs, test with unittest and Mock, add type hints, then finish a script that imports courses from CSV into Odoo.

Updated: October 16, 2026 16 min read Vinc Academy Team

Quick summary

The final part gathers every skill into one complete program: read a CSV, validate data, call Odoo's JSON-2 API, write logs and have a test suite. The tools along the way: breakpoint() for line-by-line debugging, logging instead of print, unittest (the base of Odoo's TransactionCase) with Mock so tests need no network, and type hints so code describes itself. At the end sits a working import_courses.py script, checked with 6 tests and a mock server.

Debugging: breakpoint() and pdb

Instead of sprinkling print everywhere, stop the program exactly where you suspect trouble and look around. The built-in breakpoint() opens the pdb debugger at that line:

def price_per_hour(price, hours):
    breakpoint()                    # stop here and open the pdb debugger
    return price / hours

price_per_hour(4500000, 24)
# > script.py(3)price_per_hour()
# -> return price / hours
# (Pdb) p hours                    <- print a variable
# 24
# (Pdb) n                          <- run the next line
# (Pdb) c                          <- continue to the end or the next breakpoint
pdb commandEffect
p expressionPrints a variable or expression
n (next)Runs the next line without entering functions
s (step)Runs the next line and steps into a called function
c (continue)Runs on to the end or the next breakpoint
l (list)Shows the code around the current line
w (where)Shows the call stack (like a traceback)
q (quit)Leaves the debugger

You can also run a whole program under the debugger with python3 -m pdb script.py. With Odoo, the usual route is pip install ipdb and placing import ipdb; ipdb.set_trace() where you want to stop, as mentioned in part 2 of the Odoo series, running the server in a terminal so you can type commands. Remember to remove breakpoints before committing: a stray breakpoint() left on a server freezes the process waiting for someone to type.

logging: levelled logs

print does not say how important a message is, has no timestamp and cannot be silenced in production. logging solves all three:

import logging

print(logging.DEBUG, logging.INFO, logging.WARNING, logging.ERROR, logging.CRITICAL)
# 10 20 30 40 50

logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(name)s: %(message)s", datefmt="%H:%M:%S")
log = logging.getLogger("vinc.import")      # a named logger, usually __name__

log.debug("hidden because the level is INFO")
log.info("loaded %d courses", 5)            # 11:41:00 INFO vinc.import: đã nạp 5 khóa học
log.warning("course %s has no hours", "PY-F")     # 11:41:00 WARNING vinc.import: khóa PY-F thiếu giờ

try:
    1 / 0
except ZeroDivisionError:
    log.exception("calculation error")           # ERROR plus the full traceback
LevelValueUse it when
DEBUG10Detail for developers tracking a bug
INFO20Confirming things work as expected
WARNING30Something unusual but the program carries on (the default level)
ERROR40A job could not be done
CRITICAL50A serious error, the program may be unable to continue
  • Only messages at or above the configured level appear: with level=INFO the debug line is dropped.
  • Pass arguments separately (log.info("loaded %d", n)) rather than building the string with an f-string: the string is only assembled when the line is actually written.
  • log.exception(...) inside an except block records the traceback too.
  • Name loggers after the module (logging.getLogger(__name__)) so you can filter by source.

Odoo does exactly this: in Odoo code you meet _logger = logging.getLogger(__name__) followed by _logger.warning(...) (the server-action documentation has an example), and you tune verbosity with odoo-bin's --log-level option. Rule of thumb: print for a program's results, logging for everything else.

Writing tests with unittest

Automated tests run your code with known data and compare the outcome with what you expect. Python ships unittest, and Odoo's TransactionCase (part 13 of the Odoo series) is merely an extension of it: what you learn here carries straight over to testing models.

import unittest

class TestCourseRow(unittest.TestCase):
    def setUp(self):                          # runs before EACH test
        self.row = {"name": "  Odoo  ", "hours": "24"}

    def test_valid_row(self):
        course = CourseRow.from_dict(self.row)
        self.assertEqual(course, CourseRow(name="Odoo", hours=24))

    def test_bad_hours(self):
        for bad in ("abc", "0", "-3"):
            with self.subTest(hours=bad):     # each value is a separate check
                with self.assertRaises(InvalidRow):
                    CourseRow.from_dict({"name": "X", "hours": bad})

if __name__ == "__main__":
    unittest.main()
MethodChecks
assertEqual(a, b)a == b
assertTrue(x) / assertFalse(x)A true / false value
assertIn(a, b)a in b
assertIsNone(x)x is None
assertRaises(Error)The with block inside must raise that kind of error

Run the suite with python3 -m unittest -v (it discovers test_*.py files). A failing test prints the mismatching values clearly:

class T(unittest.TestCase):

        self.assertEqual(1 + 1, 3)

Mock: testing without a network

Tests should not call the real API: slow, needs a key and may change data. unittest.mock.Mock builds a fake object that remembers how it was called, so you can check that your code made the right calls:

from unittest.mock import Mock

def test_calls_api_for_each_row(self):
    client = Mock()                           # a fake object standing in for the real OdooClient
    client.call.return_value = [1]
    rows = [CourseRow("A", 8), CourseRow("B", 16)]

    self.assertEqual(import_rows(client, rows), 2)
    self.assertEqual(client.call.call_count, 2)
    client.call.assert_any_call("vinc.course", "create",
                                vals_list=[{"name": "A", "duration_hours": 8}])

That is why part 13 recommended wrapping HTTP in OdooClient: import_rows takes the client as a parameter, so a test simply passes a fake one.

Type hints: self-describing code

Type hints record the expected types of parameters and return values. Python does not check them at run time, but they help readers, editors and type-checking tools catch slips early:

def total(hours: list[int], factor: float = 1.0) -> float:
    return sum(hours) * factor

print(total([1, 2], 2))                  # 6.0 (factor is an int though declared float: Python does not complain)
print(total.__annotations__)
# {'hours': list[int], 'factor': <class 'float'>, 'return': <class 'float'>}

def find(code: str) -> dict | None:      # a dict or None
    return {"code": code} if code else None

print(find(""), find("X"), find(123))   # None {'code': 'X'} {'code': 123}   <- type hints do not block at run time
HintMeaning
x: int, name: strBasic types
list[int], dict[str, int]A list of ints, a dict with string keys and int values
str | NoneA string or None
-> floatThe return type
@dataclass with name: strDeclares the fields of a data class (part 8)

Odoo's documentation also states method signatures with types, for example search(domain, offset, limit, order) -> Self, so reading type hints helps you follow the ORM reference faster.

import_courses.py

#!/usr/bin/env python3
"""Import courses from a CSV file into Odoo through the JSON-2 API."""
import argparse
import csv
import logging
import os
import sys
from dataclasses import dataclass
from pathlib import Path

import requests

_logger = logging.getLogger("import_courses")


class OdooAPIError(Exception):
    """An error returned by Odoo or a connection error."""


class InvalidRow(Exception):
    """An invalid CSV row."""


@dataclass
class CourseRow:
    name: str
    hours: int

    @classmethod
    def from_dict(cls, row: dict) -> "CourseRow":
        name = (row.get("name") or "").strip()
        if not name:
            raise InvalidRow("missing course name")
        try:
            hours = int(row["hours"])
        except (KeyError, ValueError) as e:
            raise InvalidRow(f"invalid hours: {row.get('hours')!r}") from e
        if hours <= 0:
            raise InvalidRow(f"hours must be greater than 0: {hours}")
        return cls(name=name, hours=hours)


class OdooClient:
    def __init__(self, base_url: str, api_key: str, database: str | None = None, timeout: int = 10):
        self.base_url = base_url.rstrip("/")
        self.timeout = timeout
        self.session = requests.Session()
        self.session.headers["Authorization"] = f"bearer {api_key}"
        if database:
            self.session.headers["X-Odoo-Database"] = database

    def call(self, model: str, method: str, **payload):
        url = f"{self.base_url}/json/2/{model}/{method}"
        try:
            response = self.session.post(url, json=payload, timeout=self.timeout)
        except requests.RequestException as e:
            raise OdooAPIError(f"Could not call {url}: {e}") from e
        if not response.ok:
            try:
                message = response.json().get("message", response.text)
            except ValueError:
                message = response.text
            raise OdooAPIError(f"HTTP {response.status_code}: {message}")
        return response.json()


def read_rows(path: Path) -> tuple[list[CourseRow], list[str]]:
    ok, errors = [], []
    with open(path, encoding="utf-8", newline="") as f:
        for number, row in enumerate(csv.DictReader(f), start=2):   # row 1 is the header
            try:
                ok.append(CourseRow.from_dict(row))
            except InvalidRow as e:
                errors.append(f"row {number}: {e}")
    return ok, errors


def import_rows(client, rows: list[CourseRow], dry_run: bool = False) -> int:
    created = 0
    for row in rows:
        if dry_run:
            _logger.info("[dry-run] would create: %s (%s hours)", row.name, row.hours)
            continue
        ids = client.call("vinc.course", "create",
                          vals_list=[{"name": row.name, "duration_hours": row.hours}])
        _logger.debug("created id=%s", ids)
        created += 1
    return created


def main(argv=None) -> int:
    parser = argparse.ArgumentParser(description="Import courses from CSV into Odoo.")
    parser.add_argument("csv_file", type=Path)
    parser.add_argument("--dry-run", action="store_true", help="check only, do not call the create API")
    parser.add_argument("-v", "--verbose", action="store_true", help="show detailed logs")
    args = parser.parse_args(argv)

    logging.basicConfig(level=logging.DEBUG if args.verbose else logging.INFO,
                        format="%(levelname)s %(message)s")
    try:
        rows, errors = read_rows(args.csv_file)
    except FileNotFoundError:
        _logger.error("File not found: %s", args.csv_file)
        return 2
    for message in errors:
        _logger.warning("skipping %s", message)
    _logger.info("read %d valid rows, %d bad rows", len(rows), len(errors))

    client = OdooClient(os.environ["ODOO_URL"], os.environ["ODOO_API_KEY"], os.environ.get("ODOO_DB"))
    try:
        created = import_rows(client, rows, dry_run=args.dry_run)
    except OdooAPIError as e:
        _logger.error("Odoo reported an error: %s", e)
        return 1
    _logger.info("done: created %d courses", created)
    return 0 if not errors else 3


if __name__ == "__main__":
    sys.exit(main())

Common mistakes when starting out

  • Leaving a breakpoint() or debug print in the code. Search for and remove them before committing; use logging for what should stay.
  • Calling logging.basicConfig after logs have already been emitted. Only the first configuration takes effect; call it once, early, inside main.
  • Tests that depend on order or outside data. Each test must prepare its own data (setUp, temporary folders) and never hit a real network.
  • Assuming type hints block type errors. They do not stop find(123) from running; you need a type checker or tests to catch such errors.
  • Test names that do not start with test. unittest skips them (the same rule as in Odoo's part 13 of the Odoo series).

FAQ

When should I use breakpoint() instead of print to debug? ▾
breakpoint() opens the pdb debugger right at that line, letting you inspect variables (p), step line by line (n, s) and continue (c) without editing the code further. A few print calls are enough for simple flows, but for complex ones breakpoint() is faster and cleaner; remember to remove it before committing.
Why use logging instead of print? ▾
logging attaches a level (DEBUG through CRITICAL), a timestamp and a logger name, and you can turn it on or off by level without editing code. print suits a program's results, logging suits operational information; Odoo also uses logging.getLogger(__name__) and tunes it with the --log-level option.
Do type hints catch type errors at run time? ▾
No. Python does not check type hints at run time, so find(123) still runs even with find(code: str). They help readers, editors and static type checkers such as mypy; catching type errors needs that checker or tests.
Does Odoo use unittest or its own test framework? ▾
Odoo uses unittest: TransactionCase and Odoo's test classes extend unittest.TestCase, so assertEqual, setUp and assertRaises from this part carry straight over to testing models.
