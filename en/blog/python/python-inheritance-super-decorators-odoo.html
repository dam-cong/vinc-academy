Python Inheritance, super() and Decorators for Odoo Devs

Overriding create or writing @api.depends both rest on two Python techniques: inheritance with super() and decorators. This guide teaches them with runnable examples, then shows the golden rules when overriding methods in Odoo.

Updated: October 16, 2026 16 min read Vinc Academy Team

Quick summary

Inheritance lets a child class reuse and extend a parent: class OnlineCourse(Course). When overriding a method, call super() to run the parent's logic. A decorator is a function that wraps another to add behavior, written as @name on the line above def. Odoo uses both everywhere: super().create(vals_list) when overriding, @api.depends, @api.model, @api.constrains and @http.route.

Class inheritance and super()

A child class names its parent in parentheses. It receives every attribute and method of the parent and may override any method it wants to change. The super() function returns a "bridge" to the parent class so you can call the original method:

class Course:
    def __init__(self, name, hours):
        self.name, self.hours = name, hours

    def describe(self):
        return f"{self.name} - {self.hours}h"

class OnlineCourse(Course):                  # inherits from Course
    def __init__(self, name, hours, platform="Zoom"):
        super().__init__(name, hours)        # call the parent class's __init__
        self.platform = platform

    def describe(self):                      # override the parent method
        base = super().describe()            # reuse the parent's result
        return f"{base} (online: {self.platform})"

c = OnlineCourse("Odoo", 24)
print(c.describe())     # Odoo - 24h (online: Zoom)
print(isinstance(c, Course), issubclass(OnlineCourse, Course))   # True True
print([k.__name__ for k in OnlineCourse.__mro__])   # ['OnlineCourse', 'Course', 'object']
  • super().__init__(name, hours) runs the parent's initialization, so the child need not repeat assigning name and hours.
  • super().describe() fetches the parent method's result and you add to it instead of rewriting from scratch.
  • isinstance(c, Course) is True for an object of the child class: an OnlineCourse "is also" a Course.
  • __mro__ (method resolution order) shows the order in which Python searches for methods: the child first, then the parent, finally object.

Multiple inheritance and mixins

A class may inherit from several classes. The most useful pattern is the mixin: a small class offering a single capability (logging, timestamps…) that is "mixed into" other classes:

class LogMixin:
    def log(self, msg):
        print(f"[{type(self).__name__}] {msg}")

class Tracked(LogMixin, Course):
    def describe(self):
        self.log("describe was called")
        return super().describe()

print(Tracked("Git", 8).describe())
# [Tracked] describe was called
# Git - 8h
print([k.__name__ for k in Tracked.__mro__])
# ['Tracked', 'LogMixin', 'Course', 'object']

Python searches methods along __mro__ and super() follows the same order, so mixins and the main class cooperate. Odoo leans on this principle heavily: its documentation describes _inherit accepting a list of parent models when the new model has a _name, which is multiple inheritance at the model level.

Overriding methods and the golden rules of super()

Overriding create and write is a daily task for Odoo developers (part 9 of the Odoo series). The structure is always the same: prepare the input, call the parent, handle the result, return. A plain-Python imitation:

class Base:
    @classmethod
    def create(cls, vals):
        print("Base.create", vals)
        return vals

class MyModel(Base):
    @classmethod
    def create(cls, vals):
        vals = dict(vals)                 # work on a copy
        vals.setdefault("code", "AUTO")   # your logic first
        result = super().create(vals)     # call the parent: NEVER forget
        print("after creating")
        return result                     # return the same kind as the parent

print(MyModel.create({"name": "x"}))
# Base.create {'name': 'x', 'code': 'AUTO'}
# after creating
# {'name': 'x', 'code': 'AUTO'}

Odoo's documentation stresses two things: always call super() so you do not break the processing chain (only very rare cases justify skipping it), and return the same kind of data as the parent method: if the parent returns a dict, the override must too. Work on a copy of arguments (like dict(vals) from part 5) so you do not change the caller's data.

super() and MRO order in multiple inheritance

With "diamond-shaped" multiple inheritance, super() is not simply "call the direct parent" but "call the next class in __mro__". That is how each class in the chain runs exactly once and classes overriding the same method cooperate:

class A:
    def hello(self):
        return ["A"]

class B(A):
    def hello(self):
        return ["B"] + super().hello()

class C(A):
    def hello(self):
        return ["C"] + super().hello()

class D(B, C):
    def hello(self):
        return ["D"] + super().hello()

print(D().hello())                       # ['D', 'B', 'C', 'A']
print([k.__name__ for k in D.__mro__])   # ['D', 'B', 'C', 'A', 'object']

That is why the rule "always call super()" matters: if one class in the chain skips it, every class after it in __mro__ never runs. A similar model applies when several modules extend one Odoo model: each overrides the method and must call super() so the other modules' parts keep working.

Inheritance or composition?

Inheritance expresses an "is a" relationship (an OnlineCourse is a Course). When the relationship is merely "has a", use composition: keep the other object as an attribute. Overusing inheritance builds deep, hard-to-follow class trees; composition is more flexible:

class Instructor:
    def __init__(self, name):
        self.name = name

class Offering:                          # composition: "has a", not "is a"
    def __init__(self, course, instructor):
        self.course = course
        self.instructor = instructor

    def title(self):
        return f"{self.course.name} - {self.instructor.name}"

print(Offering(Course("Odoo", 24), Instructor("Hien")).title())   # Odoo - Hien

In Odoo the "has a" relationship is a Many2one (instructor_id) and "has many" a One2many: models use composition through relational fields, while _inherit is for when you truly want to extend or reuse that model itself.

Decorators: functions wrapping functions

A decorator is a function that takes another function and returns a new one with added behavior. The @timer syntax above a def line is shorthand for slow_sum = timer(slow_sum). It rests on the closures you met in part 5:

import functools

def timer(func):
    @functools.wraps(func)                # keep the original function's name and docstring
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        print(f"{func.__name__} done")
        return result
    return wrapper

@timer                                    # same as slow_sum = timer(slow_sum)
def slow_sum(n):
    """Sum 1..n"""
    return sum(range(n + 1))

print(slow_sum(10), slow_sum.__name__, slow_sum.__doc__)
# slow_sum done
# 55 slow_sum Sum 1..n

functools.wraps matters: it copies the original function's name and docstring onto the wrapper. Without it the function turns into wrapper and loses its docstring, which hurts debugging and any tool or framework that reads function names (logs, debuggers, route registries...):

def no_wraps(func):
    def wrapper(*a, **k):
        return func(*a, **k)
    return wrapper

@no_wraps
def f():
    "doc"

print(f.__name__, f.__doc__)     # wrapper None   <- name and docstring lost

Decorators with arguments

To pass arguments as in @retry(3) you need one more function layer: retry(3) returns the real decorator. This is precisely the structure of @api.depends('a', 'b') and @http.route('/x', auth='public'):

def retry(times):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last = None
            for i in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except ValueError as e:
                    last = e
                    print(f"try {i} failed: {e}")
            raise last
        return wrapper
    return deco

calls = {"n": 0}

@retry(3)                                 # a decorator with arguments: retry(3) returns deco
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ValueError("not yet")
    return "ok"

print(flaky())
# try 1 failed: not yet
# try 2 failed: not yet
# ok

The order of several decorators

def deco(tag):
    def d(f):
        def w():
            return f"<{tag}>" + f() + f"</{tag}>"
        return w
    return d

@deco("a")
@deco("b")
def x():
    return "x"

print(x())    # <a><b>x</b></a>   (the decorator closest to the function applies first)

Two useful decorators to write or reuse

Besides logging, the most common decorators remember results (a cache) for slow functions and check arguments before running the function. The standard library ships functools.cache (and lru_cache with a size limit):

import functools

@functools.cache                         # remembers results by argument
def course_price(code):
    print("looking up", code)              # printed only on the first call
    return {"ODO-F": 100}.get(code, 0)

print(course_price("ODO-F"), course_price("ODO-F"))
# looking up ODO-F
# 100 100

def require_positive(func):              # a decorator that checks an argument
    @functools.wraps(func)
    def wrapper(hours, *args, **kwargs):
        if hours <= 0:
            raise ValueError("hours must be > 0")
        return func(hours, *args, **kwargs)
    return wrapper

@require_positive
def sessions(hours):
    return hours // 8

print(sessions(24))                      # 3
sessions(0)
# ValueError: hours must be > 0

Take care when caching a function with side effects or one that depends on changing data: stale results keep being returned even after the source data changed. Caching suits "pure" functions such as a fixed lookup table.

@classmethod and @staticmethod

class Tool:
    @staticmethod
    def hours_to_days(h):                 # needs neither self nor cls
        return h / 8

    @classmethod
    def from_string(cls, s):              # receives the class, often used as a second "constructor"
        name, hours = s.split(":")
        return Course(name, int(hours))

print(Tool.hours_to_days(24))             # 3.0
print(Tool.from_string("Odoo:24").describe())   # Odoo - 24h

@staticmethod is an ordinary function that happens to live in the class (taking neither self nor cls). @classmethod receives the class itself as the first parameter, commonly used as an "alternative constructor" such as from_string. Together with @property from part 8 these are the built-in decorators you meet most.

Decorators you meet in Odoo code

# 1. a decorator with arguments: declares a computed field's dependencies
@api.depends('price', 'duration_hours')
def _compute_price_per_hour(self):
    ...

# 2. a decorator without arguments: create receives a list of vals
@api.model
def create(self, vals_list):
    courses = super().create(vals_list)
    return courses

# 3. a data constraint
@api.constrains('duration_hours')
def _check_duration(self):
    ...

# 4. a controller route; an override must re-apply @route()
@http.route('/vinc_course/courses', auth='public')
def courses(self, **kw):
    ...
DecoratorEffect (per Odoo's documentation)
@api.depends(...)Declares the fields a compute method depends on; the ORM recomputes when they change
@api.constrains(...)A constraint-checking method, run when the named fields are edited
@api.onchange(...)Updates the form when a field changes, in the interface only
@api.modelA method where the content of self does not matter, only the model
@api.ondelete(at_uninstall=False)Runs during deletion, letting you block deletes without affecting module uninstall
@http.route(...)Binds a method to a URL; overriding a controller must re-apply @route()

You rarely write these decorators yourself; you just need to understand they are functions wrapping functions and place them right above the def line. That explains why Odoo's documentation notes that overriding a controller method and forgetting @route() makes the route vanish: the decorator is what registers the method with the system.

Common mistakes when starting out

  • Forgetting super().__init__(...) in a child class. The parent's attributes are never created, and later you hit AttributeError.
  • Overriding a method but forgetting return. The function returns None instead of the parent's result, breaking every caller.
  • Writing a decorator without functools.wraps. The function loses its name and docstring (f.__name__ becomes wrapper).
  • Forgetting to call retry(3) for a decorator with arguments. Writing @retry instead of @retry(3) passes the function into the argument slot.

Summary

  • A child class inherits, overrides and uses super() to reuse its parent; a mixin supplies one extra capability.
  • When overriding Odoo methods: always call super(), work on a copy of arguments and return the same kind of value.
  • A decorator is a function wrapping a function; use functools.wraps; decorators with arguments need one more layer.
  • Recognize @api.depends, @api.constrains, @api.model and @http.route as decorators.

FAQ

What is super() for? ▾
super() returns a bridge to the parent class so you can call the original method, for example super().create(vals_list). That lets you add logic before or after while keeping the parent's behavior.
Why must I call super() when overriding a method in Odoo? ▾
Odoo's documentation stresses always calling super() so you do not break the processing chain, and returning the same kind of data as the parent method; if the parent returns a dict, so must the override.
What is a decorator? ▾
A decorator is a function that takes a function and returns a new one with added behavior. The @name syntax above a def line is shorthand for func = name(func).
Why do I need functools.wraps when writing a decorator? ▾
It copies the original function's name and docstring onto the wrapper. Without it the function is renamed wrapper and loses its docstring, which makes debugging harder.
