Classes and OOP in Python: From Objects to Odoo Models

Every Odoo model is a Python class. This guide teaches basic OOP through a plain-Python Course class, then compares it with the Odoo VincCourse class so you understand that fields are attributes, self is a recordset and why the naming conventions match.

Updated: October 16, 2026 15 min read – views Vinc Academy Team

Quick summary

A class is a mold and an object is a product made from it: c = Course("Odoo", 24). Inside a class, __init__ initializes data, self is the object currently in use, attributes store data and methods are functions bound to the object. An Odoo model is a class extending models.Model: fields are class attributes, _name names the model, and self in a method is a recordset, a set of objects rather than just one.

Classes and objects: the basics

Let us build a plain-Python Course class that imitates a course in the vinc_course project:

class Course:
    prefix = "ODO"                       # class attribute (shared)

    def __init__(self, name, hours, price=0.0):
        self.name = name                 # attribute of each object
        self.hours = hours
        self.price = price
        self.published = False

    @property
    def price_per_hour(self):            # read like an attribute, computed on demand
        return self.price / self.hours if self.hours else 0.0

    def publish(self):
        if self.hours <= 0:
            raise ValueError("Hours must be greater than 0")
        self.published = True

    def __repr__(self):
        return f"Course({self.name!r}, {self.hours}h)"
  • __init__ runs whenever an object is created. Its first parameter is always self, referring to that very object; Python passes it for you when you call Course(...).
  • self.name = name creates an attribute of the object; each object has its own set of attributes.
  • A method (such as publish) is a function declared in the class, whose first parameter is also self.
  • __repr__ decides the string shown when you print an object or see it in a list; without it you only see an unreadable line like <Course object at 0x...>.
c = Course("Odoo basics", 24, 4500000)
print(c)                      # Course('Odoo basics', 24h)
print(c.name, c.hours, c.published)   # Odoo basics 24 False
c.publish()
print(c.published, round(c.price_per_hour))   # True 187500

other = Course("Python", 16)
print([c, other])             # [Course('Odoo basics', 24h), Course('Python', 16h)]
print(isinstance(c, Course), type(c).__name__)   # True Course

Notice that c.publish() needs no self argument: Python slips c in. The isinstance(c, Course) function tests whether an object belongs to a class, and vars(c) gives you a dict of its attributes.

Class attributes and object attributes

An attribute declared directly in the class body (like prefix) belongs to the class and is shared by all objects; one assigned through self. belongs to each object. Reassigning through an object merely creates an own attribute on that object:

print(Course.prefix, c.prefix)     # ODO ODO
c.prefix = "X"                     # creates an own attribute on c, class unchanged
print(c.prefix, Course.prefix)     # X ODO

class Bad:
    tags = []                      # a class-level list: shared by EVERY object
    def add(self, t):
        self.tags.append(t)

a, b = Bad(), Bad()
a.add("x")
print(b.tags)                      # ['x']   <- b sees it too!

class Good:
    def __init__(self):
        self.tags = []             # each object has its own list
    def add(self, t):
        self.tags.append(t)

a, b = Good(), Good()
a.add("x")
print(a.tags, b.tags)              # ['x'] []

This trap mirrors the changeable default value from part 5: a class-level list is shared. The rule: an object's own data is always initialized in __init__.

Special (dunder) methods and comparing objects

Methods named like __name__ are called silently by Python when you use familiar syntax. You have met __init__ and __repr__; here are a few more that come up often:

MethodCalled whenExample
__init__An object is createdCourse("Odoo", 24)
__repr__Showing an object in a list, debugging[course]
__str__print, f-stringsf"{course}"
__eq__The == operatora == b
__len__The len() functionlen(course)
 
class Course:
    def __init__(self, name, hours):
        self.name, self.hours = name, hours
    def __repr__(self):                 # for developers (debugging, lists)
        return f"Course({self.name!r}, {self.hours})"
    def __str__(self):                  # for users (print, f-strings)
        return f"{self.name} ({self.hours}h)"
    def __eq__(self, other):            # defines the == operator
        return isinstance(other, Course) and (self.name, self.hours) == (other.name, other.hours)
    def __len__(self):                  # len(course)
        return self.hours

a, b = Course("Odoo", 24), Course("Odoo", 24)
print(a == b, a is b)                   # True False
print(repr(a), str(a), len(a))          # Course('Odoo', 24) Odoo (24h) 24
print(f"{a}", [a])                      # Odoo (24h) [Course('Odoo', 24)]

Two points to remember. First, == compares identity by default (are they the same object?); to treat two objects holding the same data as equal you must write __eq__ yourself. The is operator always tests for the same object. Second, __repr__ targets developers (ideally rich enough to recreate the object) while __str__ targets end users; if you write only one, make it __repr__.

@dataclass: a class that merely holds data

For a class that mostly bundles data (like a CSV row or an API response), writing __init__, __repr__ and __eq__ by hand is repetitive. The standard library's @dataclass decorator generates them from a list of annotated attributes. For a list or dict default use field(default_factory=list) to dodge the sharing trap mentioned in part 5:

from dataclasses import dataclass, field

@dataclass
class CourseDC:
    name: str
    hours: int
    price: float = 0.0
    tags: list = field(default_factory=list)   # a safe list default

d = CourseDC("Odoo", 24)
print(d)                                  # CourseDC(name='Odoo', hours=24, price=0.0, tags=[])
print(d == CourseDC("Odoo", 24))          # True
print(CourseDC("X", 1).tags)              # []  (each object has its own list)

You will use @dataclass in parts 13 and 14 to describe data read from files or APIs before sending it to Odoo.

Naming conventions: _ and __

Python has no truly "private" attributes. By convention a single leading underscore (_internal) signals "internal use". A double leading underscore (__secret) makes Python rename the attribute to _ClassName__secret to avoid clashes with subclasses, not to hide it completely:

class Acc:
    def __init__(self):
        self._internal = 1        # convention: internal, do not touch from outside
        self.__secret = 2         # the name is mangled to _Acc__secret

x = Acc()
print(x._internal, hasattr(x, "__secret"), x._Acc__secret)   # 1 False 2

In Odoo a single underscore carries even more weight: a method starting with _ cannot be called from buttons or external APIs.

@property: computed, yet used like an attribute

@property turns a method into a read-only attribute: c.price_per_hour needs no parentheses and is always computed from current data. Assigning to a property without a setter raises AttributeError: property 'price_per_hour' of 'Course' object has no setter. To validate values on assignment, add a setter:

class Timer:
    def __init__(self):
        self._h = 0
    @property
    def h(self):
        return self._h
    @h.setter
    def h(self, v):
        if v < 0:
            raise ValueError("h must be >= 0")
        self._h = v

t = Timer()
t.h = 5
print(t.h)                         # 5
t.h = -1
# ValueError: h phải >= 0

Naming convention: a single leading underscore (_h) says "internal detail, do not touch from outside". Odoo uses the same convention for private methods such as _compute_total.

Objects holding objects

class Session:
    def __init__(self, name, hours):
        self.name, self.hours = name, hours

class Course2:
    def __init__(self, name):
        self.name = name
        self.sessions = []         # a course "has many" sessions

    def add_session(self, s):
        self.sessions.append(s)
        return self

    @property
    def total_hours(self):
        return sum(s.hours for s in self.sessions)

cc = Course2("Odoo").add_session(Session("1", 3)).add_session(Session("2", 4))
print(cc.total_hours, len(cc.sessions))     # 7 2

A course "has many" sessions: that is the One2many relation of the Odoo series, imitated here with a list attribute. The expression sum(s.hours for s in self.sessions) is exactly how a compute method totals hours.

How a Python class becomes an Odoo model

from odoo import fields, models

class VincCourse(models.Model):
    _name = 'vinc.course'
    _description = "Course"

    name = fields.Char(required=True)             # class attribute
    duration_hours = fields.Integer()
    session_ids = fields.One2many('vinc.course.session', 'course_id')

    def action_publish(self):
        for course in self:                       # self is a recordset, loop over each record
            course.is_published = True

Two differences to remember. First, you normally do not write an __init__ for a model like the one above: the ORM machinery of models.Model creates the objects (per the documentation the class is instantiated once per database where the module is installed) and you just declare fields. Second, inside a model method self is a recordset, so you loop for course in self to handle each record (part 3); on each pass course is a one-element recordset. The ORM documentation also warns you not to give a field and a method the same name in one model, because the later declaration silently overwrites the earlier one.

Practice: Session and Course classes

  1. Re-run the Course2 and Session example above.
  2. Add an end_hour property or a remove_session(name) method to Course2.
  3. Add a check: add_session raises ValueError if hours <= 0.

The aim is to get used to putting logic into a class's methods rather than scattering it across functions: exactly the habit you need when writing Odoo model methods.

Common mistakes when starting out

Course()
# TypeError: Course.__init__() missing 2 required positional arguments: 'name' and 'hours'

c.price_per_hour = 5
# AttributeError: property 'price_per_hour' of 'Course' object has no setter

x = Course("A", 1)
y = x                              # y is the same object, not a copy
y.name = "B"
print(x.name)                      # B
  • Missing arguments when creating an object. A TypeError lists the required parameters still missing.
  • A list/dict at class level. Shared between all objects; initialize it in __init__.
  • Thinking assignment copies an object. y = x only adds a name for the same object; changing y changes x.
  • Forgetting self. Inside a method, reach attributes through self.name; writing just name refers to a different variable or fails.

Summary

  • A class is a mold, an object an instance; __init__ initializes, self is the current object.
  • Own data is initialized in __init__; class-level lists/dicts are shared.
  • @property gives computed values used like attributes; add a setter to validate assignment.
  • An Odoo model is a class whose fields are attributes; self is a recordset so always loop with for record in self.

FAQ

What is self in Python? ▾
self is a reference to the very object calling the method. It is always the first parameter of a method in a class and Python passes it for you, so c.publish() equals Course.publish(c).
What is the difference between class and object attributes? ▾
An attribute declared in the class body is shared by all objects, while one assigned through self in __init__ belongs to each object. A class-level list or dict is shared, so initialize it in __init__.
What is @property for? ▾
It turns a method into a read-only attribute computed on demand, such as c.price_per_hour. To validate values on assignment, add a setter with @name.setter.
How does self in an Odoo model method differ from ordinary self? ▾
In Odoo, self is a recordset that may hold 0, 1 or many records, so you loop for record in self to handle each record instead of treating it as a single object.
