Python Error Handling: try/except, raise, with and ValidationError

Data can always be wrong and files can always be missing. This guide teaches try/except/finally, raise, custom exceptions and the with statement, then compares them with the ValidationError and UserError Odoo uses to report problems to users.

Updated: October 16, 2026 15 min read Vinc Academy Team

Quick summary

Errors in Python are exceptions. try wraps code that may fail, except handles that exact kind of error, finally always runs for cleanup, and raise reports an error on purpose when data is invalid. The with statement guarantees resources such as files are closed. In Odoo you report problems to users with raise ValidationError(...) or raise UserError(...), and in tests you catch them with with self.assertRaises(...).

try, except, else, finally

When a statement fails, Python stops and "throws" an exception up the calling layers until an except catches it; if nobody does, the program halts and prints a traceback. The four blocks of a try statement:

def to_hours(text):
    try:
        hours = int(text)             # code that may fail
    except ValueError:
        print("Not a number:", text) # runs only on a ValueError
        return None
    else:
        print("converted")          # runs when there was NO error
        return hours
    finally:
        print("always runs")            # always runs, error or not

print(to_hours("24"))
# converted
# always runs
# 24
print(to_hours("abc"))
# Not a number: abc
# always runs
# None
BlockRuns whenUsed for
tryAlwaysHolding code that may fail, kept as short as possible
except KindAn error of exactly that kind occurredHandling or recording the error
elseNo error occurredThe follow-up work when all went well
finallyAlways, even on error or returnCleanup: closing files, releasing resources

Catching the right kind

try:
    {"a": 1}["b"]
except (KeyError, IndexError) as e:   # catch several kinds, get the error object via "as e"
    print(type(e).__name__, e)        # KeyError 'b'

try:
    open("missing.csv")
except FileNotFoundError as e:
    print("FileNotFoundError:", e)
# FileNotFoundError: [Errno 2] No such file or directory: 'missing.csv'

def safe_div(a, b):
    try:
        return a / b
    except ZeroDivisionError as e:
        print("ZeroDivisionError:", e)   # division by zero
        return 0.0

Catch the most specific kind of error you know how to handle. A tuple in except catches several kinds at once; as e gives you the error object for printing its message or reading attributes. The errors you meet most when handling data:

Reading a traceback: the most important skill

When an exception is not caught, Python prints a traceback: the chain of function calls leading to the error. Learn to read it from the bottom up: the last line names the error kind and message, and the lines above are the "path" you took. Take a script reading a course list where the second row spells its hours in words:

def parse_hours(text):
    return int(text)

def load_course(row):
    return {"name": row["name"], "hours": parse_hours(row["hours"])}

rows = [{"name": "Odoo", "hours": "24"}, {"name": "Git", "hours": "eight"}]
for row in rows:
    print(load_course(row))

Running it prints:

{'name': 'Odoo', 'hours': 24}
Traceback (most recent call last):
  File "tb.py", line 9, in <module>
    print(load_course(row))
  File "tb.py", line 5, in load_course
    return {"name": row["name"], "hours": parse_hours(row["hours"])}
  File "tb.py", line 2, in parse_hours
    return int(text)
ValueError: invalid literal for int() with base 10: 'eight'
  • The last line (ValueError: invalid literal for int() ... 'eight') is explicit: the error is a ValueError and the offending value is 'eight'.
  • The frame nearest the end (parse_hours, line 2) is where the error occurred, the int(text) line.
  • The frames above tell you who called it: load_course and then the module-level for loop. You follow them back to find which data row ("Git") caused the trouble.

A good habit: read the last line first, then the last frame of your own code (skip library frames if any). In Odoo, tracebacks appear in the server log and frames through odoo/... are just scaffolding; look for the first frame that belongs to your module.

EAFP and LBYL: two error-handling styles

There are two approaches: LBYL ("look before you leap": check the condition first, then act) and EAFP ("easier to ask forgiveness than permission": just act and catch the error if it comes). Python leans towards EAFP because it avoids data changing between the check and the use, but neither is absolutely right. When a missing key is normal, d.get() or in is usually clearer; when the failure is truly exceptional, use try/except:

d = {"a": 1}

# LBYL: look before you leap (check the condition first)
value = d["b"] if "b" in d else "none"

# EAFP: easier to ask forgiveness than permission (just do it, catch the error)
try:
    value = d["b"]
except KeyError:
    value = "none"

# usually the tidiest with a dict
value = d.get("b", "none")

assert value == "none", "miscalculated"     # assert: checks a developer's assumption
# AssertionError: miscalculated  (if the condition is false)

The assert keyword is for developer assumptions ("this must be true here"), not for validating user-entered data, because it can be switched off when Python runs with optimization options. External data always needs a real raise.

raise: reporting errors on purpose

def check(hours):
    if hours <= 0:
        raise ValueError(f"Invalid number of hours: {hours}")
    return hours

try:
    check(0)
except ValueError as e:
    print("Caught:", e)               # Caught: Invalid number of hours: 0

try:
    try:
        1 / 0
    except ZeroDivisionError:
        print("log it, then re-raise")
        raise                           # a bare raise: re-raises the error being handled
except ZeroDivisionError:
    print("the caller still receives the error")

Use raise when input data breaks a business rule, instead of letting the program continue with bad data. A bare raise inside except re-raises the very error being handled, useful when you want to log it and let an upper layer decide.

Custom exceptions

class CourseError(Exception):
    """A course business error."""

class InvalidHours(CourseError):
    def __init__(self, hours):
        super().__init__(f"Invalid number of hours: {hours}")
        self.hours = hours

def convert(text):
    try:
        return int(text)
    except ValueError as e:
        raise InvalidHours(text) from e     # keep the original cause

try:
    convert("x")
except CourseError as e:                    # catches the parent class and its children
    print(e)                                # Invalid number of hours: x
    print(repr(e.__cause__))
    # ValueError("invalid literal for int() with base 10: 'x'")

Create a class extending Exception to give your project's business errors a name. Catching the parent class (CourseError) catches all its children. The raise ... from e syntax keeps the original cause in __cause__, very helpful when debugging. The whole exception tree derives from BaseException; most errors you meet extend Exception, whereas KeyboardInterrupt (Ctrl+C) does not, so except Exception does not swallow it.

with: automatic cleanup

The with statement works with a context manager: an object that knows how to "open" and "close". The classic case is a file, closed automatically when leaving the with block, error or not, so you need not remember close():

import tempfile, os
path = os.path.join(tempfile.mkdtemp(), "a.txt")

with open(path, "w", encoding="utf-8") as f:    # the file closes automatically when leaving the with block
    f.write("ODO-F\n")
print(f.closed)                                  # True

with open(path, encoding="utf-8") as f:
    print(f.read().strip())                      # ODO-F

You can write your own context manager using the contextlib.contextmanager decorator: the part before yield runs on entering the block, and the finally part after it runs on leaving, even if the block's body fails:

from contextlib import contextmanager

@contextmanager
def section(name):
    print("start", name)
    try:
        yield                                    # the body of the with block runs here
    finally:
        print("end", name)                  # always runs, kể cả khi thân bị lỗi

with section("import"):
    print("working")
# start import
# working
# end import

try:
    with section("error"):
        raise ValueError("broken")
except ValueError:
    print("caught")
# start error
# end error      <- finally still runs
# caught

Reporting errors in Odoo: ValidationError and UserError

from odoo.exceptions import UserError, ValidationError

@api.constrains('duration_hours')
def _check_duration(self):
    for course in self:
        if course.duration_hours <= 0:
            raise ValidationError("Teaching hours must be greater than 0.")   # shown to the user as an error message

@api.ondelete(at_uninstall=False)
def _unlink_except_published(self):
    if any(course.is_published for course in self):
        raise UserError("A published course cannot be deleted.")

# in a test
with self.assertRaises(ValidationError):
    self.course.duration_hours = 0
Odoo exceptionUse whenSeen in
ValidationErrorData violates a constraintAn @api.constrains method must raise it when the condition fails
UserErrorBlocking an operation for a business reasonFor example inside @api.ondelete when deletion is not allowed
AccessErrorThe user lacks rightsRaised by create, write, search on rights violations (part 5 of the Odoo series)
ValueErrorA field name does not existRaised by create when passed values name a wrong field

The message you pass to ValidationError/UserError is what the user sees, so write it clearly and say what they should do. In tests, with self.assertRaises(ValidationError): checks that your constraint really blocks bad data (part 13 of the Odoo series).

Practice: converting CSV rows safely

def parse_row(row):
    """Turn a dict of strings into typed values; raise InvalidHours on failure."""
    try:
        hours = int(row["hours"])
    except (KeyError, ValueError) as e:
        raise InvalidHours(row.get("hours")) from e
    if hours <= 0:
        raise InvalidHours(hours)
    return {"code": row["code"].strip().upper(), "hours": hours}

rows = [{"code": " odo-f ", "hours": "24"}, {"code": "x", "hours": "abc"}, {"code": "y", "hours": "-1"}]
ok, errors = [], []
for row in rows:
    try:
        ok.append(parse_row(row))
    except CourseError as e:
        errors.append(str(e))
print(ok)       # [{'code': 'ODO-F', 'hours': 24}]
print(errors)   # ['Invalid number of hours: abc', 'Invalid number of hours: -1']

This is a very realistic pattern for processing imported file data (parts 11 and 14): collect good rows in one list and bad rows in another, without the program stopping midway.

Common mistakes when starting out

try:
    risky()
except:                      # CATCHES EVERYTHING, even KeyboardInterrupt
    pass                     # and swallows the error: no trace is left

# better: catch the right kind and record it
try:
    risky()
except ValueError as e:
    logging.warning("skipping bad row: %s", e)
  • A bare except: or except Exception: pass. It swallows every error, including programming mistakes, so the program goes wrong silently. Catch the specific kind and log it (logging.exception(...) records the traceback too).
  • Wrapping a whole long function in one try. You cannot tell which line failed. Wrap only the lines that can really fail.
  • Using errors in place of ordinary conditions. Testing if key in d: or using d.get() is usually clearer than catching KeyError when a missing key is normal.
  • Picking the wrong exception in Odoo. Data constraints use ValidationError; blocking operations uses UserError. The message is for the end user, not the developer.

Summary

  • try/except/else/finally handles errors; catch specific kinds and avoid a bare except:.
  • raise reports invalid data; raise X from e keeps the original cause; custom exceptions name business errors.
  • with guarantees cleanup of resources (files, connections), error or not.
  • Odoo: ValidationError for constraints, UserError for blocking operations, with messages written for users.

FAQ

Should I catch errors broadly with except Exception? ▾
Only catch the specific kind you know how to handle. A bare except or except Exception with pass swallows every error, including programming mistakes, so the program fails silently. If you must catch broadly, log the traceback.
What is finally for? ▾
The finally block always runs, whether or not there was an error and even with a return, so use it for cleanup such as closing files or releasing resources. The with statement does this automatically for files.
How do ValidationError and UserError differ in Odoo? ▾
ValidationError is for data constraints; an @api.constrains method must raise it when the condition fails. UserError blocks an operation for a business reason, for example forbidding deletion inside @api.ondelete. Both show their message to the user.
What is raise ... from e for? ▾
It raises a new error while keeping the original one in the __cause__ attribute, helping you trace the root cause when debugging.
