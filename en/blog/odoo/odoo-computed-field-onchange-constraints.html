Computed Fields, Onchange and Constraints in Odoo 20

The first business logic in a module is usually automatic calculation and blocking bad data. This guide explains computed fields, onchange and constraints, when to use each, and why business rules do not belong in an onchange.

Updated: October 16, 2026 15 min read – views Vinc Academy Team

Quick summary

A computed field derives its value from other fields through the method named in compute=, with dependencies declared by @api.depends. An onchange only assists data entry on a form, while constraints guarantee that data stays valid. Prefer computed fields over onchanges, and reach for SQL constraints (models.Constraint) first, Python constraints (@api.constrains) when the check is more complex.

Computed fields: values derived from other fields

Until now each field was written directly to its table and fetched directly from it. A computed field works differently: nothing is read from the database; the value is produced on demand by a function defined on the model. To make one, set the compute attribute to a method name; that method must set a value on each record contained in self. By convention the method is private, with a name starting with _.

For example: the number of sessions and the average price per hour of a course (added to models/course.py):

session_count = fields.Integer(compute='_compute_session_count')
price_per_hour = fields.Float(compute='_compute_price_per_hour')

@api.depends('session_ids')
def _compute_session_count(self):
    for course in self:
        course.session_count = len(course.session_ids)

@api.depends('price', 'duration_hours')
def _compute_price_per_hour(self):
    for course in self:
        course.price_per_hour = (
            course.price / course.duration_hours if course.duration_hours else 0.0)

Place these lines in the VincCourse class, and import api next to fields and models in the file header.

  • @api.depends(...) lists the fields the result relies on. The ORM uses that list to recompute the field whenever one of them changes.
  • self is a recordset, so always loop with for record in self.
  • A path through a relational field works as a dependency too, e.g. @api.depends('session_ids.session_date'), for Many2one, One2many and Many2many alike.
  • For multi-record sets, mapped() collects values neatly, e.g. max(course.session_ids.mapped('session_date')).

The inverse method: making a computed field editable

A computed field is read-only by default, since users are not expected to set it. If you want to type into it as well, add an inverse parameter. The compute method fills the computed field; the inverse method does the opposite and writes back to the fields it depends on. Mind the timing: the inverse runs when the record is saved, whereas compute runs each time a dependency changes.

duration_days = fields.Float(compute='_compute_duration_days',
                             inverse='_inverse_duration_days')

@api.depends('duration_hours')
def _compute_duration_days(self):
    for course in self:
        course.duration_days = course.duration_hours / 8.0

def _inverse_duration_days(self):
    for course in self:
        course.duration_hours = int(course.duration_days * 8)

Should a computed field be stored?

By default a computed field is not stored, so you cannot search on it unless you also provide a search method. Setting store=True persists it in the table, which enables searching and grouping. The price is computing load: whenever a dependency changes, every affected record is recalculated, which can become heavy with millions of rows. Computed fields can also be chained, one relying on another; the ORM keeps the order right but sometimes at a performance cost. Estimate that cost before deciding.

Related fields: values taken from a field on another model

A related field is a special computed field: it reaches a nested field by following a path of relational fields and taking a field from the final model, using the related parameter:

instructor_name = fields.Char(related='instructor_id.partner_id.name')
instructor_email = fields.Char(related='instructor_id.email', store=True,
                               depends=['instructor_id'])
  • By default a related field is not stored, not copied on duplicate, read-only and evaluated in superuser mode. Add store=True to persist it like a computed field; it then recomputes itself when its dependencies change.
  • Many attributes are inherited from the source field unless you redeclare them: string, help, groups, digits, size, translate, selection, comodel_name, domain, context; required carries over only if every field in the chain is required.
  • To control exactly when it recomputes, use depends=['instructor_id']: the field refreshes only when instructor_id changes, not when the name on the other side changes.
  • Many2many and One2many fields cannot be strung together in a related field's path. Another model's One2many or Many2many is reachable only via a Many2one defined on the current model.

Onchange: helping with data entry on forms

The onchange mechanism lets the interface refresh a form as soon as the user fills in a field, while nothing is persisted yet. You write a method decorated with @api.onchange('field_name'); inside it, self stands for the record on the form, and whatever you assign to self shows up on screen. No loop is needed, because onchange only runs in a form, so self is always one record.

@api.onchange('is_published')
def _onchange_is_published(self):
    if self.is_published and not self.start_date:
        self.start_date = fields.Date.today()

The user stays free to edit the value afterwards. An onchange can also return a warning that does not stop the user, shaped like {'warning': {'title': ..., 'message': ...}}. Two limits to remember: @onchange accepts plain field names only, not dotted paths such as partner_id.tz; and you should not call create, write or unlink on the temporary record an onchange receives, since the outcome is undefined. Just assign field values.

Onchange limits to know about

  • An onchange method runs on a temporary record holding the values currently in the form; anything you assign to its fields is pushed to the browser for you.
  • An onchange cannot rewrite the very One2many or Many2many field it is attached to; this restriction comes from the web client.
  • To set several values at once you can call self.update({...}) instead of assigning field by field.
  • A warning can be returned as a small notification with 'type': 'notification'; otherwise it appears in a dialog.

Computed field or onchange?

Computed fieldOnchange
When it runsAlways, including when records are created from codeOnly inside the form view
Business logicSuitableNot suitable: creating a record from code never triggers it
DebuggingEasy: one method sets the fieldHard: several onchanges may set the same field

Odoo's guidance: when both would work, pick the computed field. And resist making forms "too clever": too much automation leaves users confused.

Constraints: keeping data valid

How do you stop users from entering bad data, such as a negative price? Odoo offers two ways to check invariants automatically: SQL constraints and Python constraints.

SQL constraints

Declare them with a models.Constraint attribute holding an SQL expression and an error message. This is the efficient way to keep data consistent:

_check_price = models.Constraint(
    'CHECK(price >= 0)',
    "The course price cannot be negative.",
)
_name_uniq = models.Constraint(
    'UNIQUE(name)',
    "This course name already exists.",
)

Python constraints

For more elaborate checks, use a method decorated with @api.constrains, naming the fields involved. It runs automatically when any of them is edited, and must raise ValidationError if the condition fails:

from odoo.exceptions import ValidationError

@api.constrains('duration_hours')
def _check_duration(self):
    for course in self:
        if course.duration_hours <= 0:
            raise ValidationError("Teaching hours must be greater than 0.")

When comparing floats, always use float_compare() and float_is_zero() from odoo.tools.float_utils instead of comparing directly. If performance matters, choose SQL constraints over Python ones.

Common mistakes when learning

  • Putting a business rule in an onchange. You try it on the form and it works, yet records created from code, imports or the API skip the rule entirely. An onchange fires only in the form view; business rules belong in computed fields or constraints.
  • Adding an SQL constraint and the module upgrade fails. If existing data already breaks the rule (say a course priced 0 when you add CHECK(price > 0)), the constraint cannot be applied and the log reports it could not add the constraint. Fix or delete the offending rows, then upgrade again.

Summary

  • Computed field: compute + @api.depends; set a value on every record in self.
  • inverse makes a computed field editable; store=True enables searching at the price of computation.
  • A related field is a computed field walking a relation chain; unstored and read-only by default.
  • An onchange merely assists data entry on forms; business rules belong in computed fields and constraints.
  • Prefer SQL constraints; use Python for more complex checks.

FAQ

How does a computed field differ from a normal field? ▾
A normal field is saved in and loaded from its table directly. A computed field gets its value from a method when needed, and by default is not stored, so you cannot search on it unless you set store=True or define search.
When should I set store=True on a computed field? ▾
When you need to search or group by it. But whenever a dependency changes the value is recalculated for every affected record, which can be heavy with large data, so weigh the cost.
Why should business logic not live in an onchange? ▾
An onchange fires only in the form view. Records created from code, imports or the API never trigger it, so business rules belong in computed fields or constraints.
Should I use SQL or Python constraints? ▾
SQL constraints are more efficient and preferred whenever the rule can be expressed in SQL. Use Python constraints with @api.constrains when the check is more complex.
