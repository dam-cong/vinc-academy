Inheritance in Odoo 20: _inherit, xpath, Method Overrides

Odoo is designed to be extended without touching original source. This guide covers three levels of inheritance: overriding CRUD methods, extending models with _inherit and adjusting existing views with xpath, plus common mistakes.

Updated: October 16, 2026 15 min read – views Vinc Academy Team

Quick summary

Odoo lets you extend another module's models and views without touching its source. For models, use _inherit to add fields, add methods or override methods; for views, create a child view pointing at the original through inherit_id and use xpath to add, replace or remove elements. When overriding a method, always call super().

Why is inheritance central to Odoo?

Odoo's strength is modularity: each module serves one business need, yet modules can interact and extend each other. The right approach is to layer changes on top rather than edit the original module's files, because direct edits are lost at the next version upgrade. This part walks through three levels of inheritance, from plain to Odoo-specific: Python inheritance (overriding methods), model inheritance and view inheritance.

Python inheritance: overriding CRUD methods

Your model derives from models.Model through ordinary Python class inheritance, so the four basic operations (read(), write(), create(), unlink()) are already inherited. Those methods (and every other method of Model) can be overridden to add business logic. The usual skeleton for overriding create():

@api.model
def create(self, vals_list):
    # run your logic, adjust vals_list if needed ...
    courses = super().create(vals_list)
    # ... then hand back what the parent method produced
    return courses
  • @api.model is needed on create() because the content of self means nothing while creating; the other CRUD methods do not need it.
  • Always call super() so you do not break the processing chain. Only a handful of very particular cases justify skipping it.
  • Return the same kind of value as the parent does: a parent giving back a dict means your override has to give back a dict as well.

Blocking deletion with @api.ondelete

For unlink(), you will rarely want to override it directly. Write a dedicated method decorated with @api.ondelete(at_uninstall=False) instead: it is called during deletion and avoids trouble when the module is uninstalled (an overridden unlink that raises errors can leave orphaned tables or records behind). Example: forbid deleting a published course:

from odoo.exceptions import UserError

@api.ondelete(at_uninstall=False)
def _unlink_except_published(self):
    if any(course.is_published for course in self):
        raise UserError("A published course cannot be deleted.")

Remember that self may hold several records, hence the any(...) check or a loop.

Model inheritance: adding to an existing model

Odoo has two model inheritance mechanisms. The first, by far the most common, lets a module alter a model defined elsewhere by: adding fields, redefining fields, adding constraints, adding methods or overriding existing ones. The second is delegation: each record is linked to a record of a parent model and transparently exposes that parent's fields.

DeclarationMeaning
_inherit = 'res.users' (no _name)Extends the existing model in place
_name = 'x' plus _inherit = 'y'Creates a new model x that inherits its structure from y
_inherits = {'a.model': 'a_id'}Delegation: the new model shows every field of the parent while the values stay on the linked record

Example: show the published courses a user is in charge of directly in the user form. We add a field to res.users. Following convention, keep each extended model in a separate file:

custom-addons/vinc_course/models/res_users.py

from odoo import fields, models


class ResUsers(models.Model):
    _inherit = 'res.users'

    course_ids = fields.One2many(
        'vinc.course', 'instructor_id', string="Courses in charge",
        domain=[('is_published', '=', True)])

Remember to import the file in models/__init__.py. The domain on the field limits the list to published courses.

View inheritance with inherit_id and xpath

Rather than editing the original view in place, Odoo stacks "extension" views on top of it. A child view names its parent through inherit_id; instead of a full layout, its arch holds xpath elements that pick spots in the parent and alter them. Example: add a tab to the user form (base.view_users_form):

custom-addons/vinc_course/views/res_users_views.xml

<odoo>
    <record id="res_users_view_form_inherit_vinc_course" model="ir.ui.view">
        <field name="name">res.users.form.inherit.vinc_course</field>
        <field name="model">res.users</field>
        <field name="inherit_id" ref="base.view_users_form"/>
        <field name="arch" type="xml">
            <xpath expr="//notebook" position="inside">
                <page string="Courses">
                    <field name="course_ids"/>
                </page>
            </xpath>
        </field>
    </record>
</odoo>

expr is an XPath expression that must pick exactly one element of the parent view; position says what to do with it:

positionEffect
insideAppends the content at the end of the selected element
before / afterInserts the content as a sibling right before / after the selected element
replaceSwaps the selected element for the new content
attributesChanges attributes of the selected element

When only one element is targeted you can shorten it by placing position on the target element itself, e.g. <field name="description" position="after">...</field>; the result equals using xpath. Finally, since this view extends one from the base module, make sure your module lists base in depends and declares the file in data.

Examples for each position value

<!-- add a field after the name field -->
<xpath expr="//field[@name='name']" position="after">
    <field name="level"/>
</xpath>

<!-- insert ahead of an element -->
<xpath expr="//field[@name='price']" position="before">
    <field name="duration_hours"/>
</xpath>

<!-- change an element's attributes -->
<xpath expr="//field[@name='name']" position="attributes">
    <attribute name="string">Course title</attribute>
</xpath>

<!-- swap an element for new content -->
<xpath expr="//field[@name='description']" position="replace">
    <field name="description" placeholder="Short description..."/>
</xpath>

With replace, a $0 node inside the new content is substituted by the original element, letting you wrap the old element instead of discarding it. With attributes, the <attribute name="..."> elements inside the xpath body name the attributes to change.

A few notes on model inheritance

  • _inherit takes one model name or a list. When _name is set, the entries of _inherit are the parents the new model derives from; when _name is not set, it names the single model being extended in place.
  • Delegation with _inherits is "compositional": the new model shows every parent field but persists none, because values live on the linked record. When several parents declare a field under one name, the one from the last parent in the list wins.
  • In @api.ondelete, leave at_uninstall at False in nearly every case, so removing a module never raises business-rule errors.
  • Keep each inherited model in its own file named after the model (for example models/res_users.py).

Common mistakes with inheritance

  • Overriding create, write… but forgetting super() or returning the wrong type. Skipping super() breaks Odoo's processing chain (fields are not saved, other modules cannot run their logic). Always call super() and hand back the same kind of data as the parent.
  • An xpath that finds nothing, or finds several elements. The documentation says both cases raise an error when the view loads. Make the expression specific enough (for example with @name) and double-check it against the original view in developer mode.

Summary

  • When overriding CRUD methods, always call super() and return the same kind of value; use @api.ondelete instead of overriding unlink.
  • _inherit extends a model, _inherits delegates to a parent model.
  • A child view points at its parent with inherit_id and selects exactly one element via xpath.
  • Your module must list the original module in depends.

FAQ

How does _inherit differ from _inherits? ▾
_inherit applies Python-style inheritance, either to build on a model that already exists or to define a new model sharing its structure. _inherits is delegation: the new model shows the parent fields while the values stay on the linked parent record.
Must I call super when overriding create or write? ▾
Almost always. Skipping super breaks Odoo's processing chain, and what you return must have the same shape as the parent result (a dict in, a dict out).
Why prefer @api.ondelete over overriding unlink? ▾
A method decorated with @api.ondelete runs during deletion yet stays compatible with module uninstallation. An overridden unlink that raises errors can make uninstalling leave orphaned tables or records.
How does xpath select elements in an inherited view? ▾
The expr attribute holds an XPath expression that has to hit exactly one element of the parent view; zero or several hits raise an error. The position attribute (inside, before, after, replace, attributes) says what to do with it.
