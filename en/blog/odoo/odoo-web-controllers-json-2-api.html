Odoo 20 Web Controllers and the JSON-2 API

Letting Odoo talk to a website, a mobile app or other software takes endpoints. This guide shows how to write controllers with @route and how to use the built-in JSON-2 API with API keys, access rights and transactions.

Updated: October 16, 2026 16 min read Vinc Academy Team

Quick summary

Odoo offers two ways to expose data to the outside world: write your own controller with @route, or use the built-in JSON-2 API. A controller extends http.Controller, and each route declares its auth (public, user, bearer, none) and type (http or jsonrpc). The JSON-2 API accepts POST /json/2/<model>/<method> with an API key in the Authorization: bearer header, and always respects the permissions of the key's owner.

Web controllers: creating endpoints for a module

Models have their own inheritance system, and controllers have theirs, because when a request arrives the database and modules may not be ready yet (no database created or selected). You create a controller by extending Controller and declare routes with methods decorated by route().

The scaffold from part 3 already has a controllers/ folder. Create controllers/main.py with an endpoint returning published courses as JSON:

custom-addons/vinc_course/controllers/main.py

from odoo import http
from odoo.http import request


class VincCourseController(http.Controller):

    @http.route('/vinc_course/courses', auth='public', type='http', methods=['GET'])
    def courses(self, **kw):
        courses = request.env['vinc.course'].sudo().search([('is_published', '=', True)])
        data = [{'id': c.id, 'name': c.name, 'level': c.level} for c in courses]
        return request.make_json_response(data)

Replace the import line in controllers/__init__.py with from . import main, upgrade the module and open http://localhost:8069/vinc_course/courses. A few points to understand:

  • request is the current request object; request.env gives you the ORM environment, request.make_json_response() serializes data to JSON with a matching Content-Type, and request.render() renders a QWeb template.
  • For public routes the request runs as the shared Public user. In part 5 we granted rights only to internal users, so the example uses sudo() deliberately, filtering on published records and returning only safe fields. Do not scatter sudo() everywhere.

@route options

ParameterMeaning
routeThe path(s) the method serves, in werkzeug's route format
type'http' or 'jsonrpc' (called 'json' up to Odoo 18); decides where parameters are read and how the response is serialized
auth'user': login required; 'bearer': authenticated by an API key in the Authorization header; 'public': may be anonymous (runs as the Public user); 'none': always active even with no database, mainly for the framework
bearer_scopeScope of the token; required for auth='bearer' routes and forbidden on every other auth mode
methodsAllowed HTTP verbs; every verb is allowed when omitted
csrfCSRF protection; on by default for type='http', off for type='jsonrpc'
corsContent of the CORS header Access-Control-Allow-Origin

The request object and its helpers

HelperPurpose
request.get_http_params()Merges key/value pairs from the query string and from body forms (both application/x-www-form-urlencoded and multipart/form-data)
request.make_response(data, headers, cookies, status)Builds a non-HTML response, or an HTML one with custom headers or cookies. Returning non-HTML data without a complete response object leaves clients unable to interpret it correctly
request.make_json_response(data, ...)Serializes data to JSON and sets Content-Type unless you already did
request.not_found()Shortcut for an HTTP 404 response
request.render(template, qcontext)Renders a QWeb template lazily: the work happens at the very end of dispatch, so the template or qcontext can still be altered before then
request.reroute(path)Rewrites the current URL, like a light redirect that returns no 3xx code to the browser
request.update_env(user, context, su)Changes the user, context or superuser mode of the request's environment
request.csrf_token() / validate_csrf()Generates and checks CSRF tokens; by default a token is valid for 48 hours

The jsonrpc route type

A type='jsonrpc' route carries JSON-RPC 2 over HTTP but deviates from the standard twice: the payload's method entry is disregarded (the URL already picks the controller), and params has to be a JSON object with named keys instead of an array. You may also send context to replace the session context; it is stripped before the endpoint is called:

--> {"jsonrpc": "2.0", "method": "call", "params": {"arg1": "val1"}, "id": null}
<-- {"jsonrpc": "2.0", "result": {"res1": "val1"}, "id": null}

Extending another module's controller

To override, subclass the original controller and redefine the method. You must decorate it again with @route() (arguments may be left out), otherwise the method drops out of the routing table. Arguments in the new decorator are merged over the old ones:

class Restrict(VincCourseController):

    @http.route(auth='user')
    def courses(self, **kw):
        return super().courses(**kw)

The snippet switches the route from public to user, meaning a login is now required.

The JSON-2 API: calling models from external software

Besides hand-written controllers, Odoo makes part of its Models API reachable over HTTP at the /json/2 endpoint (available since Odoo 19). No extra module code is needed: just send a POST to /json/2/<model>/<method>.

Availability

According to the documentation, access to data through the external API exists only on Odoo's Custom pricing plans; One App Free and Standard plans do not include it. Check your plan before designing an integration.

Request layout

PartContent
Authorization headerMandatory: the word bearer, a space, then your API key
Content-Type headerMandatory: application/json, preferably with a charset
X-Odoo-Database headerOptional database name; needed when one server hosts several databases and dbfilter does not use the Host header
URL pathmodel carries the technical model name and method the method to execute
JSON bodyids (record ids; leave empty for @api.model methods), optional context, and the method's own parameters

Example: reading published courses from Python:

import requests

BASE_URL = "https://mycompany.example.com/json/2"
headers = {
    "Authorization": "bearer " + API_KEY,   # load the key from a safe place
    "X-Odoo-Database": "mycompany",
}
res = requests.post(
    f"{BASE_URL}/vinc.course/search_read",
    headers=headers,
    json={"domain": [["is_published", "=", True]], "fields": ["name", "level"]},
)
res.raise_for_status()
print(res.json())

Success returns HTTP 200 with the method's return value as JSON. On failure the server answers 4xx/5xx with a JSON object with the keys name, message, arguments, context and debug.

Creating and managing API keys

  • Generate a key from the user preferences, in the account-security area, using the new-key button. You must give it a label and a lifetime, and its value appears a single time, so copy it and keep it somewhere safe.
  • A key can live at most three months, so long-running keys must be replaced at least every three months. For interactive use prefer a short lifetime, typically one day.
  • When rotating, create the new key first, confirm every service uses it, and only then revoke the old one.

Managing API keys programmatically

Odoo exposes RPC methods to generate and revoke keys. By default only users with the Settings administration right may use them; to allow others, set the system parameter base.enable_programmatic_api_keys to True (under Settings → Technical → System Parameters).

  • res.users.apikeys.generate() takes key (a valid existing key), scope (a string or null), name (a readable label) and expiration_date (ISO 8601). It returns the new key as a string that cannot be fetched again.
  • A scope limits where a key may be used. The rpc scope is the generic one for RPC through controllers with auth='bearer'. Unscoped keys use null.
  • A user may generate up to 10 keys programmatically by default (change it with base.programmatic_api_keys_limit); exceeding it fails with HTTP 422. The expiration date is checked against the longest lifetime allowed by the user's roles.
  • res.users.apikeys.revoke() invalidates a key immediately; a wrong key yields HTTP 403. The key being revoked need not be the one in the Authorization header, so during rotation authenticate with the new key to revoke the old one.

Security and transactions

  • The API follows standard Odoo security: each operation is verified against the key owner's model rights, per-record rules and field restrictions (the subject of part 5).
  • For long-term automated integrations, create a dedicated bot user with minimal rights and an empty password so password login is disabled.
  • Each call runs in its own SQL transaction: committed on success, discarded on error. Several calls cannot share one transaction, so related operations must be wrapped in a single server-side method (often named starting with action_).

Leaving the old RPC endpoints behind

Older integrations that talk to /xmlrpc, /xmlrpc/2 or /jsonrpc should be migrated, since those endpoints are deprecated: Odoo 20 already dropped their db service, and the common and object ones are planned to disappear with Odoo 22. Your own @route(type='jsonrpc') controllers are not affected.

Common mistakes when building APIs

  • A JSON-2 call returns 401 "Invalid apikey". The header must read Authorization: bearer <key>, and the key must be unexpired and not revoked. Remember a key is shown only once when created.
  • A controller override makes the route vanish. You forgot to decorate with @route() again; without it the method is removed from the routing table.
  • Several consecutive JSON-2 calls leave inconsistent data. Each call is its own transaction, so other users can slip in between. Combine the steps into one method on the model.

Summary

  • Controllers extend http.Controller; @route declares auth, type and methods.
  • When overriding a controller you must decorate with @route() again.
  • JSON-2: POST /json/2/<model>/<method>, bearer API key, the key owner's rights, one transaction per call.
  • Wrap related operations in a single method to keep data consistent.

FAQ

What is the difference between type http and jsonrpc in @route? ▾
The type decides where request parameters are read and how the response is serialized. Routes of type http have CSRF protection on by default, while type jsonrpc (named json up to Odoo 18) has it off.
How do auth public, user, bearer and none differ? ▾
user requires a login; bearer authenticates through an API key in the Authorization header; public allows anonymous access and runs under the common Public account; none is always active even without a database and is mainly for the framework.
How do I call the JSON-2 API? ▾
Send a POST to /json/2/<model>/<method> with an Authorization bearer header carrying the API key, Content-Type application/json and a JSON body with ids, context and the method's parameters.
Where do I create an API key and how long does it last? ▾
Generate it from your user preferences in the account-security section. Its value is displayed a single time and its lifetime is capped at three months, so long-lived keys need regular rotation.
