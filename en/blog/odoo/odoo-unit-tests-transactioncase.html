Odoo 20 Unit Tests: TransactionCase, Tags and Form

Automated tests let you upgrade Odoo and edit code without fear of breaking business rules. This guide shows how to write Python tests with TransactionCase, check onchanges with Form, add tags and run with --test-tags.

Updated: October 16, 2026 14 min read – views Vinc Academy Team

Quick summary

Odoo builds on Python's unittest library. You add a tests/ package to the module, put files named test_*.py in it, import them in tests/__init__.py, then write classes extending TransactionCase whose methods start with test_. Run them with --test-tags /module_name on a database where the module is installed. A test that is not imported in tests/__init__.py simply does not run.

What kinds of tests does Odoo have?

Odoo supports three flavors of testing: Python unit tests (checking a model's business logic), JavaScript unit tests (checking the JS code on its own) and tours (simulating a real session to make sure the Python and JavaScript halves cooperate). This part concentrates on Python tests, the kind you will write most while building modules.

Tests are a safety net: when you upgrade Odoo or edit a method, the suite tells you at once whether the business rules from earlier parts, such as computed fields, constraints and access rights, still hold.

Test folder layout

Add a package named tests to the module and Odoo discovers the test files inside it automatically. A test file's name must start with test_ and it must be imported in tests/__init__.py:

vinc_course/
├── ...
└── tests/
    ├── __init__.py
    └── test_course.py

custom-addons/vinc_course/tests/__init__.py

from . import test_course

Writing tests with TransactionCase

TransactionCase is the most used test class. All test methods share one transaction, each method sits in its own savepoint, and at the end the cursor is shut with no commit. So test data is cleaned up automatically and your database stays untouched. Data shared by all methods should be prepared once in setUpClass:

custom-addons/vinc_course/tests/test_course.py

from odoo.exceptions import UserError, ValidationError
from odoo.tests import Form, TransactionCase, tagged


@tagged('post_install', '-at_install')
class TestVincCourse(TransactionCase):

    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.course = cls.env['vinc.course'].create({
            'name': "Odoo Foundation",
            'duration_hours': 20,
            'price': 2000,
        })

    def test_price_per_hour(self):
        self.assertEqual(self.course.price_per_hour, 100)

    def test_duration_must_be_positive(self):
        with self.assertRaises(ValidationError):
            self.course.duration_hours = 0

    def test_cannot_delete_published(self):
        self.course.is_published = True
        with self.assertRaises(UserError):
            self.course.unlink()

    def test_publish_sets_start_date(self):
        with Form(self.env['vinc.course']) as form:
            form.name = "Form course"
            form.is_published = True
        self.assertTrue(form.record.start_date)
  • Give every test method a test_ prefix.
  • Use the standard unittest assertions such as assertEqual, assertTrue and assertRaises.
  • self.env is the ORM environment for creating and searching records; self.ref('module.xml_id') returns an id from an external id, and self.browse_ref(...) returns the record itself.
  • After each method finishes, the record cache and registry cache are cleaned.

Testing onchanges with Form

The Form class imitates a form view on the server side: it fires onchanges at creation and whenever you set a field, and handles defaults around x2many fields. Because onchanges only run inside forms (part 8), this is how you test them. Assign fields straight onto the form, use it as a context manager so it saves on exit, and fetch the saved record through form.record. Note that save() raises AssertionError if a required field is still empty.

Form with many-to-many and one-to-many fields

The Form class copes with relational fields too. For a Many2one you simply assign a recordset. A Many2many appears as an M2MProxy that lets you add or drop records. A One2many exists only through its parent, so you work on it with sub-forms produced by new() and edit(), normally used as context managers so each sub-form is saved into the parent:

with Form(self.course) as form:
    form.tag_ids.add(self.tag)               # Many2many: add
    form.tag_ids.remove(id=self.old_tag.id)  # Many2many: drop by id
    with form.session_ids.new() as line:     # One2many: new line
        line.name = "Session 1"
    with form.session_ids.edit(0) as line:   # edit the first line
        line.name = "Opening session"
    form.session_ids.remove(index=0)         # delete the first line

Two rules worth keeping in mind with Form: save() skips read-only fields and untouched ones (any assignment or onchange flags a field as modified, even when it receives its old value); and when there is nothing to save it just returns the current record. You may pass view (an id, an xmlid or a view object) as the source of onchange and constraint behavior; otherwise the model's default form view applies.

Testing the interface and HTTP with HttpCase

Plain Python tests never touch a browser. For anything involving HTTP or JavaScript, Odoo provides HttpCase: a transactional test case equipped with a url_open helper to request URLs and headless Chrome to run JavaScript. The third kind of test, the tour, plays out a realistic scenario to confirm that the Python and JavaScript sides cooperate.

The browser_js(url_path, code, ...) helper opens a page in the browser and executes JavaScript. Its commonly used parameters:

ParameterMeaning
url_pathPath of the page to load
codeJavaScript to execute
readyA JavaScript object that must exist before the run continues
loginWhich user is logged in during the test, such as 'admin'
timeoutMaximum wait in seconds, 60 by default
success_signalThe string to console.log() on success, "test successful" by default
error_checkerA function that filters out error logs to ignore; without it every error log fails the test
watch, debugOpen a browser window so you can watch the run, or open full-screen Chrome with devtools and a breakpoint

A test signals success by logging the exact success_signal string with console.log(), and signals failure by throwing an exception or by calling console.error and passing text. In debug mode the tour runs with debug=assets and stops right at the exception.

Preparing data and cleaning up

  • Data shared by all methods belongs in setUpClass, created once; this suits suites made of quick tests that nevertheless need a lot of background data.
  • Once each method ends, Odoo empties both the record cache and the registry cache. Models and fields in the registry, however, are not wiped. If a test creates custom models or fields, arrange the cleanup with self.env.transaction.will_change_registry().
  • Two built-in helpers: self.ref('module.xml_id') returns an id and self.browse_ref('module.xml_id') returns the record; both raise ValueError when the external id is missing, and the id must be written in full as module.identifier.

Selecting tests with tags: examples

By default a test deriving from BaseCase counts as standard. You can remove a class from the default suite and run it only on demand:

@tagged('-standard', 'nice')
class TestNice(TransactionCase):
    ...

# run only tests tagged nice
python3 odoo-bin -d odoo20_test --test-tags nice
# run both nice and standard (values add up)
python3 odoo-bin -d odoo20_test --test-tags nice,standard
# run standard but leave out slow
python3 odoo-bin -d odoo20_test --test-tags 'standard,-slow'

@tagged decorates classes; put on a function or method it does nothing. A - prefix drops a tag, or drops tests carrying that tag from the selection even when another tag selected them. In the [-][tag][/module][:class][.method] spec, a method name that is unique can stand alone as .method_name; separate several specs with commas.

Summary

  • Python tests live in the tests/ package, in test_*.py files imported by tests/__init__.py.
  • TransactionCase cleans up data automatically; use setUpClass for shared data.
  • Form is how you test onchanges and form behavior, including x2many fields.
  • HttpCase and tours cover the interface and the Python-JavaScript cooperation.
  • Run with --test-tags /module on a database where the module is installed.

Tagging and running tests

Tags help you pick which tests to run. The @tagged() decorator works on classes (it does nothing on functions or methods). A - prefix removes a tag. The special tags:

TagMeaning
standardTests deriving from BaseCase carry it implicitly; and standard is also the default value of --test-tags
post_installRuns after every module has been installed
at_installRuns immediately after the module installs, before other modules do. Rarely needed because it hinders parallel runs; usually paired with -post_install

Specs given to --test-tags follow the pattern [-][tag][/module][:class][.method]:

# install (or -u) the module, run only its tests, then stop
python3 odoo-bin --addons-path=addons,../custom-addons \
    -d odoo20_test -i vinc_course --test-tags /vinc_course --stop-after-init

# a single class or method
python3 odoo-bin -d odoo20_test --test-tags /vinc_course:TestVincCourse.test_price_per_hour

# every standard test except those tagged slow
python3 odoo-bin -d odoo20_test --test-tags 'standard,-slow'

With --test-tags there is no need to add --test-enable. Run tests on a separate database (for example odoo20_test) instead of your everyday working one.

Common mistakes when starting to write tests

  • You wrote a test but it never runs. Typically the file is not imported in tests/__init__.py (the documentation warns such tests are skipped), the method name does not start with test_, or you used a bare unittest.TestCase without the standard/post_install tags, so it is outside the default suite.
  • Running --test-tags but the module is not installed in that database. Tests execute only for installed modules. On a fresh database add -i module_name at least once; afterwards, when you change code, use -u.

FAQ

My test does not run. What are the usual causes? ▾
Most often the test file is not imported in tests/__init__.py, the method name does not start with test_, or a bare unittest.TestCase was used without the standard and post_install tags.
How does TransactionCase work? ▾
All test methods run in one transaction, each in its own sub-transaction (savepoint), and at the end the cursor is closed with no commit, so test data disappears on its own.
How do I run the tests of just one module? ▾
Use --test-tags /module_name, for example --test-tags /vinc_course. Narrow it to a class or method with the syntax [-][tag][/module][:class][.method]. The module must already be installed in the database.
When should I use Form in a test? ▾
When you need to check onchanges or form-view behavior on the server side. Form fires onchanges at creation and when you assign fields, just like a user working in the interface.
