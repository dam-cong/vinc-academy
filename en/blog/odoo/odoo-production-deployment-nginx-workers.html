Deploy Odoo 20 to Production: Nginx, HTTPS, Workers

Going from a development box to a real server takes more than running odoo-bin. This guide gathers the production setup: odoo.conf, dbfilter, PostgreSQL, workers, Nginx with HTTPS and a security checklist before going public.

Updated: October 16, 2026 17 min read Vinc Academy Team

Quick summary

To deploy Odoo 20 to production, switch from multi-threaded to multi-process mode (workers), put Odoo behind a reverse proxy such as Nginx with HTTPS and enable proxy_mode, restrict databases with dbfilter, set a strong admin_passwd, hide the database list and install no demo data. Use a dedicated, non-superuser PostgreSQL account.

How production differs from a development machine

A development box only has to run. A server facing the Internet also needs system-level setup: which database gets served, how PostgreSQL is reached, how many processes handle requests, HTTPS for the traffic and some baseline hardening. Odoo's documentation covers these steps on its system-configuration page, to be applied after an installation like the one in part 2. What follows is a suggested order of work.

Choosing an installation method

Even with packages you still install wkhtmltopdf 0.12.6 by hand (not via pip) so PDFs get headers and footers, as noted in the reports part.

The odoo.conf file

Rather than typing many command-line flags, keep settings in a file. Here is a template for a server with its own PostgreSQL connection:

[options]
admin_passwd = <long random string>
db_host = 127.0.0.1
db_port = 5432
db_user = odoo
db_password = <password>
dbfilter = ^mycompany$
list_db = False
proxy_mode = True
workers = 5
max_cron_threads = 1
limit_memory_soft = 629145600
limit_memory_hard = 1677721600
limit_time_cpu = 600
limit_time_real = 1200

The key entries are explained below.

dbfilter: picking the database from the domain

Odoo is multi-tenant: one server can serve several databases. A logged-in backend user picks the database at login, but anonymous visitors (website, portal) are not tied to one, so Odoo needs a rule. dbfilter is a regular expression that decides based on the requested domain, and it may contain %h (hostname) or %d (first subdomain). On a server holding several databases, especially with the website in use, setting dbfilter is mandatory.

Once each domain matches a single database, also set list_db = False (equivalent to the --no-database-list flag) so that no database is listed and the management pages stay closed.

PostgreSQL in production

  • By default PostgreSQL accepts only UNIX-socket and loopback connections. If Odoo and PostgreSQL live on different machines, PostgreSQL must listen on the network (or you use an SSH tunnel), and you set db_host, db_port, db_user, db_password in Odoo.
  • Give Odoo a PostgreSQL account that is not a superuser, and preferably let another account own the databases.
  • Encrypting the Odoo-to-PostgreSQL link is possible with db_sslmode, which takes one of six levels from disable up to verify-full.
  • The screens that manage databases are protected by admin_passwd, a setting available only in the configuration file. Make it a long random value.

Workers: multi-process instead of multi-thread

Odoo ships two built-in server modes. The multi-threaded one is simple, meant for development and demos and works on Windows too, but Python's GIL keeps it from using hardware well; it is the default (omit --workers or give it the value 0). The multi-process one is for production: it spawns a pool of workers at startup, new requests wait in a queue for a free worker, dedicated cron workers exist, and a resource monitor can kill and restart misbehaving workers. It is switched on by giving workers any value other than zero, and it is unavailable on Windows.

Estimating workers and RAM

  • Rule of thumb for the maximum worker count: (CPU count × 2) + 1; cron workers consume CPU as well.
  • Roughly one worker serves about 6 concurrent users.
  • Assume 20% heavy and 80% light requests; a heavy worker takes around 1GB of RAM and a light one about 150MB (when computed fields and SQL are well designed). RAM needed = workers × (0.8 × 150MB + 0.2 × 1GB).

The documentation's example: a 4-CPU server with 60 concurrent users. Theory suggests 10 workers (60/6) with a cap of 9 from the CPU rule; they choose 8 workers plus 1 for cron, about 3GB of RAM for Odoo, and a monitoring system to watch CPU load.

Worker limits and recycling

The multi-process monitor relies on the following limits (memory is in bytes; the configuration template above uses values different from the defaults to suit a small server):

SettingDefaultEffect
limit_memory_soft2048 MiBMaximum virtual memory per worker; past it the worker is killed and recycled at the end of the current request
limit_memory_hard2560 MiBHard cap; a worker above it is killed at once without waiting for the request to finish
limit_time_cpu60CPU seconds allowed per request; beyond it the worker is killed
limit_time_real120"Wall-clock" limit per request (SQL waiting included); beyond it the worker is killed
limit_request8196Requests one worker serves before being recycled and restarted
max_cron_threads2Workers reserved for cron; in multi-process mode they come on top of the HTTP workers

The live-chat port --gevent-port defaults to 8072 and is used only in multi-process or gevent mode.

HTTPS with Nginx and proxy_mode

Odoo sends credentials in clear text, so a secure deployment must use HTTPS. The usual way is placing Odoo behind an SSL-terminating reverse proxy such as Nginx, which involves enabling proxy_mode (only when Odoo really sits behind a proxy), configuring SSL termination, configuring request forwarding, and redirecting plain HTTP to HTTPS. A trimmed template:

upstream odoo     { server 127.0.0.1:8069; }
upstream odoochat { server 127.0.0.1:8072; }

map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 80;
    server_name odoo.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name odoo.example.com;
    ssl_certificate     /etc/ssl/nginx/server.crt;
    ssl_certificate_key /etc/ssl/nginx/server.key;
    proxy_read_timeout 720s;

    location /websocket {
        proxy_pass http://odoochat;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location / {
        proxy_pass http://odoo;
        proxy_redirect off;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";
    }
}
  • In multi-process mode a dedicated live-chat worker listens on --gevent-port (8072 in the template). The proxy has to forward every request under the /websocket/ path to that worker.
  • The Strict-Transport-Security response header makes browsers insist on HTTPS; from then on you must keep valid HTTPS running permanently, or users will meet warnings or be locked out.
  • Static files (paths like /<module>/static/...) can be served directly by Nginx to relieve Odoo; root and try_files depend on your --addons-path.

How proxy_mode behaves

proxy_mode makes Odoo honor the X-Forwarded-* headers by way of Werkzeug's proxy handling. Two details are easy to miss: Odoo ignores every X-Forwarded-* header when the request lacks X-Forwarded-Host, and the real IP is always taken from the last entry of the X-Forwarded-For chain. So your web server must send all the headers shown in the Nginx template above. If you accidentally open Odoo directly (bypassing Nginx) while proxy_mode is on, Odoo logs a warning that includes the configuration you need.

Running Odoo as a WSGI application

Odoo can be mounted as a standard WSGI application. It supplies a sample script, odoo-wsgi.example.py, to customize, with configuration set directly in odoo.tools.config rather than on the command line or in a file. Keep in mind that a WSGI server exposes only the main HTTP endpoint (web client, website, web service); since Odoo no longer controls worker creation, it cannot start cron or live-chat workers by itself:

  • Cron: run one of Odoo's built-in servers next to the WSGI one, configured to process only cron through --no-http (or http_enable = False). On Linux prefer multi-process, for example --workers=-1 together with --max-cron-threads=n.
  • Live chat: needs a gevent-compatible WSGI server, able to hold many simultaneous long connections without much processing power. Every request whose path starts with /websocket/ must be sent to it, while other requests go to the regular WSGI server. The cron server can double as the live-chat server if you drop --no-http.

Security checklist before going public

  • Choose a strong admin_passwd, and shut the database administration pages right after the system goes live.
  • Avoid admin as a login name, and keep administrator accounts out of daily work. Never keep default passwords such as admin/admin, even on test or staging databases.
  • Skip demo data on public servers: demo databases come with stock logins and passwords that attackers can abuse.
  • Apply dbfilter and list_db = False, and keep the PostgreSQL account unprivileged.
  • Keep up with new builds; run multi-process with sensible limits (memory, CPU, time).
  • Front Odoo with an HTTPS web server holding a valid certificate, limit request size, configure timeouts, then switch on proxy mode.
  • For SSH use public keys only, consider a VPN, firewall rules for trusted IPs and a brute-force blocker such as fail2ban; add rate limiting at the proxy or firewall.
  • Run demo, test and staging copies on other hosts than production, secured just as carefully.

About backups

Odoo's data consists of the PostgreSQL database and the filestore (in the official Docker image that is /var/lib/odoo, the volume from part 2). This part does not go deep into backup and monitoring options because they depend on your infrastructure; plan for both components before go-live and rehearse restores regularly.

Common mistakes when deploying

  • Putting Nginx in front but forgetting proxy_mode. Odoo then trusts the details of the proxy rather than those of the real visitor (hostname, scheme, IP address). Start Odoo with proxy mode so it reads the X-Forwarded-* headers the proxy sends. Enable it only when Odoo truly sits behind a reverse proxy.
  • Exposing a server whose database has demo data or an admin/admin password. The documentation warns that such default credentials can be exploited even on staging. Create a fresh database without demo data and change the administrator's login and password.
  • Forgetting to route /websocket/ to the live-chat worker. In multi-process mode, requests keep going to the ordinary HTTP workers by default. Configure the proxy to send paths starting with /websocket/ to the --gevent-port port and run Odoo in proxy mode.

Summary

  • Production: multi-process (workers), Nginx + HTTPS, proxy_mode, dbfilter, list_db = False.
  • Dedicated non-superuser PostgreSQL account; no demo data; no default passwords.
  • Estimate workers with (CPU × 2) + 1 and ~6 users per worker; set memory and time limits.
  • Route /websocket/ to the live-chat worker; rehearse a backup restore before go-live.

FAQ

Should production Odoo run multi-threaded or multi-process? ▾
Run multi-process by setting workers to a non-zero integer. Multi-threaded is the default, simple and fine for development or demos, but it makes poor use of hardware because of Python's GIL.
How do I estimate the number of workers? ▾
The rule of thumb for the maximum is CPU count times 2 plus 1, and roughly one worker serves 6 concurrent users. Cron workers also use CPU, so count them too.
What is proxy_mode for? ▾
When Odoo runs behind a reverse proxy such as Nginx, proxy_mode makes it use the visitor's real headers (hostname, scheme, IP) instead of the proxy's. Enable it only when Odoo truly sits behind a proxy.
Why set dbfilter and list_db? ▾
dbfilter tells Odoo which database serves which domain, and it is required when one server holds several databases. Once each domain matches a single database, set list_db to False so databases are not listed and the management screens are blocked.
