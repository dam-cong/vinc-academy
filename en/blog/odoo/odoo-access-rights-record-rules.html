Odoo 20 Security: Access Rights and Record Rules

Security decides who can see and edit which data. This guide shows how to declare access rights for a model, write per-record rules and avoid the security mistakes that the Odoo documentation warns about.

Updated: October 16, 2026 13 min read – views Vinc Academy Team

Quick summary

Odoo uses two data-driven security mechanisms, both tied to user groups: access rights (permissions per model) and record rules (conditions per record). A model without access rights is closed to everyone. You declare rights in security/ir.model.access.csv and must list that file in the manifest's data; record rules are written in XML with a domain_force.

CSV data files: the foundation of security

Odoo leans heavily on data: next to the Python code, a module also ships records that get loaded when you install it. A CSV file is one carrier for such records, and security settings are delivered the same way. Three conventions to remember:

  • By convention, security-related data files live in the security/ folder, while views and actions go in views/.
  • Each file has to be listed under data in __manifest__.py, and its content is read only during an install or upgrade of the module.
  • The manifest order is the loading order, so a file that points to records from another file must be listed after it.

User groups (res.groups)

Both mechanisms reach people through groups: someone may sit in as many groups as needed, and every security rule is attached to a group, never to an individual. The res.groups model has these main attributes:

  • name: a readable label spelling out the group's role or purpose.
  • category_id: the module category, which ties a group to an application (a family of related business models) and presents its groups as a one-of-many choice on the user form.
  • implied_ids: other groups assigned together with this one. This is a handy pseudo-inheritance: an implied group can still be taken away from one user while the implying group stays.
  • comment: extra notes about the group.

Access rights: permissions per model

An access right lets a group of users perform operations on a whole model. If no access right matches a user's operation (through their groups), the user has no access. That is why the model from part 4, which had no rights yet, made Odoo log a no access rules warning and block all access.

An access right is a row in the table behind ir.model.access, and its main attributes are: model_id (the model it governs), group_id (the group receiving the rights; empty means every user, including portal and public users) and four permissions perm_read, perm_write, perm_create, perm_unlink. All four are off by default. Rights stack up: what a user may do is everything granted by any group they belong to.

Create security/ir.model.access.csv for the vinc.course model:

custom-addons/vinc_course/security/ir.model.access.csv

id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
access_vinc_course_user,vinc.course user,model_vinc_course,base.group_user,1,1,1,1
ColumnMeaning
idExternal identifier of the access right, should be unique in the module
nameDescriptive name
model_id:idThe model, written as model_ + the _name with dots turned into underscores: vinc.course becomes model_vinc_course
group_id:idGroup receiving the rights; base.group_user is the internal-user group
perm_*1 grants, 0 denies. unlink means "delete"

To make the group read-only, change the last four numbers to 1,0,0,0. Then declare the file in the manifest, before any view files:

'data': [
    'security/ir.model.access.csv',
],

Run -u vinc_course again: the no access rules warning disappears.

Record rules: conditions per record

An access right answers "may I act on this model at all?". A record rule then asks "on which records?". Rules are checked record by record, after access rights, and are records of the ir.rule model. One important difference: rules allow by default. When the model-level right is granted and no rule targets the user, nothing stops them.

Main attributes of ir.rule:

  • model_id: the model affected.
  • groups: the groups the rule applies to; empty makes it a global rule.
  • domain_force: the condition, written as a domain. A record matching the domain is allowed, otherwise forbidden. You can use user, time, company_id and company_ids in it.
  • perm_*: which operations the rule applies to. For rules, an unselected operation is simply not checked; all are selected by default (the opposite of access rights).

Example: internal users see only published courses.

custom-addons/vinc_course/security/vinc_course_rules.xml

<odoo>
    <record id="vinc_course_rule_published" model="ir.rule">
        <field name="name">Vinc Course: only published for users</field>
        <field name="model_id" ref="model_vinc_course"/>
        <field name="groups" eval="[(4, ref('base.group_user'))]"/>
        <field name="domain_force">[('is_published', '=', True)]</field>
    </record>
</odoo>

Add 'security/vinc_course_rules.xml' to data right after the CSV file, then upgrade the module.

Global and group rules compared

Global rule (no group)Group rule
When several rules applyThey intersect: all must be satisfiedThey unify: satisfying any one is enough
Adding a new ruleAlways narrows access furtherCan widen access, but never beyond global rules

Restricting access per field

A field can carry a groups attribute (external ids joined by commas in one string). Users outside every listed group do not see the field in views, and reading or writing it directly raises an access error. Example: price = fields.Float(groups='base.group_system').

Security mistakes to avoid

Odoo's documentation highlights a few developer mistakes worth learning about from day one:

  • Trusting the arguments of public methods. Any method not starting with _ can be called over RPC with arbitrary parameters, while access rights are only checked during CRUD operations. A method doing something sensitive must verify conditions itself, and internal work belongs in a method starting with _.
  • Bypassing the ORM with raw SQL. That also bypasses translations, the active flag and access rights. Prefer search; if SQL is unavoidable, always pass parameters separately and never concatenate strings.
  • Using t-raw to display user-entered content in templates, a common route to XSS.

Three safe patterns to memorize

  • Never splice strings into SQL. Do not use string addition or % formatting to put variables into a query. Pass parameters separately so the database library (psycopg2) decides how to format them; Odoo also has an SQL class that builds queries from templates and handles inputs. From worst to best: concatenation, separate parameters, the SQL class, and ideally the ORM with search([...]).
  • Use the Domain class rather than gluing domain lists together. A domain is a serializable list, so if a user controls part of unnormalized input they can inject extra conditions (such as ['|', ('id', '>', 0)] to see every record). Use Domain(...) and the &= operator to combine safely.
  • Do not use t-raw with user-entered content. Data integrity is hard to guarantee between computation and the browser DOM, and a t-raw judged harmless now may become dangerous after a later fix or refactoring. Prefer t-out, which escapes HTML automatically.

Common mistakes when learning security

  • The model exists, but regular users see nothing. Check the startup log for a no access rules warning. According to the documentation, a model without access rights is treated as closed to everyone. Create ir.model.access.csv, add it to data in the manifest and upgrade with -u.
  • Creating several global rules on one model. Global rules intersect, so two non-overlapping rules leave no record that satisfies both, and every user loses access. The documentation calls this risky; prefer group rules where possible.

Summary

  • Access order: groups, access rights (per model), record rules (per record), field-level access.
  • A model without access rights is closed to everyone; declare them in ir.model.access.csv and list the file in data.
  • Record rules allow by default; avoid stacking several global rules.
  • Public methods, raw SQL and t-raw are three common sources of security bugs.

FAQ

Why do users see no data in my new model? ▾
When a model has no access right, Odoo treats it as closed to everyone and logs a no access rules warning. Create ir.model.access.csv, declare it in the manifest data list and upgrade the module.
What is the difference between access rights and record rules? ▾
Access rights grant a group permissions on the whole model. Record rules add per-record conditions, for example only showing published records. Rules are checked after access rights.
How do global rules differ from group rules? ▾
Global rules intersect, so all must be satisfied and they always narrow access. Group rules unify, so satisfying any one is enough; they can widen access but never beyond global rules.
How do I write the model_id:id column in ir.model.access.csv? ▾
Write model_ followed by the model _name with dots replaced by underscores. For example the model vinc.course becomes model_vinc_course.
