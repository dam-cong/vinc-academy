OWL Basics in Odoo 20: Components, Hooks and Assets

OWL underpins the Odoo web interface. This guide helps you understand OWL components, write your first one, add files to asset bundles and grasp the web client building blocks: registries, services and hooks.

Updated: October 16, 2026 14 min read – views Vinc Academy Team

Quick summary

Odoo's web interface is built with OWL, a declarative component framework whose templates are written in QWeb. A component usually consists of a JavaScript file and an XML template, added to the web.assets_backend bundle through the manifest's assets key. Inside a component, initialize state in setup() (never the constructor) with hooks such as useState.

What is OWL and where does it sit in Odoo?

What you see at /odoo is one long-running page rather than a series of full page loads: each click fetches just the data required, redraws the affected part and updates the address bar. This client is written with OWL, a declarative component system in the spirit of Vue and React. A component's markup is a QWeb template, enriched with a handful of OWL directives. The Odoo documentation stresses that all new development should use OWL whenever possible. OWL's source is maintained in its own GitHub repository, and every Odoo version from 14 onwards shares the same OWL version.

Two meanings of "frontend"

In the Odoo ecosystem, frontend usually means the public website and backend the web client, which differs from the common browser-versus-server meaning. In the docs, "component" always means an OWL component, while "widget" is the older approach.

Your first OWL component

As a rule, a component should be made of 2-3 files kept together: a JavaScript file, an XML template and optionally an SCSS/CSS file. Here is a simple counter for the vinc_course module:

vinc_course/static/src/components/course_counter/course_counter.js

import { Component, useState } from "@odoo/owl";

export class CourseCounter extends Component {
    static template = "vinc_course.CourseCounter";

    setup() {
        this.state = useState({ value: 0 });
    }

    increment() {
        this.state.value++;
    }
}

vinc_course/static/src/components/course_counter/course_counter.xml

<?xml version="1.0" encoding="UTF-8"?>
<templates xml:space="preserve">
    <t t-name="vinc_course.CourseCounter">
        <button class="btn btn-primary" t-on-click="increment">
            Viewed: <t t-out="state.value"/>
        </button>
    </t>
</templates>
  • useState creates reactive state: when state.value changes, the interface updates by itself.
  • t-on-click="increment" is an OWL directive that binds an event to a component method.
  • Keep templates in XML files so translation works, and let the component merely name its template. Defining the template inside JavaScript via the xml helper suits first experiments only.
  • The template naming convention is addon_name.ComponentName, which prevents clashes between modules.

Use setup(), not the constructor

Components are classes and so have constructors, but a JavaScript constructor cannot be overridden the way Odoo needs. Therefore do all initialization inside the setup() method. No component in Odoo may use constructor(parent, props) directly.

Adding files to an assets bundle

JavaScript, CSS and templates are not loaded on their own. You declare them under the manifest's assets key: a dictionary mapping bundle names to lists of files, with glob support so one line can cover many files:

'assets': {
    'web.assets_backend': [
        'vinc_course/static/src/components/**/*',
    ],
},
BundleContents
web.assets_backendEverything tied to the backend client: actions, views, static XML templates
web.assets_frontendEverything tied to the public site: shop, portal, forum, blog
web.assets_commonLow-level pieces shared by the backend client, the website and Point of Sale; foundations of the framework
web.assets_unit_testsAll JavaScript test code

Standard JavaScript modules stored below /static/src or /static/tests are turned into Odoo's own module format with no action from you. Files are then merged, minified (unless debug=assets is on) and sent to the browser; when debugging, use ?debug=assets to load the unminified versions.

Building blocks of the web client

Four concepts do most of the work in the client: registries, services, components and hooks.

  • Registry: a lookup table for one family of objects. Whatever you add becomes available everywhere else; the fields registry, for example, lists the field components views may display. Registries are the main way to extend the UI.
  • Service: long-lived code providing a feature, much like a dependency-injection system. The notification service shows notifications, the rpc service is how code talks to the server. Components obtain services through the useService hook.
  • Component: the OWL components that belong to the web client.
  • Hook: a reusable function tied to the component lifecycle, a functional take on mixins. useState is a hook, and you can write your own using onWillStart, onWillUnmount and friends.

A component reaches the environment (this.env) for services, the debug flag, the translation function and the isSmall flag (true when the screen is 767px wide or less).

Plugging a component into the interface

How a component is attached to Odoo depends on the extension point you choose: a field, a view, a client action screen or a main component of the web client (via the main_components registry). Each has its own API, so continue with the official tutorial Discover the web framework (chapters Owl components and Build a dashboard), which ships a sample repository for Odoo 20. It assumes you already know models, controllers and QWeb, exactly what this series has covered.

Where does the web client's JavaScript live?

All JavaScript (plus CSS and templates) of the web module sits in web/static/src. Anything inside can be imported using the @web prefix, e.g. import { memoize } from "@web/core/utils/functions". The main folders:

FolderContents
core/Most low-level features
fields/All field components
views/The JavaScript view components (form, list…)
search/Control panel, search bar, search panel
webclient/Code specific to the web client: navbar, user menu, action service…

The web client itself is an OWL application. Its (simplified) template holds a NavBar, an ActionContainer (which shows whatever controller the current action needs, be it a client action or a view of an act_window action) and a MainComponentsContainer (which renders everything registered under main_components, the route other parts take to extend the web client). The action service keeps a stack of active actions in memory, which are the breadcrumb entries.

The this.env object

KeyValue
qwebNeeded by OWL; holds every template
busThe main bus, coordinating some generic events
servicesAll deployed services (best reached through the useService hook)
debugA string; non-empty means the web client is in debug mode
_tThe string translation function
isSmallA boolean; true in mobile mode (screen 767px wide or less)

Templates are translated automatically, so _t is only needed to translate strings inside JavaScript code.

Asset operations

Usually you just add files to a popular bundle. For special needs the manifest also supports the operations below (the four that target one particular file, before, after, replace and remove, only work if that file was declared earlier, whether in a manifest further up the dependency chain or in an ir.asset record having a smaller sequence):

OperationSyntaxEffect
append'path'Adds a file at the end of the bundle (the default)
prepend('prepend', path)Adds a file at the start of the bundle
before('before', target, path)Adds a file just ahead of the target
after('after', target, path)Adds a file just behind the target
include('include', bundle)Nests another bundle (sub-bundles conventionally start with an underscore)
remove('remove', target)Takes a file out of the bundle
replace('replace', target, path)Swaps a file for your version, at the very same position

Order matters for CSS and bootstrap scripts. Odoo's procedure: start from an empty list; apply ir.asset records with a sequence below 16; then apply each module's manifest operations in dependency order (the web module before website); and last of all apply the leftover ir.asset records. A file already in the list is not added again, so only its first occurrence counts.

Three kinds of JavaScript files

  • Native JavaScript modules: for every new file. files below /static/src and /static/tests are converted into Odoo modules for you; in other folders a file is converted only if its first line carries an @odoo-module comment.
  • Odoo modules (the custom module system): useful only for old files not yet converted.
  • Plain JavaScript files: reserved for external libraries and a few very low-level jobs, ideally written as an IIFE so variables do not leak into the global scope. Every external library loads this way. To make Odoo skip a file, make its first line /** @odoo-module ignore **/.

Ready-made components

The web client ships a set of generic components for reuse: ActionSwiper (an action on horizontal swipe), CheckBox, ColorList, Dropdown, Notebook (page switching through tabs), Pager (pagination), SelectMenu (a dropdown to choose one option) and TagsList (tags shown as pills). Each has its own import location, for instance @web/core/action_swiper/action_swiper; check the Owl components page of the documentation before rebuilding any of these yourself.

Common mistakes when learning OWL

  • Putting initialization in the constructor. Use setup(); Odoo's documentation states that no component may use the constructor directly.
  • Creating the JS and XML files but the interface does not change. Usually the files are not in a bundle: check the manifest's assets key and the path glob, upgrade with -u, then open ?debug=assets to see whether the files load.
  • Naming a template something generic such as MyComponent. Follow addon_name.ComponentName so it cannot collide with another module.

Summary

  • The Odoo web interface is a single-page app built on OWL; new development should use OWL.
  • A component = a JavaScript class + an XML template (addon_name.ComponentName), initialized in setup().
  • Files must be in a bundle declared under the assets key; ?debug=assets helps verify.
  • Registries, services, hooks and this.env are the four concepts to master.

FAQ

What is OWL in Odoo? ▾
OWL is a declarative component framework, in the spirit of Vue and React, used to build the Odoo web client interface. Components are defined with QWeb templates extended by a few OWL-specific directives.
Why use setup() instead of the constructor? ▾
A JavaScript constructor cannot be overridden the way Odoo needs, so the documentation requires all initialization to go in the setup() method and forbids components from using the constructor directly.
How are a component's JavaScript and template files loaded? ▾
You declare them under the manifest's assets key, usually in the web.assets_backend bundle for the web client. The framework then loads the JavaScript, CSS and templates into OWL.
How do registries, services and hooks differ? ▾
A registry is a key/value map holding extensible objects. A service is long-lived code providing a feature such as notifications or server calls. A hook is a reusable function tied to the component lifecycle.
