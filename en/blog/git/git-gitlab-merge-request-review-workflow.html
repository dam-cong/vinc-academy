GitLab Merge Request: a Code Review Workflow for Teams

Part 5 walks a full merge request cycle on GitLab with the vinc_course module: an issue-based branch, push, the MR description, fixing feedback with new commits, merge, cleanup and why main is protected.

Updated: October 16, 2026 12 min read Vinc Academy Team

In short

A merge request (MR) is where the team looks at, discusses and approves a change before it reaches the main branch. This part walks a full cycle on GitLab with the vinc_course module: a branch named after an issue, push, an MR with a good description and Closes #12, fixing reviewer feedback by pushing more commits, merge, cleanup, and why main is usually protected against direct pushes. The commands run for real on a simulated repo; the interface steps follow GitLab's documentation.

What a merge request is and why companies insist on it

In part 3 you ran git merge yourself on your own machine. In a team that is risky: code nobody has seen lands in the main branch and, if it breaks, everyone pays. A merge request adds a gate in the middle. According to GitLab's documentation, an MR is a central place for the team to review code, discuss and track changes; inside one you see the description, the code changes with comments on the exact lines, CI/CD pipeline information, mergeability reports, comments and the list of commits.

An MR has two roles: the assignee (the owner, usually the author, responsible for progress) and the reviewer (who reads the code, comments and, if eligible, approves). GitLab calls it a merge request; GitHub calls it a pull request, but the workflow is practically the same.

A full cycle: from issue to main

Suppose issue #12 in GitLab asks to “add a price to courses”. First make sure you start from the latest main, then create the branch. GitLab's documentation notes that a branch prefixed with the issue number (such as 12-course-price) lets GitLab prefill the title and link the issue when you open the MR. The second message paragraph (a second -m) says Closes #12 so the issue closes itself once the MR lands:

$ git switch main
Your branch is up to date with 'origin/main'.
Already on 'main'
$ git pull
Already up to date.
$ git switch -c 12-course-price
Switched to a new branch '12-course-price'
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường học phí" -m "Closes #12"
[12-course-price 25ea246] [IMP] vinc_course: thêm trường học phí
 1 file changed, 1 insertion(+)
$ git push -u origin 12-course-price
branch '12-course-price' set up to track 'origin/12-course-price'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      12-course-price -> 12-course-price
$ git log -1 --format=%B
[IMP] vinc_course: thêm trường học phí

Closes #12

After pushing, open GitLab, go to Code → Merge requests and create a new MR for the branch you just pushed (many GitLab versions also show a suggestion button on the project page). Fill in the title and description, set yourself as assignee and pick one or two reviewers; tick Delete source branch when merge request accepted so the source branch removes itself after the merge. The description is the part worth investing in, for example:

## Purpose
Add a price field to courses so sales can quote.

## Changes
- models/course.py: add the price field (Float)
- views/course_views.xml: show price on the form and list views

## How to test
1. Upgrade the module: odoo-bin -u vinc_course -d vinc_test
2. Open Courses, enter a price, save

Closes #12

The reviewer leaves comments on individual lines. According to the documentation, threads that are still open hold up the merge, single comments do not. To act on feedback you do not create a new MR: commit and push more to the same branch and the MR updates itself. The command git log origin/main..HEAD lists exactly the commits the MR contains:

$ sed -i "s/Học phí/Học phí (VND)/" models/course.py
$ git commit -am "[IMP] vinc_course: ghi rõ đơn vị học phí theo review"
[12-course-price b190c76] [IMP] vinc_course: ghi rõ đơn vị học phí theo review
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   25ea246..b190c76  12-course-price -> 12-course-price
$ git log --oneline origin/main..HEAD
b190c76 [IMP] vinc_course: ghi rõ đơn vị học phí theo review
25ea246 [IMP] vinc_course: thêm trường học phí

Once the reviewer is happy and the pipeline is green, someone with permission clicks Merge. Default rules according to the documentation: the default branch (usually main) is protected and only Maintainers and above can merge into it; Developers can merge MRs that target unprotected branches. The graph shows a merge commit joining 12-course-price into main, together with the MR's two commits. In a real setup GitLab also offers squash (combining the MR's commits into one) at merge time; part 8 explains squashing.

A small habit with real value: right after your MR is merged, switch to main, run git pull, and only then create the next branch. If you skip it, the new branch starts from an old main and the next MR is likely to conflict or drag in already-merged commits. Likewise do not leave merged branches lying around: delete both the local and the GitLab copy as in part 4.

Approvals, auto-merge and what each GitLab tier gives you

How review works depends on your GitLab tier. According to the documentation, on the Free tier anyone with the Developer role or higher can approve an MR but approvals are optional and do not prevent merging. Premium and Ultimate add required rules: a minimum number of approvers, kinds of reviewer (backend, frontend, QA...) or a CODEOWNERS file that names reviewers per folder; without enough approvals the MR cannot be merged. Once a reviewer is happy but the pipeline is still running, they can put the MR on auto-merge: once all checks pass GitLab merges it for you.

Why you cannot push straight to main

Per GitLab's documentation, a repository's default branch comes protected. A protected branch controls who may merge and push, prevents accidental deletion and can require review. Maintainers configure it under Settings → Repository → Branch rules. To show the effect, this example uses a hook on the simulated “GitLab” that refuses pushes to main; the remote: line is our own text, and real GitLab prints its own wording, but the final remote rejected line looks the same:

$ echo "# thử đẩy thẳng" >> README.md
$ git add README.md
$ git commit -m "[ADD] vinc_course: README"
[main a5b2c69] [ADD] vinc_course: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git push
remote: Nhánh main được bảo vệ: hãy push nhánh riêng và mở merge request.        
To git@gitlab.example.com:vinc/vinc_course.git
 ! [remote rejected] main -> main (pre-receive hook declined)
error: failed to push some refs to 'git@gitlab.example.com:vinc/vinc_course.git'

The commit is already on your local main. The standard fix: keep the commit by creating a branch from here and pushing that, then move local main back to exactly origin/main (the git reset --hard command is explained in part 7; make sure the commit is safe on the new branch before running it):

$ git switch -c fix/readme
Switched to a new branch 'fix/readme'
$ git push -u origin fix/readme
branch 'fix/readme' set up to track 'origin/fix/readme'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      fix/readme -> fix/readme
$ git switch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)
Switched to branch 'main'
$ git reset --hard origin/main
HEAD is now at 828392e Merge branch '12-course-price' into 'main'
$ git status -sb
## main...origin/main

Writing a merge request that is easy to review

DoWhy
Small MRs with one purposeReviewers read quickly and catch more; easy to undo if needed
Describe the reason, changes and how to testReviewers do not have to guess your intent
Link the issue with Closes #12According to the documentation, words such as Close/Closes, Fix/Fixes, Resolve/Resolves and Implement/Implements before an issue reference close it automatically on merge
Open the MR earlyThe documentation recommends opening early giving the team room to spot bugs early; if unfinished, say so in the title or body
Re-read your own diff firstCatches forgotten print calls, stray files and committed passwords

What a reviewer looks for in an Odoo module MR

  • Access rights: does a new model have a row in ir.model.access.csv (the access-rights part of the Odoo series).
  • Manifest: is the new XML file listed under data in __manifest__.py, in dependency order.
  • Module upgrade: was -u vinc_course run on a test database without errors.
  • Scope: does the MR touch another module or unrelated files; Odoo's guidelines also advise against one commit changing several modules at once.
  • Secrets: no passwords, API keys or real odoo.conf in the diff.

Common beginner mistakes

  • A direct push to main is blocked. Do not try to force it. Create a branch from the current commit, push it and open an MR as above.
  • Opening a new MR for every round of fixes. Just push more commits to the same branch; the existing MR updates itself and keeps the whole discussion.
  • The MR reports conflicts with the target branch. Someone changed the same lines on main while you worked. Bring the fresh main into your branch and resolve the conflicts locally (part 6), then push again.
  • An MR as big as a project. Dozens of files and several purposes make reviewers skim. Split it into chained MRs; GitLab even retargets a dependent MR when the previous one is merged.

Summary

  • An MR is the review gate: code reaches the main branch only after someone reads it and the pipeline passes.
  • The flow: issue-based branch → commits → push → open MR → fix feedback with new commits → merge → clean up.
  • Closes #12 in a commit or description closes the issue on merge.
  • The default branch is protected: direct pushes are refused, so go through an MR.

When two MRs change the same place you meet a conflict. It is the scariest part for newcomers, and easier than you think. Part 6 shows how to read the <<<<<<< markers, fix by hand and finish the merge.

Frequently asked questions

Are merge requests and pull requests different? ▾
They are the same idea: a request to merge one branch into another with review. GitLab calls it a merge request, GitHub a pull request. The Git commands on your side are identical; only the web interface differs.
Do I open a new merge request to address reviewer feedback? ▾
No. Commit more and push to the same branch; the merge request updates itself and keeps the whole discussion. When done you mark the threads as resolved.
How do I make an issue close itself as the merge request is merged? ▾
Put a keyword with an issue reference in the MR description or a commit, for example Closes #12. According to GitLab's documentation, words such as Close, Fix, Resolve and Implement (and their variants) before the reference close the issue as the MR is merged.
Why can't I push straight to main? ▾
The default branch of a GitLab repository is protected out of the box: only roles granted permission may merge or push into it. Push your own branch and open a merge request; Maintainers adjust the rules under Settings > Repository > Branch rules.
