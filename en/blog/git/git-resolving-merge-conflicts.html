Git Conflicts: How to Resolve Merge Conflicts

Part 6 handles a real conflict in vinc_course's __manifest__.py: read the conflict markers, edit by hand, check, git add and commit, know when to use merge --abort and turn on the zdiff3 style for readability.

Updated: October 16, 2026 11 min read Vinc Academy Team

In short

A conflict happens when Git cannot decide which version to keep, usually because two branches changed the same line; nothing is broken; Git is simply asking you. This part handles a genuine conflict in vinc_course's __manifest__.py: reading the <<<<<<<, =======, >>>>>>> markers, editing by hand, checking with py_compile and git diff --check, then git add and commit. You also learn git merge --abort to start over and the zdiff3 display style that is easier to read.

What a conflict is and when it happens

Git is very good at merging: if two people edit two different files, or the same file in two distant areas, it combines them without asking. A conflict appears only when both branches touch the same lines, or one side deletes a file the other modified. Git then stops the merge halfway, marks the uncertain spot in the file and waits for you to decide.

In an Odoo module a few “hot spots” conflict easily because everybody adds at the same place:

Frequent hot spotWhy
__manifest__.py → dataTwo features add files to the same list; if the whole list is on one line, both changes hit that line
security/ir.model.access.csvEvery new model appends a line at the end, so two branches insert at the same place
XML views of the same modelTwo people edit the same <field> block
Translation .po filesUpdated in bulk, so many branches change the same lines

Reading the conflict markers

Let us create a real conflict. Branch feature/security declares the access file, branch feature/views declares the view file, and both edit the 'data': [] line. Merging the first goes smoothly (fast-forward) because main has not changed; merging the second collides:

$ git switch main
Switched to branch 'main'
$ git merge feature/security
Updating 47905cb..3c18c3d
Fast-forward
 __manifest__.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge feature/views
Auto-merging __manifest__.py
CONFLICT (content): Merge conflict in __manifest__.py
Automatic merge failed; fix conflicts and then commit the result.
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   __manifest__.py

no changes added to commit (use "git add" and/or "git commit -a")
$ git diff
diff --cc __manifest__.py
index a9ec392,9244d07..0000000
--- a/__manifest__.py
+++ b/__manifest__.py
@@@ -2,6 -2,6 +2,10 @@@
      'name': 'Vinc Course',
      'version': '1.0',
      'depends': ['base'],
++<<<<<<< HEAD
 +    'data': ['security/ir.model.access.csv'],
++=======
+     'data': ['views/course_views.xml'],
++>>>>>>> feature/views
      'license': 'LGPL-3',
  }
$ cat __manifest__.py
{
    'name': 'Vinc Course',
    'version': '1.0',
    'depends': ['base'],
<<<<<<< HEAD
    'data': ['security/ir.model.access.csv'],
=======
    'data': ['views/course_views.xml'],
>>>>>>> feature/views
    'license': 'LGPL-3',
}

git status lists the file under Unmerged paths labelled both modified, and suggests both ways out (fix and commit, or --abort). Inside the file Git inserts three kinds of marker:

MarkerMeaning
<<<<<<< HEADStart of the side from the branch you stand on (here main)
=======The divider between the two versions
>>>>>>> feature/viewsEnd of the side from the branch being merged in

During a conflict git diff prints an unusual form (a combined diff): every line has two symbol columns, the left compared with your branch and the right compared with the incoming branch. You do not need to memorise how to read it; just know it shows exactly the lines still in dispute and shrinks as you resolve them.

Resolving step by step

The routine is always the same, big conflict or small:

  • Open the file and find the markers (or use an editor with a merge UI, such as VS Code with its Accept Current/Incoming/Both buttons).
  • Decide the final result: keep one side, keep both or rewrite. Here both are right, so we keep both files in the list.
  • Remove every marker (<<<<<<<, =======, >>>>>>>) from the file.
  • Check the file still works (for Python: py_compile; for an Odoo module: a trial upgrade -u vinc_course).
  • git add the file to say “resolved”, then git commit to finish the merge.
$ cat __manifest__.py
{
    'name': 'Vinc Course',
    'version': '1.0',
    'depends': ['base'],
    'data': [
        'security/ir.model.access.csv',
        'views/course_views.xml',
    ],
    'license': 'LGPL-3',
}
$ python3 -m py_compile __manifest__.py && echo OK
OK
$ git add __manifest__.py
$ git status -s
M  __manifest__.py
$ git commit
[main 4fb4729] Merge branch 'feature/views'
$ git log --oneline --graph -n 5
*   4fb4729 Merge branch 'feature/views'
|\  
| * 250f5a1 [ADD] vinc_course: khai báo view
* | 3c18c3d [ADD] vinc_course: khai báo quyền truy cập
|/  
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course

Running git commit without -m opens your editor with a prefilled “Merge branch …” message; save and close and you are done (in the example the editor is replaced by a no-op so you do not see it). In Odoo's convention, merge commits may carry the [MERGE] tag.

Too scary? Abort with git merge --abort

You can always return to the state before the merge as long as you have not committed. git merge --abort restores everything as if the merge never ran, and you can start again after asking a colleague which version should win. The example below uses a different conflict: two branches both rename the label of the hours field.

$ git switch -c feature/hours-label
Switched to a new branch 'feature/hours-label'
$ sed -i "s/Số giờ/Số giờ học/" models/course.py
$ git commit -qam "[IMP] vinc_course: đổi nhãn số giờ"
$ git switch main
Switched to branch 'main'
$ sed -i "s/Số giờ/Tổng số giờ/" models/course.py
$ git commit -qam "[IMP] vinc_course: đổi nhãn tổng số giờ"
$ git merge feature/hours-label
Auto-merging models/course.py
CONFLICT (content): Merge conflict in models/course.py
Automatic merge failed; fix conflicts and then commit the result.
$ git merge --abort
$ git status -sb
## main

When you just need one side wholesale

If the decision is to keep one branch's version for the whole file, no hand editing is needed. git restore --theirs <file> takes the incoming branch's version, while --ours takes the version from the branch you stand on. You still have to git add and commit. Use it carefully, since this throws away whatever the other side changed in that file:

$ git merge feature/hours-label
Auto-merging models/course.py
CONFLICT (content): Merge conflict in models/course.py
Automatic merge failed; fix conflicts and then commit the result.
$ git restore --theirs models/course.py
$ grep hours models/course.py
    hours = fields.Integer(string='Số giờ học')
$ git add models/course.py
$ git commit -m "[MERGE] vinc_course: chọn nhãn số giờ học"
[main 45067cb] [MERGE] vinc_course: chọn nhãn số giờ học

A more readable display with zdiff3

The default style shows only the two versions, so you sometimes cannot tell what the line looked like originally. The git config documentation describes the diff3 and zdiff3 styles that add the common ancestor between the branches (after the ||||||| marker), letting you see what each side changed relative to the original. Turn it on with git config --global merge.conflictStyle zdiff3:

$ git config merge.conflictStyle zdiff3
$ git merge feature/hours-label
Auto-merging models/course.py
CONFLICT (content): Merge conflict in models/course.py
Automatic merge failed; fix conflicts and then commit the result.
$ grep -n -A8 "<<<<<<<" models/course.py
9:<<<<<<< HEAD
10-    hours = fields.Integer(string='Tổng số giờ')
11-||||||| 4fb4729
12-    hours = fields.Integer(string='Số giờ')
13-=======
14-    hours = fields.Integer(string='Số giờ học')
15->>>>>>> feature/hours-label
$ git merge --abort

Reading the output above: the original is “Số giờ”, main changed it to “Tổng số giờ” and the other branch to “Số giờ học”. Knowing the original, you quickly see both sides trying to say the same thing in different words, and you only need to pick one name.

Besides editing by hand, you can use a visual tool. Most modern editors (VS Code, JetBrains IDEs) show a conflict as three panes: yours, incoming and the result, with buttons to pick each part. Git also has git mergetool, which opens the merge tool you declared in the merge.tool setting. Any tool only helps you choose faster; deciding what to keep is still your job, so read the final result carefully before git add.

The delete versus modify kind of conflict

Not every conflict leaves markers in a file. When one branch deletes a file while the other still modifies it, Git reports modify/delete and leaves the modified version in the working tree. git status -s shows the letter pair UD (deleted on the merged-in side). You choose: keep the file with git add, drop it with git rm, then commit:

$ git switch -c feature/rm-notes
Switched to a new branch 'feature/rm-notes'
$ git rm -q NOTES.md
$ git commit -qm "[REM] vinc_course: bỏ ghi chú"
$ git switch main
Switched to branch 'main'
$ echo "thêm một dòng" >> NOTES.md
$ git commit -qam "[IMP] vinc_course: bổ sung ghi chú"
$ git merge feature/rm-notes
CONFLICT (modify/delete): NOTES.md deleted in feature/rm-notes and modified in HEAD.  Version HEAD of NOTES.md left in tree.
Automatic merge failed; fix conflicts and then commit the result.
$ git status -s
UD NOTES.md
$ git rm -q NOTES.md
$ git commit -m "[MERGE] vinc_course: bỏ ghi chú"
[main bf19726] [MERGE] vinc_course: bỏ ghi chú

Reducing conflicts through how you work

  • Bring main into your branch often (part 3) so conflicts stay small and appear early.
  • Small merge requests and short-lived branches (part 5): less time for others to touch the same place.
  • One item per line in the data or depends lists: two changes at different positions merge automatically instead of colliding as they do when the whole list sits on one line.
  • Tell each other when both of you edit a big shared file such as the main view or a translation file.

Common beginner mistakes

  • Leaving conflict markers in the file. If you forget to remove them, the file breaks at once. With Python the compiler reports a syntax error right on the marker line; git diff --check also warns about a leftover conflict marker before you commit:
$ python3 -m py_compile __manifest__.py
  File "__manifest__.py", line 5
    <<<<<<< HEAD
    ^^
SyntaxError: invalid syntax
$ git diff --check
__manifest__.py:5: leftover conflict marker
__manifest__.py:7: leftover conflict marker
__manifest__.py:9: leftover conflict marker
$ git commit -m "merge"
U	__manifest__.py
error: Committing is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'
hint: as appropriate to mark resolution and make a commit.
fatal: Exiting because of an unresolved conflict.
  • The example above also shows a second mistake: running git commit before git add-ing the fixed file is refused with “Committing is not possible because you have unmerged files”. Run git add to say it is resolved.
  • Picking a side at random to move on. Silently losing a colleague's change is the hardest mistake to notice because nothing reports it. When unsure, ask the author of the other side's commit (see git log --merge or git blame in part 12).
  • Panicking and deleting the whole repo. You almost never need to: git merge --abort puts everything back, and committed data always remains in .git.

Summary

  • A conflict = both sides edit the same lines (or one edits while the other deletes); Git stops and waits for you.
  • Markers: <<<<<<< HEAD (your side) · ======= · >>>>>>> branch (the merged side).
  • Edit → remove markers → check → git add → git commit; if unsure, git merge --abort.
  • git diff --check catches leftover markers; merge.conflictStyle zdiff3 shows the original too.

You can now cope when things collide. What about when you yourself slip: a bad edit, commit or push? Part 7 introduces the undo toolkit: restore, reset, revert and reflog to rescue even commits you thought were lost.

Frequently asked questions

What is a merge conflict, and is it a failure? ▾
Nothing is broken. It is the moment Git cannot decide which version is right, usually because two branches edited the same lines or one deleted a file the other modified. Git stops the merge, marks the disputed spot and waits for you.
How do I cancel a conflicted merge and start over? ▾
Run git merge --abort. It returns the repo to its state before the merge, as long as you have not committed the merge result.
Why does git commit say unmerged files after I edited the file? ▾
Because you have not git add-ed the fixed file. Git treats a conflict as resolved only once the file is staged with git add (or git rm for a deleted file).
How do I know a conflict marker was left in my code? ▾
Run git diff --check: Git warns about a leftover conflict marker with line numbers. For Python files, py_compile or simply running the program also reports a syntax error on the marker line.
