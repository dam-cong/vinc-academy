What Is Git? Install and First-Time Setup for Devs

The first part of the Git series: tell Git from GitLab, install it, set your name and email, understand the three areas, then create a repo and the first commit for the vinc_course module.

Updated: October 16, 2026 9 min read Vinc Academy Team

In short

Git records the history of your source code on your own machine; GitLab and GitHub are where a whole team shares and reviews it. This part takes you from an empty machine to the first commit of the vinc_course repository: installing Git, setting your name and email, creating a repo with git init, understanding the three areas (working tree, staging, repository) and looking things up with git help. Every command here was really run on Git 2.47.

What Git is and why every team uses it

Picture your vinc_course module with twenty Python and XML files. Today you change a model, tomorrow a view, next week a colleague adds a report. With plain folders you end up with vinc_course_final, vinc_course_final_2 and vinc_course_really_final, and when a bug appears nobody knows who changed which line. Git solves exactly that: each time you commit it snapshots the whole project together with the author, the time and a message that explains the change.

Git is a distributed version control system: every machine keeps a full copy of the history, so you can read the log, compare changes or create branches even offline. You only need the network to sync with colleagues. In a company this comes with a familiar routine: everyone works on their own branch, pushes it to GitLab, opens a merge request for review, and only then merges into the main branch. The 12 parts of this series unfold that whole routine; this one lays the foundation.

NameWhat it isYou use it to
GitA command-line program installed on your machineCommit, branch, read history, merge changes
GitLabA hosting service for team repositories with merge requests, permissions and CIShare code, review it, run automatic checks
GitHubA service similar to GitLab (it calls them pull requests)Same purpose; the Git commands on your side are identical

Remember that Git does not depend on GitLab. You can use Git entirely on your machine and connect it to GitLab or GitHub later. This series uses GitLab because many companies run an internal GitLab for client code; every Git command works unchanged with GitHub.

Installing Git

Install it once and use it forever. Following Git's official download page, each operating system has a familiar route:

SystemHow to install
WindowsDownload Git for Windows from git-scm.com, keep the default options, then use Git Bash or the VS Code terminal
Ubuntu / Debiansudo apt install git
macOSbrew install git, or run git once and let the system offer the Xcode Command Line Tools

After installing, open a terminal and run git --version. This series was tested on Git 2.47; the modern commands git switch and git restore arrived in 2.23, so any version from 2.30 up is fine.

First-time setup: name, email, default branch

Every commit records its author, so the first job is to tell Git who you are. Use the same email you registered on GitLab so your commits are linked to your account. Two other settings are worth doing now: the default branch of new repos (main) and the editor Git opens when it needs a longer message.

$ git --version
git version 2.47.3
$ git config --global user.name "Nguyễn Văn An"
$ git config --global user.email "an.nguyen@example.com"
$ git config --global init.defaultBranch main
$ git config --global core.editor "code --wait"
$ git config --global --list --show-origin
file:~/.gitconfig	user.name=Nguyễn Văn An
file:~/.gitconfig	user.email=an.nguyen@example.com
file:~/.gitconfig	init.defaultbranch=main
file:~/.gitconfig	core.editor=code --wait

The --global flag stores the value in the .gitconfig file in your home folder (the output above shows the source thanks to --show-origin). Git has two more levels, and the later one overrides the earlier:

LevelFlagStored inApplies to
system--systemThe system config fileEvery user on the machine
global--global~/.gitconfigAll your repos
local--local (default).git/configOnly the current repo

The local level is handy when one laptop serves both company and personal projects: keep the company email globally, then in a personal repo run git config user.email "you@example.com" (no flag) so only that repo uses another address.

Three areas: understand them once, use them forever

Most beginner confusion comes from not telling apart the three places a file can live:

  • The working tree is the files you see and edit every day.
  • The staging area (also called the index) is a shopping basket of the changes you picked for the next commit with git add.
  • The local repository is the commit history, stored in the hidden .git folder. Delete .git and the whole history is gone, so do not tinker inside it.

Separating staging from committing sounds redundant, yet it is a big advantage: you can edit five files and commit only the two that belong together, keeping each commit about one thing. The fourth place, the remote, appears when you connect the repo to GitLab in part 4.

Creating the first repo for vinc_course

git init turns a folder into a repo by creating a .git folder inside. git status is the command you will type most: it always tells you which branch you are on and what is waiting for attention.

$ mkdir vinc_course
$ cd vinc_course
$ git init
Initialized empty Git repository in ~/work/vinc_course/.git/
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
$ ls -A
.git
$ cat .git/HEAD
ref: refs/heads/main

The .git/HEAD file says the current branch is main, just as we set in init.defaultBranch. Now the smallest possible life cycle: create a file, stage it, commit it.

$ echo "# vinc_course" > README.md
$ git status -s
?? README.md
$ git add README.md
$ git status -s
A  README.md
$ git commit -m "Thêm README cho vinc_course"
[main (root-commit) dce25f0] Thêm README cho vinc_course
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git log --oneline
dce25f0 Thêm README cho vinc_course
$ git status
On branch main
nothing to commit, working tree clean

Read the two git status -s outputs closely: ?? means the file is untracked, and A in the first column means it is already in staging. A value such as dce25f0 is the short identifier of the commit; on your machine it will differ because it depends on time and author.

Looking things up when you forget

Nobody remembers every Git option, veterans included. Two habits save you: git help <command> (or git <command> --help) opens the full manual page, while git <command> -h prints the usage right in the terminal. If you mistype a command, Git suggests similar ones with an “is not a git command” message.

To type less, set an alias for commands you use often. The example below makes git st a short form of git status, then uses git config --get and --show-origin to see where a value comes from:

$ git config --global alias.st "status -sb"
$ git st
## main
$ git config --get user.name
Nguyễn Văn An
$ git config --show-origin user.email
file:~/.gitconfig	an.nguyen@example.com

Common beginner mistakes

  • Committing with the wrong identity. If you have not configured it, many machines still commit because Git guesses a name and email from the system account, but it prints “Your name and email address were configured automatically based on your username and hostname. Please check that they are accurate.” Do not ignore that line. To fix the commit you just made, run git commit --amend --reset-author after setting the right user.name and user.email.
  • Seeing “Author identity unknown”. When Git cannot guess (or you turned on user.useConfigOnly to forbid guessing), the commit is refused with the message below. Simply run the two git config commands it suggests.
$ git commit -m "Thêm README"
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: no email was given and auto-detection is disabled
  • A repo inside a repo. Running git init inside a folder that already belongs to another repo creates a nested repo and makes git status confusing. Check with git status before you init.

Summary

  • Git keeps history on your own machine; GitLab and GitHub are only where you share and review.
  • Configure once: user.name, user.email, init.defaultBranch; local overrides global.
  • Three areas: working tree → staging (git add) → repository (git commit); add the remote when you push to GitLab.
  • git status always tells you the next step; git help and -h let you look things up yourself.

You now have a repo and a first commit. The next part covers the daily loop: edit files, see differences with git diff, pick what to commit, read git log and keep files that should never enter the repo out with .gitignore.

Frequently asked questions

How is Git different from GitLab? ▾
Git is a program installed on your machine that records the history of your source code. GitLab is a hosting service for team repositories that adds merge requests, permissions and CI. You can use Git fully without GitLab; GitHub is a similar service to GitLab.
Do I have to set user.name and user.email? ▾
Every commit records the author name and email, so set them right away. If you have not, many machines still commit because Git guesses from the system account and prints a warning; if user.useConfigOnly is on or Git cannot guess, the commit is refused with an Author identity unknown message.
Should the default branch be main or master? ▾
Both work; Git lets you choose with init.defaultBranch. Many teams use main and GitLab also names new projects main, so run git config --global init.defaultBranch main to match your team.
What is the staging area for? ▾
Staging (the index) is where you pick the changes that go into the next commit with git add. It lets you edit many files yet commit only the related ones, keeping every commit about one thing.
