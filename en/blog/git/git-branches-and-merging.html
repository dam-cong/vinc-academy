Git Branch and Merge: Work in Parallel Without Clashes

Part 3 creates a branch for each feature of the vinc_course module, merges them back with git merge (fast-forward and merge commit), cleans up finished branches and handles two common mistakes: switching with unfinished edits and detached HEAD.

Updated: October 16, 2026 11 min read Vinc Academy Team

In short

A branch is a lightweight pointer to a commit, so a new branch appears almost instantly and removing it costs just as little. Every team agrees on one branch per feature so that one person's unfinished work cannot break another's. This part uses git switch -c to create branches for new vinc_course fields, merges them back with git merge (fast-forward and merge commit), deletes finished branches and handles two common situations: switching with unfinished edits and detached HEAD.

What a branch is and why one branch per task

Imagine the team has three jobs running: adding a price field, adding a course level and fixing docs. If all three commit to one single line, an unfinished job leaks into the others and you cannot release only the finished one. Git answers with branches: each job gets its own line of history starting from the same point, and when it is done you merge it back into the main branch.

Technically a branch is only a name attached to a commit. When you commit, the current branch name moves to the new commit. HEAD is the pointer telling you which branch you are on. Because nothing is copied, creating a branch takes under a second no matter how big the repo is.

CommandWhat it does
git branchList local branches; the * marks the current one
git branch -aAlso list remote branches (part 4)
git switch <nhánh>Move to an existing branch
git switch -c <nhánh>Create a new branch from here and move to it
git merge <nhánh>Merge that branch into the current one
git branch -d <nhánh>Delete a merged branch (safe)
git branch -m <mới>Rename the current branch

You can see this for yourself: the .git/HEAD file holds the current branch name, and git rev-parse shows the commit a branch name points to.

$ cat .git/HEAD
ref: refs/heads/main
$ git rev-parse --short main
58544f6
$ git branch -v
* main 58544f6 Merge branch 'feature/course-code'

Since Git 2.23 the commands git switch (change branch) and git restore (restore files) split up the many jobs of git checkout. Older guides still use git checkout and it still works, but this series uses the new commands because their names say what they do.

Creating branches and moving between them

A common convention is to name branches by kind of work: feature/ for features, fix/ for bug fixes. We create a branch for the price field, commit a change, then go back to main. Watch the two grep calls: the file content really changes with the branch you stand on.

$ git branch
* main
$ git switch -c feature/course-price
Switched to a new branch 'feature/course-price'
$ git branch
* feature/course-price
  main
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường học phí"
[feature/course-price 3d09a30] [IMP] vinc_course: thêm trường học phí
 1 file changed, 1 insertion(+)
$ git log --oneline --graph --all
* 3d09a30 [IMP] vinc_course: thêm trường học phí
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git switch main
Switched to branch 'main'
$ grep -c price models/course.py
0
$ git switch feature/course-price
Switched to branch 'feature/course-price'
$ grep -c price models/course.py
1

The --graph view shows the new branch one commit ahead of main. The next step is to merge it into main.

Two small tips speed you up. First, git switch - returns to the branch you just left, handy when hopping between two branches. Second, git switch -c <name> <start-point> creates a branch from another commit or branch instead of from where you stand, as with main~2 later on. Remember a branch always starts where you point it, so move to an up-to-date main before creating a new feature branch.

Merging: fast-forward and merge commits

git merge always runs from the branch that receives the changes: you stand on main and name the branch to bring in. There are two outcomes depending on the shape of history. If main has no new commits since the branch split off, Git just slides the main pointer forward: a fast-forward, no new commit.

$ git switch main
Switched to branch 'main'
$ git merge feature/course-price
Updating 47905cb..3d09a30
Fast-forward
 models/course.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline --graph
* 3d09a30 [IMP] vinc_course: thêm trường học phí
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git branch -d feature/course-price
Deleted branch feature/course-price (was 3d09a30).
$ git branch
* main

A more realistic case: while you work on the level branch a colleague commits to main. The two histories went separate ways, so Git creates a merge commit with two parents to join them. The diagram at the top is exactly this case.

$ git switch -c feature/course-level
Switched to a new branch 'feature/course-level'
$ echo "    level = fields.Selection([('basic', 'Cơ bản'), ('adv', 'Nâng cao')])" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường cấp độ"
[feature/course-level 82624ed] [IMP] vinc_course: thêm trường cấp độ
 1 file changed, 1 insertion(+)
$ git switch main
Switched to branch 'main'
$ echo "# vinc_course" > README.md
$ git add README.md
$ git commit -m "[ADD] vinc_course: README"
[main e26c754] [ADD] vinc_course: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git merge feature/course-level
Merge made by the 'ort' strategy.
 models/course.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline --graph
*   f2e2ab5 Merge branch 'feature/course-level'
|\  
| * 82624ed [IMP] vinc_course: thêm trường cấp độ
* | e26c754 [ADD] vinc_course: README
|/  
* 3d09a30 [IMP] vinc_course: thêm trường học phí
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git branch --merged
  feature/course-level
* main
$ git branch -d feature/course-level
Deleted branch feature/course-level (was 82624ed).

Read the graph: the second star on the left is the README commit on main, the branch on the right is the level commit, and the top line is the merge commit joining both. Because the two changes touch different files (or different lines) Git can merge them by itself; when they touch the same line you get a conflict, the subject of part 6. git branch --merged lists branches already contained in the current one, meaning they are safe to delete.

Many teams want a merge commit every time so history records “when this feature was merged”, even when a fast-forward is possible. The --no-ff flag does exactly that:

$ git switch -c feature/course-code
Switched to a new branch 'feature/course-code'
$ echo "    code = fields.Char(string='Mã khóa')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm mã khóa học"
[feature/course-code 303f5c8] [IMP] vinc_course: thêm mã khóa học
 1 file changed, 1 insertion(+)
$ git switch main
Switched to branch 'main'
$ git merge --no-ff feature/course-code
Merge made by the 'ort' strategy.
 models/course.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline --graph -n 4
*   58544f6 Merge branch 'feature/course-code'
|\  
| * 303f5c8 [IMP] vinc_course: thêm mã khóa học
|/  
*   f2e2ab5 Merge branch 'feature/course-level'
|\  
| * 82624ed [IMP] vinc_course: thêm trường cấp độ
$ git branch -d feature/course-code
Deleted branch feature/course-code (was 303f5c8).

Cleaning up after the work is done

A merged branch has no more value, so delete it to keep the list tidy. git branch -d deletes only merged branches and refuses if you would lose commits. To drop an experiment for good use -D (capital) to force it, but be sure you no longer need those commits.

$ git switch -c experiment/video
Switched to a new branch 'experiment/video'
$ echo "# thử video" >> README.md
$ git commit -am "[IMP] vinc_course: thử nhúng video"
[experiment/video 9a15432] [IMP] vinc_course: thử nhúng video
 1 file changed, 1 insertion(+)
$ git switch main
Switched to branch 'main'
$ git branch -d experiment/video
error: the branch 'experiment/video' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D experiment/video'
hint: Disable this message with "git config advice.forceDeleteBranch false"
$ git branch -D experiment/video
Deleted branch experiment/video (was 9a15432).

Habits that keep branches tidy

  • Short-lived branches. The longer a branch lives the further it drifts from main, and the more painful the merge. Slice work so branches live days, not weeks.
  • One purpose per branch. Do not bundle “add price field” with “fix the report”; undoing or reviewing them separately becomes hard.
  • Never commit straight to main. Most teams protect the main branch and allow changes only through merge requests (part 5).
  • Catch up with main often. When main gets new changes, bring them into your branch so conflicts show up early:
$ git switch -c feature/course-sync main~2
Switched to a new branch 'feature/course-sync'
$ echo "ghi chú đồng bộ" > SYNC.md
$ git add SYNC.md
$ git commit -m "[ADD] vinc_course: ghi chú đồng bộ"
[feature/course-sync e6ebc3c] [ADD] vinc_course: ghi chú đồng bộ
 1 file changed, 1 insertion(+)
 create mode 100644 SYNC.md
$ git merge main
Merge made by the 'ort' strategy.
 models/course.py | 2 ++
 1 file changed, 2 insertions(+)
$ git log --oneline --graph -n 1
*   fd027f5 Merge branch 'main' into feature/course-sync
|\  
$ git switch main
Switched to branch 'main'
$ git branch -D feature/course-sync
Deleted branch feature/course-sync (was fd027f5).

This time git merge main runs from the feature branch, so the feature branch is the receiving side. It does not touch main, which makes it safe. Part 8 shows the alternative, rebase.

Common beginner mistakes

  • Switching branches with unfinished edits. If the file you edited differs between the two branches, Git refuses to protect your work:
$ git switch -c feature/x
Switched to a new branch 'feature/x'
$ echo "    x = fields.Char()" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm trường x"
$ git switch main
Switched to branch 'main'
$ echo "    y = fields.Char()" >> models/course.py
$ git switch feature/x
error: Your local changes to the following files would be overwritten by checkout:
	models/course.py
Please commit your changes or stash them before you switch branches.
Aborting
  • Three ways out: commit it, git stash (part 9), or discard it with git restore (part 7). Do not force the switch with -f before you understand what it throws away.
  • Falling into “detached HEAD”. Running git checkout <commit> or git switch --detach puts HEAD on a commit that is on no branch. Commits made now are easy to lose. To keep them run git switch -c <branch-name>; to go back run git switch -:
$ git stash -q
$ git checkout HEAD~1 2>&1 | head -5
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
$ git switch -
Previous HEAD position was 847d6e3 [ADD] vinc_course: khung module và model vinc.course
Switched to branch 'feature/course-price'
  • Spaces in a branch name. Branch names cannot contain spaces; join words with hyphens (and prefer lowercase ASCII so they are easy to type in a terminal):
$ git switch -c "feature/course price"
fatal: 'feature/course price' is not a valid branch name
hint: See `man git check-ref-format`
hint: Disable this message with "git config advice.refSyntax false"
$ git switch -c feature/course-price
Switched to a new branch 'feature/course-price'
  • Committing on main by mistake. Forgetting to create a branch and committing straight to main is common; look at the * in git branch or the first line of git status before committing. Part 7 shows the rescue.

Summary

  • A branch is a light pointer; one branch per task, named feature/..., fix/....
  • git switch -c creates and moves; file content follows the branch.
  • git merge runs from the receiving branch: fast-forward for straight history, merge commit when diverged; --no-ff always forces a merge commit.
  • -d deletes merged branches, -D forces it.
  • With unfinished edits, commit or stash before changing branch.

Frequently asked questions

What is a Git branch, and does it copy the code? ▾
A branch is just a name pointing at a commit; no files are copied. When you commit, the current branch name moves to the new commit. That is why branches are created and removed almost instantly.
How do fast-forward and merge commits differ? ▾
A fast-forward happens when the receiving branch has no new commits: Git just moves the branch pointer ahead and creates no commit. If the two branches went separate ways, Git creates a merge commit with two parents. The --no-ff flag always forces a merge commit.
How is git switch different from git checkout? ▾
git switch (since Git 2.23) only changes and creates branches; git restore restores files. Both were split out of git checkout, which used to do too many jobs. git checkout still works as before.
When should I use git branch -D instead of -d? ▾
-d deletes only merged branches and refuses if you would lose commits. -D forces deletion regardless of merge state; use it when you are sure you want to drop an experimental branch for good.
