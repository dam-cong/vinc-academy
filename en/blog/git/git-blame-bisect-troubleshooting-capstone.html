Git Blame, Bisect and a Capstone Project for Odoo Teams

The final part of the Git series: use git blame, git log -S and git bisect run to find the commit that broke things, then run a whole cycle from issue and merge request to tag, hotfix and cherry-pick, with a cheat-sheet of all 12 parts.

Updated: October 16, 2026 14 min read Vinc Academy Team

In short

The final part finds “who and which commit broke it”, then joins the whole series into one complete working cycle. git blame shows which commit last changed each line, git log -S finds the commit that added or removed a piece of text, and git bisect run binary-searches the culprit commit by itself. The capstone really runs the workflow: take an issue, branch, commit, rebase, push, merge request, tag, hotfix and cherry-pick back to main, with a cheat-sheet of all 12 parts.

Tracing line by line: git blame and git log -S

When a function returns a wrong result the first question is “since when is this line here, and why?”. git blame prints every line with the commit, author and time of its latest change; -L limits it to a line range or a function name. In this sample repo price_per_hour originally divided the price by the hours, but a colleague “optimised” it. Blame points straight at it: the return line belongs to Binh's commit while the def line is still An's.

If you do not know where the line is, search by content. git log -S"text" (the “pickaxe” style) lists the commits that changed how many times that text occurs, meaning they added or removed it:

Blame reports the last commit that touched a line, which is not always the root of the problem: if someone only reformatted it, blame points at them. The -M and -C flags trace lines relocated or duplicated across files, and --ignore-rev lets you skip a bulk formatting commit. Use blame to understand context and ask the right person, not to assign blame.

Binary-searching the culprit: git bisect

When you know an older version worked (tag v1.0.0) and the current one is wrong, but dozens of commits lie between them, git bisect finds the first bad commit by binary search: at each step it takes you to the commit halfway through the suspect range, you say “good” or “bad”, and the range halves. 1,000 commits take only about 10 steps. You can press good/bad yourself or hand it a script: per the documentation, git bisect run calls the script at each step and reads exit code 0 as good, 1–127 (except 125) as bad, 125 as “cannot test this commit, skip it”, and any other code aborts the process.

Our test script checks exactly one thing: a price of 4,500,000 over 24 hours must equal 187,500. It lives outside the repo so bisect can switch commits without losing it:

python3 -c "import sys;sys.path.insert(0,'models');from utils import price_per_hour;sys.exit(0 if price_per_hour(4500000, 24) == 187500 else 1)"
$ git bisect start
status: waiting for both good and bad commits
$ git bisect bad
status: waiting for good commit(s), bad commit known
$ git bisect good v1.0.0
Bisecting: 3 revisions left to test after this (roughly 2 steps)

In just three checks across seven commits Git concludes 8cff483 is the first bad commit, and we read it with git show. Remember git bisect reset to return to your working branch:

$ git show --stat --oneline 8cff483
8cff483 [IMP] vinc_course: tối ưu price_per_hour
 models/utils.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

For bisect to be effective, every commit must work on its own, exactly the “small, consistent steps” advice of the gitworkflows document from part 10. A history full of half-broken commits forces bisect to skip many steps.

Capstone: one complete working cycle

Now we join the parts into a working day. An takes issue #21 “add a course code”, works on a dedicated branch, pushes to GitLab, the MR is approved and merged and the team tags 1.1.0; then a label problem is found in the running version so a hotfix 1.1.1 is made and brought back to main. The fastest way to learn is to rebuild the scenario yourself on a scratch repo. Five suggested exercises:

  • Create a bare repo to act as “GitLab” (git init --bare) and clone it twice to play both An and Binh.
  • Deliberately create a conflict in __manifest__.py and resolve it with both merge and rebase.
  • Write your own commit-msg hook and try skipping it with --no-verify.
  • Tag a release, branch a hotfix from it and cherry-pick it to the main branch.
  • Plant a bug in the middle of history and let git bisect run find it by itself.

When Git shows a strange error: four calm steps

  • Read the whole message, especially the hint: lines. Git often spells out the command to run, as you saw in earlier parts.
  • git status says where you are: which branch, whether a merge or rebase is in progress, which files await attention.
  • git log --oneline --graph --all gives the picture of history; add --decorate to see branches and tags.
  • Pause before any destructive command (reset --hard, clean -f, push --force). Create a backup branch, and if you slip use git reflog.

Common beginner mistakes

  • The bisect script cannot run at some commits. Importing the whole models package, for instance, drags in odoo and fails at once. When the script ends with a generic error code Git counts that commit as “bad” and draws a wrong conclusion. Test the script on a known-good and a known-bad commit first, and return 125 when it cannot test.
  • Forgetting git bisect reset. You are still in a bisect session (a detached HEAD). Run git bisect reset before carrying on.
  • Using blame to assign guilt. The last commit to touch a line is not necessarily the cause; read its git show and ask the author rather than jumping to conclusions.
  • Switching versions during bisect with unfinished edits. Commit or stash (part 9) before git bisect start so nothing is lost.

Summary of the whole series

  • Foundations: the three areas, small commits with good messages, .gitignore from the start.
  • Collaboration: short-lived branches, GitLab, merge requests, conflicts and rebase within the rules.
  • Safety: choose the right undo command, always keep the reflog and backup branches as a net.
  • Releasing: tags, hotfixes from tags, cherry-pick; hooks and CI so machines do the checking.
  • Tracing: blame, log -S and bisect to find causes instead of guessing.

Frequently asked questions

What is git blame for? ▾
git blame prints every line of a file with the commit, author and time of its latest change, helping you see when and why the line appeared. Use -L to limit lines or a function, and -M and -C to trace lines relocated or duplicated.
How does git bisect work? ▾
You mark one good and one bad commit; Git binary-searches the range between them, jumping to the halfway commit at each step for you to test, halving the range each time. With git bisect run script, Git runs your script at every step and reads the exit code as good or bad.
Which exit codes of a bisect script are special? ▾
Per the Git documentation: 0 means good, 1 to 127 (except 125) means bad, 125 means skip a commit that cannot be tested, and any other code aborts the bisect.
How do I find the commit that added or removed a piece of text? ▾
Use git log -S"text" (the pickaxe) to list the commits that changed how many times that text occurs; git log -G uses a regular expression. Then git show commit-id to read it.
