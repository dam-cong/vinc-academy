Git Stash, Cherry-pick and Tags: Hotfixes and Releases

Part 9 runs a real hotfix scenario: shelve unfinished work with git stash, branch from the live tag, tag the patch release, cherry-pick -x back to main and retrieve your work, on the vinc_course module.

Updated: October 16, 2026 13 min read Vinc Academy Team

In short

Three tools for three “mid-task” situations: stash shelves unfinished work so you can switch jobs, cherry-pick carries exactly one commit to another branch, tag marks a release. This part runs a real hotfix scenario: you are halfway through the price branch when a bug appears in the running 1.0.0; you shelve the work, branch a hotfix from the tag, tag 1.0.1, cherry-pick the fix back to main, then retrieve your unfinished work.

The Friday-afternoon hotfix story

Version 1.0.0 of vinc_course is live at the customer. You are halfway through the price field on your own branch when you are told the “Số giờ” label is misleading and needs an urgent fix. You cannot commit half-baked work, and you do not want an unfinished feature in the fix. This part's three tools handle each step:

JobTool
Shelve unfinished work, come back latergit stash
Know exactly which commit is runninggit tag
Fix starting from the released versionBranch from the tag
Bring the fix to main without anything elsegit cherry-pick

Tags: marking a release

A tag is a fixed name attached to a commit, usually for version numbers. Unlike a branch it does not move when you commit. Git's documentation describes two kinds: annotated tags (made with -a) store a date, the tagger and a message, meant for releases; lightweight tags are just a name, meant for temporary markers. Name them after the version the manifest declares (the Odoo documentation recommends semantic versioning for the version field). Note that a plain git push does not push tags; push them explicitly, and check the remote with ls-remote:

$ git tag -a v1.0.0 -m "Phát hành 1.0.0"
$ git tag
v1.0.0
$ git show v1.0.0 --no-patch
tag v1.0.0
Tagger: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 10:17:00 2026 +0700

Phát hành 1.0.0

Author: Nguyễn Văn An <an.nguyen@example.com>

Stash: shelving unfinished work

git stash takes the uncommitted changes out of the working tree, stores them on a separate stack and returns the files to the latest commit. You can switch branches cleanly and come back to retrieve them. By default it shelves only tracked files: the newly created NOTE.md stays behind (add -u to include new files):

$ git switch -c feature/course-price
Switched to a new branch 'feature/course-price'
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ echo "ghi chú" > NOTE.md
$ git status -s
 M models/course.py
?? NOTE.md
$ git stash push -m "dở học phí"
Saved working directory and index state On feature/course-price: dở học phí
$ git status -s
?? NOTE.md
$ git stash list
stash@{0}: On feature/course-price: dở học phí
CommandWhat it does
git stash push -m "mô tả"Shelve with a recognisable name
git stash push -uInclude untracked files
git stash listList shelved entries
git stash show -pShow the latest entry's changes
git stash popApply and drop from the stack
git stash applyApply but keep the entry
git stash dropDelete an entry

Stash suits short gaps: minutes to a few hours. If the unfinished work will last until tomorrow, make a temporary commit ([WIP]) on your own branch and fold it later with interactive rebase as in part 8; a commit has a name and lives in history, whereas a stash is easy to forget. When a stash conflicts with newer changes, git stash branch <name> creates a new branch from the very commit you stashed on and applies the entry there, a tidy way out.

Hotfix: branching from a tag

Thanks to the tag, you branch exactly from the version that is running rather than from main (which has other commits by now). Fix, commit, tag 1.0.1 and push; whoever deploys just takes that tag:

$ git switch -c hotfix/1.0.1 v1.0.0
Switched to a new branch 'hotfix/1.0.1'
$ sed -i "s/Số giờ/Số giờ (giờ)/" models/course.py
$ git commit -qam "[FIX] vinc_course: ghi rõ đơn vị số giờ"
$ git tag -a v1.0.1 -m "Hotfix 1.0.1"
$ git push origin v1.0.1
To git@gitlab.example.com:vinc/vinc_course.git
 * [new tag]         v1.0.1 -> v1.0.1
$ git log --oneline -n 3 --decorate
1f85d3e (HEAD -> hotfix/1.0.1, tag: v1.0.1) [FIX] vinc_course: ghi rõ đơn vị số giờ
47905cb (tag: v1.0.0) [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course

Cherry-pick: carrying exactly one commit elsewhere

The fix must also reach main so the next release does not repeat the bug. Merging the hotfix branch into main works too, but when the branch holds other things you want exactly one commit. git cherry-pick <commit> applies that commit's change to the current branch as a new commit. The -x flag appends a “(cherry picked from commit …)” line so later readers can trace the source; the documentation recommends it when picking between two public branches (for example porting a bug fix back to an older release line):

$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ git cherry-pick -x hotfix/1.0.1
[main 938fa6a] [FIX] vinc_course: ghi rõ đơn vị số giờ
 Date: Mon Oct 12 12:09:00 2026 +0700
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline -n 3
938fa6a [FIX] vinc_course: ghi rõ đơn vị số giờ
6305374 [ADD] vinc_course: thêm extra
47905cb [IMP] vinc_course: thêm trường số giờ
$ git log -1 --format=%B
[FIX] vinc_course: ghi rõ đơn vị số giờ

(cherry picked from commit 1f85d3e6f42ba67551050559c96ab62364d8feed)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   6305374..938fa6a  main -> main

Cherry-pick makes a new commit (different hash), so the -x line is the only link to the original. If the changes collide you meet a conflict as in part 6 and finish with git cherry-pick --continue, or cancel with --abort. You can pick a range: git cherry-pick A..B.

Now back to the unfinished work. git stash pop restores the changes and removes the entry from the list, but according to the documentation, if applying runs into conflicts the entry is not removed so you lose nothing:

$ git switch feature/course-price
Switched to branch 'feature/course-price'
$ git stash pop
On branch feature/course-price
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   models/course.py

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	NOTE.md

no changes added to commit (use "git add" and/or "git commit -a")
Dropped refs/stash@{0} (8e6da6bf2eefeff625ca4a09a60da21474acd05b)
$ git stash list

Listing, visiting and deleting tags

$ git tag -l "v1.*"
v1.0.0
v1.0.1
$ git describe
v1.0.0-2-g938fa6a
$ git switch --detach v1.0.0
HEAD is now at 47905cb [IMP] vinc_course: thêm trường số giờ
$ git switch -
Your branch is up to date with 'origin/main'.
Previous HEAD position was 47905cb [IMP] vinc_course: thêm trường số giờ
Switched to branch 'main'
$ git tag -d v1.0.0
Deleted tag 'v1.0.0' (was 5b6f223)
$ git push origin --delete v1.0.0
To git@gitlab.example.com:vinc/vinc_course.git
 - [deleted]         v1.0.0
$ git tag
v1.0.1

git describe prints the nearest tag name (counting only annotated tags by default), handy for showing the running version. git switch --detach v1.0.0 lets you view the code exactly at that release without creating a branch; git switch - returns. Deleting a tag takes two places: locally with -d, on the remote with git push origin --delete. Avoid deleting and re-creating a published tag since others already have the old one. On GitLab admins can protect tag name patterns (protected tags) so only some roles may create them.

Choosing version numbers for tags

The Odoo manifest documentation asks that version follow semantic versioning: three numbers MAJOR.MINOR.PATCH. The convention lets customers and colleagues guess the size of a change from the number alone:

ChangeNew numberExample on vinc_course
PATCH1.0.0 → 1.0.1A label or small bug fix, no data structure change
MINOR1.0.1 → 1.1.0Add the price field, backward compatible
MAJOR1.1.0 → 2.0.0Rename a model or drop a field, data migration needed

A short release checklist

  • git switch main and git pull: make sure you are on the latest reviewed version.
  • Update version in __manifest__.py, run the tests and a trial upgrade on a test database.
  • Commit the version bump, then git tag -a vX.Y.Z -m "..." and git push origin vX.Y.Z.
  • Deploy by switching to the exact tag, not to a branch that keeps moving.
  • Record what changed for the customer (a changelog) together with the tag name.

Common beginner mistakes

  • Assuming git push pushed the tag. The tag example shows ls-remote empty until you run git push origin <tag> (or --tags to push every tag).
  • Forgetting you stashed. The shelved work sits in git stash list for a week and gets forgotten. Always give it a -m description and clear it early with pop or drop.
  • New files are not stashed. As in the example, NOTE.md stayed out. To shelve untracked files too use git stash push -u.
  • Fixing on main only to find the running version lacks it. Always branch the hotfix from the running version's tag, then bring it to main by cherry-pick or merge.
  • Cherry-picking many commits casually. Each copy gets its own hash so merging the two branches later may show “duplicate” changes. Cherry-pick only when you truly need that one change alone.

Summary

  • stash push -m / pop: shelve and retrieve unfinished work; add -u for new files.
  • Annotated tags for releases; remember to push tags explicitly.
  • Hotfix: branch from the running tag, tag again, then cherry-pick -x to main.
  • Conflict during cherry-pick: fix, add, --continue (or --abort).

You now have the technical tools. What a team still needs to move in step is conventions: naming branches, writing commit messages and choosing a branching strategy. That is the subject of part 10.

Frequently asked questions

When is git stash the right tool? ▾
When you are mid-task, do not want to commit yet but must switch branches now (an urgent fix, say). git stash push -m shelves uncommitted changes and git stash pop restores them. Add -u to include untracked files.
How does cherry-pick differ from merge? ▾
Merge brings a branch's whole history into the current branch. Cherry-pick applies the changes of one or a few chosen commits as new commits (different hashes). The -x flag records the original commit in the message.
What is the difference between annotated and lightweight tags? ▾
An annotated tag (git tag -a) stores a date, the tagger and a message, and is meant for releases. A lightweight tag is just a name pointing at a commit, meant for temporary markers. Some commands, such as git describe, skip lightweight tags by default.
Why does my tag not appear on GitLab? ▾
A plain git push usually does not send tags. Push explicitly with git push origin tag-name, or git push --tags for every tag. Check with git ls-remote --tags origin.
