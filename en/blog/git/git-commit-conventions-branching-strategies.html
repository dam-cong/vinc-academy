Git Commit Conventions and Branching Strategies for Odoo Teams

Part 10 settles three conventions that make history readable for the whole team: commit messages in Odoo's [TAG] module style, branch naming, and a lean branching strategy with a protected main, merge requests and release tags.

Updated: October 16, 2026 13 min read Vinc Academy Team

In short

Everyone has the same Git tools; what makes a team run smoothly is shared conventions. This part settles three: the commit message following Odoo's [TAG] module: description pattern (explain why), branch names (feature/, fix/, hotfix/, issue number) and a lean branching strategy for client modules (protected main, short-lived branches, merge requests, release tags). It includes git log --grep to show how conventions make history searchable.

Why conventions matter

Imagine a repo history made only of “update”, “fix”, “fixed again”, “final”. Three months later the customer asks “since when has the course code been mandatory?” and nobody can answer. Git history is only valuable when readable: it is the log that git log, git blame and git bisect (part 12) rely on. Git's own gitworkflows document sums it up in its first rule: cut your work into small logical steps, with every commit consistent, working on its own and passing the tests. That makes review easier and history more useful for later tracing.

The commit message convention, Odoo style

Odoo's Git guidelines describe a message with four parts: tag, module name, short header and full description. The pattern is [TAG] module: one short sentence, ideally under 50 characters, then a blank line and a longer description, ending with references such as Closes #14 or Fixes #14. Use the module's technical name (vinc_course) because the display name can change over time. The tags according to the documentation:

TagUsed for
[ADD]Adding a new module or component
[IMP]Improvements and incremental changes
[FIX]Bug fixes
[REF]Refactoring, heavy rewrites
[REM]Removing dead code, views or modules
[REV]Reverting a commit
[MOV]Moving files (without changing content)
[MERGE]Merge commits
[REL]Release commits
[I18N]Translation file changes
[PERF] / [CLN] / [LINT]Performance / cleanup / linting

The subtlest point is that the header should complete the sentence “this commit will…”: [IMP] vinc_course: add a course code reads as “this commit will add a course code”. The description explains why, since the “what” is already in the diff. Let us make such a commit:

$ echo "    code = fields.Char(string='Mã khóa')" >> models/course.py
$ git commit -aq -m "[IMP] vinc_course: thêm mã khóa học" -m "Phòng đào tạo tra cứu khóa theo mã nên mỗi khóa cần một trường mã riêng." -m "Closes #14"
$ git log -1
commit ca324bbdd38a5a698d7573fc962ebddea73a1975
Author: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 10:10:00 2026 +0700

    [IMP] vinc_course: thêm mã khóa học
    
    Phòng đào tạo tra cứu khóa theo mã nên mỗi khóa cần một trường mã riêng.
    
    Closes #14

Each -m adds a paragraph, so the command above creates the header, a paragraph of reasoning and a Closes #14 line (GitLab uses it to close the issue on merge, part 5). For convenience you can have Git open a template whenever you commit without -m, using the commit.template setting:

$ git config --global commit.template ~/.gitmessage
$ git config --get commit.template
~/.gitmessage
$ cat ~/.gitmessage
[TAG] module: tóm tắt thay đổi

Vì sao cần thay đổi (WHY).

Closes #

A convention pays off immediately in searching. Because headers start with a tag, you can filter all bug fixes with --grep, look at the history of just the models/ folder or count each person's contributions:

$ git log --oneline
4fa042a [REF] vinc_course: tách hàm tiện ích
3609b42 [ADD] vinc_course: README
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
47905cb [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git log --oneline --grep='^\[FIX\]'
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
$ git log --oneline -- models/
4fa042a [REF] vinc_course: tách hàm tiện ích
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
47905cb [IMP] vinc_course: thêm trường số giờ
847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git shortlog -sn --no-merges HEAD
     6	Nguyễn Văn An

Two more pieces of advice from the Odoo documentation: avoid one commit touching several modules at once (hard to revert module by module), and avoid vague headers such as “bugfix” or “improvements”.

One more benefit: writing a changelog becomes almost free. Suppose v1.0.0 was released at the second commit of the history above; everything after it is the content of the next release, and thanks to the tags you can single out the bug fixes to tell the customer:

$ git tag -a v1.0.0 -m "Phát hành 1.0.0" HEAD~4
$ git log --oneline v1.0.0..HEAD
4fa042a [REF] vinc_course: tách hàm tiện ích
3609b42 [ADD] vinc_course: README
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm
ca324bb [IMP] vinc_course: thêm mã khóa học
$ git log --oneline v1.0.0..HEAD --grep='^\[FIX\]'
ff4824e [FIX] vinc_course: nhãn số giờ gây hiểu nhầm

The syntax v1.0.0..HEAD means “commits in HEAD that are not in v1.0.0”. Together with release tags (part 9) it is how a team answers “what differs from the previous version?” in seconds.

To keep each commit about one thing even when you changed several things in the same file, use git add -p (--patch): Git shows each changed chunk (hunk) and asks whether to stage it, letting you split “add a field” from “tidy a comment” into two separate commits.

Branch naming conventions

PrefixUsed forExample
feature/A new featurefeature/course-price
fix/A non-urgent bug fixfix/duplicate-code
hotfix/An urgent fix for the live versionhotfix/1.0.1
release/Preparing or maintaining a releaserelease/1.0
experiment/Throwaway experimentsexperiment/video
issue numberPer GitLab's documentation an issue-number prefix prefills the title and closes the issue12-course-price

Write lowercase, join words with hyphens and avoid special characters. Git rejects some invalid names; git check-ref-format --branch lets you test beforehand:

$ git check-ref-format --branch feature/course-price
feature/course-price
$ git check-ref-format --branch "feature/course price"
fatal: 'feature/course price' is not a valid branch name
$ git check-ref-format --branch 12-course-price
12-course-price

A lean branching strategy for client modules

The gitworkflows document describes the full workflow of the Git project itself, with four integration branches (maint, master, next, seen), and it admits that a small team can skip much of it. For a team building Odoo modules for customers, a simple version is enough and easy to keep disciplined:

StrategyHow it worksFits
Trunk-based / simple GitLab styleOne protected main; short-lived feature branches merged through MRs; a tag for each releaseSmall to mid teams releasing often (recommended)
Add release branchesBranch release/x.y when several versions must be maintained; takes hotfixes onlyCustomers who stay on old versions
One branch per Odoo versionA branch per Odoo version (for example 20.0), features branch off itModules supporting several Odoo versions
A long-lived develop branchAn extra integration layer between features and mainOnly when truly needed; breeds big conflicts

GitLab lets a project choose its merge method, including fast-forward (no merge commit), so agree as a team: merge commits to see each MR clearly, or a straight history through squash or fast-forward. Whatever you pick, write it down in the README or contributing guide so newcomers need not guess.

A one-page team rulebook

  • No direct commits to main; every change goes through a merge request that at least one person reviews.
  • One branch, one purpose; live at most a few days; delete after merging (local and remote).
  • Commit messages follow [TAG] module: description and give the reason in the body.
  • Rebase only your own branches; never rewrite shared history (part 8).
  • Every release gets an annotated tag vX.Y.Z matching version in the manifest (part 9).
  • No secrets in commits; .gitignore exists from the first commit (part 2).

Common beginner mistakes

  • Meaningless messages. “update”, “fix bug” or “changed it again” tell nobody anything. Write a header that reads as a sentence and add the reason in the body.
  • One giant commit. Bundling a feature, a bug fix and cleanup into one commit makes review hard and prevents reverting parts separately. Split with git add file by file or git add -p.
  • Branches that live too long. A branch that lasts weeks drifts far from main and causes big conflicts at merge. Cut the work smaller and bring main in often.
  • Everyone with their own convention. One writes “Feature:”, another “feat:”, another “[IMP]”: searching becomes useless. Choose one pattern, document it and let tooling check it (part 11).
  • Branch names with spaces or odd characters. Git refuses with “is not a valid branch name” as the check-ref-format result above shows; use hyphens.

Summary

  • Commits: [TAG] module: description, short header, a body explaining why, ending with Closes #n.
  • Branches: prefixes feature/, fix/, hotfix/, release/; lowercase joined with hyphens.
  • Strategy: protected main, short-lived branches, merge requests, release tags and release branches when needed.
  • A convention only works when written down and checked by tooling.

Conventions in a document get forgotten under pressure. The next part turns them into something machines check for you: Git hooks that stop badly formatted commits or leaked passwords right on your machine, and GitLab CI that runs automatic checks for the Odoo module in every merge request.

Frequently asked questions

What does a good commit message look like? ▾
Following Odoo's Git guidelines: [TAG] module: a short one-sentence header (ideally under 50 characters), a blank line, then a description explaining why the change was made, ending with references such as Closes #14. The header should complete “this commit will…”.
How do the [ADD], [IMP], [FIX] and [REF] tags differ? ▾
[ADD] adds a new module or component, [IMP] is an incremental improvement, [FIX] fixes a bug and [REF] is a heavy refactor. There are also [REM] for removals, [REV] for reverts, [MOV] for moving files, [MERGE] for merge commits, [REL] for releases and [I18N] for translation files.
Which branching strategy suits a client's Odoo project? ▾
For small to mid teams start simple: one protected main branch, short-lived feature branches merged through merge requests, and a tag for every release. Add release branches or per-Odoo-version branches only when you must maintain several versions in parallel.
How do I see what a new release changes? ▾
Use git log --oneline v1.0.0..HEAD to list commits not in the old tag; add --grep="^\[FIX\]" to filter bug fixes. This is easy when commit messages follow the tag convention.
