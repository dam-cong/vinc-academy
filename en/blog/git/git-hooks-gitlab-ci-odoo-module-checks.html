Git Hooks and GitLab CI: Auto-Checks for Odoo Modules

Part 11 turns conventions into automatic checks: pre-commit and commit-msg hooks stop secrets, broken code and badly formatted messages on your machine, then .gitlab-ci.yml lints and tests the Odoo module in every merge request.

Updated: October 16, 2026 13 min read Vinc Academy Team

In short

A hook is a script Git runs by itself at fixed moments (before a commit, when the message is entered...) and blocks the action if the script exits non-zero. This part writes two real hooks for vinc_course: pre-commit stops secret files and syntactically broken Python, commit-msg enforces a [TAG] module: description header; and shares them with the team through core.hooksPath. Then comes the second layer of checks that runs on the server: GitLab CI with a .gitlab-ci.yml file that checks every merge request, including a step that runs Odoo's tests.

What a Git hook is

The conventions of part 10 only matter if everyone follows them, and people forget under pressure. Hooks let the machine remind you. According to the githooks documentation a hook is a program in Git's hooks folder (or a folder you set with core.hooksPath) that must be executable; the file name is the event name. A non-zero exit cancels the matching action.

HookRuns whenUse it to
pre-commitAhead of the commit itself, before any messageInspect files: syntax, secrets, conflict markers
commit-msgAfter the message is written; receives the message fileValidate or normalise the header
pre-pushBefore pushing to a remoteRun quick tests before reaching GitLab

Two points from the documentation: the first two hooks can be skipped with git commit --no-verify, and the .git/hooks folder is not committed so it does not travel with the repo to colleagues. To share them, keep the hooks in a folder of the repo (for example .githooks/) and have everyone run git config core.hooksPath .githooks once.

The pre-commit hook: stopping secrets and broken code

The hook below walks every staged file. On odoo.conf or .env it refuses; on a .py file it checks the syntax with Python; finally git diff --cached --check catches leftover conflict markers (part 6). Save it as .githooks/pre-commit and make it executable:

#!/bin/sh
# Chặn commit chứa file bí mật, dấu xung đột hoặc Python sai cú pháp
for f in $(git diff --cached --name-only --diff-filter=ACM); do
  case "$f" in
    odoo.conf|.env) echo "pre-commit: không được commit $f" >&2; exit 1 ;;
    *.py)
      err=$(python3 -c "import ast,sys; ast.parse(open(sys.argv[1], encoding='utf-8').read())" "$f" 2>&1) || {
        echo "pre-commit: lỗi cú pháp trong $f" >&2; echo "$err" | tail -n 1 >&2; exit 1; } ;;
  esac
done
git diff --cached --check || exit 1

The second hook checks the commit header against part 10's Odoo pattern. Git passes it the path of the file with the message ($1); we read only the first line. Merge and revert commits generated by Git are let through:

#!/bin/sh
# Tiêu đề phải dạng [TAG] module: mô tả (cho phép Merge/Revert tự sinh)
head -n 1 "$1" | grep -Eq '^(\[(ADD|IMP|FIX|REF|REM|REV|MOV|MERGE|REL|I18N|PERF|CLN|LINT)\] [a-z0-9_]+: .+|Merge |Revert )' || {
  echo "commit-msg: tiêu đề phải có dạng [TAG] module: mô tả" >&2
  echo "            ví dụ: [FIX] vinc_course: sửa nhãn số giờ" >&2
  exit 1; }

Enable the hooks for the repo and try them. The first commit below adds the two hooks themselves, and it already had to pass both checks:

$ git config core.hooksPath .githooks
$ git add .githooks
$ git commit -m "[ADD] vinc_course: hook kiểm tra commit"
[main 8bf05a8] [ADD] vinc_course: hook kiểm tra commit
 2 files changed, 17 insertions(+)
 create mode 100755 .githooks/commit-msg
 create mode 100755 .githooks/pre-commit

Watching the hooks block

Python with a syntax error is stopped before it becomes a commit; no commit is created and the file stays staged for you to fix:

$ echo "def broken(:" > models/bad.py
$ git add models/bad.py
$ git commit -m "[ADD] vinc_course: file lỗi"
pre-commit: lỗi cú pháp trong models/bad.py
SyntaxError: invalid syntax
$ git restore --staged models/bad.py
$ rm models/bad.py

Try committing a config file holding a password (it needed add -f because .gitignore would normally block it):

$ echo "admin_passwd = secret" > odoo.conf
$ git add -f odoo.conf
$ git commit -m "[ADD] vinc_course: cấu hình"
pre-commit: không được commit odoo.conf
$ git restore --staged odoo.conf
$ rm odoo.conf

Then a message that breaks the pattern. The commit-msg hook refuses, prints a correct example, and once you rewrite it properly the commit goes through:

$ echo "# ghi chú" >> models/course.py
$ git commit -am "update"
commit-msg: tiêu đề phải có dạng [TAG] module: mô tả
            ví dụ: [FIX] vinc_course: sửa nhãn số giờ
$ git commit -am "[IMP] vinc_course: ghi chú trong model"
[main 4062c7d] [IMP] vinc_course: ghi chú trong model
 1 file changed, 1 insertion(+)

Two ways a hook does not run: --no-verify and the executable bit

The --no-verify flag skips the hooks, reasonable for an urgent commit or a temporary one on your own branch. But precisely because anyone can do it, hooks cannot be the only gate:

$ echo "# thêm" >> models/course.py
$ git commit --no-verify -am "update"
[main 0f50aa1] update
 1 file changed, 1 insertion(+)

The second failure is subtler: if the hook file loses its executable bit, Git quietly ignores it and leaves just a hint line at the end. The commit succeeds even though the check never ran:

$ chmod -x .githooks/pre-commit
$ echo "# lần nữa" >> models/course.py
$ git add models/course.py
$ git commit -m "[IMP] vinc_course: thêm ghi chú"
[main 1f8b27e] [IMP] vinc_course: thêm ghi chú
 1 file changed, 1 insertion(+)
hint: The '.githooks/pre-commit' hook was ignored because it's not set as executable.
hint: You can disable this warning with `git config advice.ignoredHook false`.

The second layer: GitLab CI

According to GitLab's documentation you need two things to run CI/CD: a runner (the agent that executes jobs; GitLab.com provides them, while on a self-managed GitLab an admin registers them) and the .gitlab-ci.yml configuration in the repository root describing the jobs. When you push, GitLab creates a pipeline of jobs that run in stage order, and the result shows up in the merge request. The file for vinc_course has three jobs: a Python syntax check, a no-secrets check and a run of Odoo's tests:

stages: [lint, test]

lint-python:
  stage: lint
  image: python:3.12
  script:
    - python -m compileall -q .
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

no-secrets:
  stage: lint
  image: alpine:3
  script:
    - test ! -e odoo.conf
    - '! grep -rIn "admin_passwd" --include="*.py" --include="*.xml" .'
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

odoo-tests:
  stage: test
  image: registry.example.com/vinc/odoo-ci:20.0   # image nội bộ có sẵn Odoo 20 và PostgreSQL
  script:
    - odoo-bin -d ci_db -i vinc_course --test-tags /vinc_course --stop-after-init
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
KeywordMeaning (per the GitLab documentation)
stagesNames and order of stages; jobs in one stage run in parallel
imageThe Docker image the job runs in
scriptShell commands the runner executes; a non-zero exit fails the job
rulesConditions deciding whether the job is created; here only for merge request pipelines

The first two jobs use exactly the commands you can try on your machine before pushing, with the results below (no output and exit code 0 mean pass):

$ python3 -m compileall -q . ; echo "exit=$?"
exit=0
$ test ! -e odoo.conf && echo "không có odoo.conf"
không có odoo.conf
$ ! grep -rIn "admin_passwd" --include="*.py" --include="*.xml" . ; echo "exit=$?"
exit=0

The third job uses -i to install the module into the ci_db database, --test-tags /vinc_course to run only this module's tests (the [-][tag][/module][:class][.method] syntax from the Odoo testing documentation) and --stop-after-init so the process exits when done; a failing test fails the job. The image name above is an example: your team builds an image with Odoo 20 and PostgreSQL and substitutes it.

Once comfortable, you will meet a few more useful keywords in GitLab's keyword reference:

KeywordUsed for
before_scriptCommands executed ahead of every job's script, for example installing libraries
cacheKeep folders (such as .venv) between runs so pipelines are faster
artifactsAttach a job's output files, such as a test report
allow_failureLet a job fail without failing the pipeline (fits advisory checks)
variablesDefine environment variables for jobs, such as the test database name

A tip to keep everything consistent: put the check commands in one file inside the repo (for example scripts/check.sh) and have both the hook and the CI job call that same file. To add a rule you edit one place, and the result on your machine matches the one on GitLab.

Fitting it into the team workflow

StepHow
Hooks for newcomersAdd git config core.hooksPath .githooks to the README's “Getting started”
Protect mainMerge only through MRs (part 5) and require a green pipeline before merging
Module testsWrite tests with Odoo's TransactionCase (the testing part of the Odoo series) so the odoo-tests job has something to run
Grow graduallyStart with lint and secret checks, add tests and deployment once the team is used to it

Common beginner mistakes

  • A hook not running and nobody noticing. A missing executable bit, or a colleague who never set core.hooksPath. The example above shows Git printing only a hint line. Document the hook setup in the README and let the pipeline be the main safeguard.
  • Making --no-verify a habit. Every skip breaks the convention once. Use it only in emergencies and let the pipeline catch what slips by.
  • Hooks that are too slow. Running the whole test suite in pre-commit makes everyone avoid it. Keep hooks to a few seconds (syntax, secrets) and move the heavy work to CI.
  • A CI job stuck waiting. Usually no active runner is available for the project; GitLab's documentation shows how to check runners under Settings → CI/CD. Ask your company's GitLab admin.
  • Wrong indentation or quoting in YAML. YAML is sensitive to whitespace; a command starting with !, as in the no-secrets job, must be quoted. Check the file with a YAML linter or GitLab's pipeline editor before pushing.

Summary

  • A hook is an automatic script; a non-zero exit makes Git cancel the action. It must be executable.
  • pre-commit inspects files, commit-msg inspects the message; share them via a repo folder and core.hooksPath.
  • Hooks can be skipped with --no-verify, so CI is needed as the shared safeguard.
  • .gitlab-ci.yml declares stages, jobs, image, script and rules; a runner executes them and results show in the merge request.

The final part puts it all together. You will use git blame and git bisect to track down the commit that caused a bug, then run a complete working cycle: feature, merge request, hotfix and release.

Frequently asked questions

What is a Git hook and where does it live? ▾
A hook is a program Git runs by itself at fixed moments such as before a commit. By default hooks live in .git/hooks and must be executable; change the folder with core.hooksPath. A non-zero exit cancels the action.
How do I share hooks with the whole team? ▾
The .git/hooks folder is not committed. Keep the hooks in a folder of the repo, for example .githooks/, commit it, then have everyone run git config core.hooksPath .githooks once, ideally documented in the README.
Can hooks be skipped? ▾
Yes. git commit --no-verify skips both of those hooks. So hooks are only a safeguard on your machine; the team needs a GitLab CI pipeline as the shared gatekeeper.
What does GitLab CI need to run? ▾
At least one active runner (GitLab.com provides them) and the .gitlab-ci.yml configuration in the repository root declaring the jobs. When you push, GitLab creates a pipeline and shows the result in the merge request.
