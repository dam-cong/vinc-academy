Git Remotes: clone, fetch, pull, push and GitLab SSH Keys

Part 4 connects the vinc_course repo to GitLab: create an SSH key, clone, push a branch, fetch to look, pull to merge, and fix the rejected push or divergent branches error every team meets.

Updated: October 16, 2026 12 min read – views Vinc Academy Team

In short

A remote is a copy of the repository on a server (usually GitLab) so the whole team can push and fetch commits. This part connects the vinc_course repo to GitLab: creating an SSH key and registering it, clone, push a branch, fetch to see colleagues' work without merging it, pull to fetch and merge, and the rejected and divergent branches errors everyone meets. To run for real, the examples use a local bare repo that plays GitLab; the commands are identical with a real GitLab.

Remotes, origin and tracking branches

So far every commit lives only on your machine. To collaborate, the team keeps a central repo on GitLab; each person has their own repo locally and syncs through it. Git calls the faraway repo a remote, and the default name of the remote you cloned from is origin. A repo can have several remotes (say the company's origin and an upstream of the original project).

The point that most often confuses people is origin/main: it is not a branch you work on but a memory on your machine of where GitLab's main stood the last time you talked to it. It only updates when you fetch, pull or push. So “has the remote got new commits?” is a question Git answers correctly only after you fetch.

CommandWhat it does
git remote -vList remotes and their URLs
git remote add origin <url>Attach an existing local repo to a remote
git clone <url>Copy a repo to your machine and set origin automatically
git fetchDownload new commits without touching your branches
git pullfetch followed by a merge into where you stand
git pushSend your branch's commits to the remote
git push -u origin <nhánh>First push, remembering the tracking branch

Connecting to GitLab with an SSH key

There are two ways to authenticate when cloning: HTTPS (asks for credentials) or SSH. According to GitLab's documentation, SSH uses a key pair made of a public key (given to GitLab) and a private key (kept secret on your machine), so you do not enter a username and password on every push or pull. One key works for every project your account can reach; you do not need one per project. The preferred key type is ED25519. Do this once per machine:

# 1. Create the key pair (the comment is your email, to identify the key)
ssh-keygen -t ed25519 -C "an.nguyen@example.com"
# Press Enter to accept the default file ~/.ssh/id_ed25519, and set a passphrase

# 2. Load the private key into ssh-agent
ssh-add ~/.ssh/id_ed25519

# 3. Print the PUBLIC key to copy (the .pub file, not the extensionless one)
cat ~/.ssh/id_ed25519.pub

# 4. After pasting the key into GitLab, test the connection
ssh -T git@gitlab.example.com
# Welcome to GitLab, @your-name!
  • In GitLab: click your avatar → Edit profile → Access → SSH keys → Add new key, paste the public key, give it a title such as “Work laptop” and click Add key.
  • Replace gitlab.example.com with your company's GitLab address (gitlab.com for GitLab.com). On first connection ssh asks you to confirm the server; compare its fingerprint with GitLab's documentation before typing yes.
  • Never paste or send the private key (the id_ed25519 file). Only the .pub file may be shared.
TypeExample URLAuthentication
SSHgit@gitlab.example.com:vinc/vinc_course.gitAn SSH key pair, no password prompt each time
HTTPShttps://gitlab.example.com/vinc/vinc_course.gitAsks for credentials when connecting

Both URLs point to the same repo; they differ only in how you prove who you are. If you cloned with one and want the other, use git remote set-url origin <new-url>. The project page on GitLab has a Code button to copy either form.

Connecting a repo to GitLab: first push and clone

If the repo already exists on your machine (like our vinc_course), create an empty project on GitLab, add the remote and push. The -u flag (--set-upstream) remembers that main tracks origin/main, so from now on a plain git push and git pull are enough.

$ git remote add origin git@gitlab.example.com:vinc/vinc_course.git
$ git remote -v
origin	git@gitlab.example.com:vinc/vinc_course.git (fetch)
origin	git@gitlab.example.com:vinc/vinc_course.git (push)
$ git push -u origin main
branch 'main' set up to track 'origin/main'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      main -> main
$ git branch -vv
* main 47905cb [origin/main] [IMP] vinc_course: thêm trường số giờ
$ git status -sb
## main...origin/main

git status -sb now prints ## main...origin/main: your branch and its memory match. Your colleague Binh, on another machine, gets the repo with git clone, which creates the folder, points origin and checks out the default branch:

$ cd ..
$ git clone git@gitlab.example.com:vinc/vinc_course.git vinc_course_binh
Cloning into 'vinc_course_binh'...
done.
$ cd vinc_course_binh

Working in parallel: pushing a branch and fetching to look

Binh creates the level branch, commits and pushes it to GitLab. It is a new branch so the remote does not know it yet, and -u comes in handy again:

$ git switch -c feature/course-level
Switched to a new branch 'feature/course-level'
$ echo "    level = fields.Selection([('basic', 'Cơ bản'), ('adv', 'Nâng cao')])" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường cấp độ"
[feature/course-level 6c73d41] [IMP] vinc_course: thêm trường cấp độ
 1 file changed, 1 insertion(+)
$ git push -u origin feature/course-level
branch 'feature/course-level' set up to track 'origin/feature/course-level'.
To git@gitlab.example.com:vinc/vinc_course.git
 * [new branch]      feature/course-level -> feature/course-level

Nothing changes on An's machine until An runs fetch. After the fetch, Binh's branch appears as origin/feature/course-level for An to inspect or review without touching any of An's own branches. Switching to that name makes Git create a local branch called the same and wire up tracking:

$ cd ../vinc_course
$ git fetch
From git@gitlab.example.com:vinc/vinc_course
 * [new branch]      feature/course-level -> origin/feature/course-level
$ git branch -a
* main
  remotes/origin/feature/course-level
  remotes/origin/main
$ git switch feature/course-level
branch 'feature/course-level' set up to track 'origin/feature/course-level'.
Switched to a new branch 'feature/course-level'
$ git log --oneline -n 2
6c73d41 [IMP] vinc_course: thêm trường cấp độ
47905cb [IMP] vinc_course: thêm trường số giờ
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'

fetch and pull: where they differ

git pull is in effect git fetch plus a git merge into the branch you are on. A safe habit is fetch first, look, then merge, so you see which commits are coming. For example Binh pushes a README commit to main; An fetches, sees behind 1, then pulls and Git simply fast-forwards:

$ cd ../vinc_course_binh
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ echo "# vinc_course" > README.md
$ git add README.md
$ git commit -m "[ADD] vinc_course: README"
[main 518a39d] [ADD] vinc_course: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   47905cb..518a39d  main -> main
$ cd ../vinc_course
$ git fetch
From git@gitlab.example.com:vinc/vinc_course
   47905cb..518a39d  main       -> origin/main
$ git status -sb
## main...origin/main [behind 1]
$ git pull
Updating 47905cb..518a39d
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git log --oneline -n 2
518a39d [ADD] vinc_course: README
47905cb [IMP] vinc_course: thêm trường số giờ

When a push is rejected and pull says “divergent”

The classic team situation: An commits locally while Binh pushes another commit to the same branch. Their histories have split, so GitLab does not let An push over it. Let us reproduce it:

$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -am "[IMP] vinc_course: thêm trường học phí"
[main 7b05493] [IMP] vinc_course: thêm trường học phí
 1 file changed, 1 insertion(+)
$ cd ../vinc_course_binh
$ echo "Module quản lý khóa học." >> README.md
$ git commit -am "[IMP] vinc_course: mô tả README"
[main b6a59e9] [IMP] vinc_course: mô tả README
 1 file changed, 1 insertion(+)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   518a39d..b6a59e9  main -> main
$ cd ../vinc_course
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'git@gitlab.example.com:vinc/vinc_course.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

The rejected … (fetch first) message means the remote holds commits your machine does not have. Fetch them first. But this time git pull refuses to run because Git does not know whether to reconcile with merge or rebase:

$ git pull
From git@gitlab.example.com:vinc/vinc_course
   518a39d..b6a59e9  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

Git lists three configuration choices. For now pick merge with the --no-rebase flag; part 8 compares it with rebase. Because the two commits touch different files, Git merges them on its own and then you push:

$ git pull --no-rebase
Merge made by the 'ort' strategy.
 README.md | 1 +
 1 file changed, 1 insertion(+)
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   b6a59e9..bfdc341  main -> main
$ git log --oneline --graph -n 4
*   bfdc341 Merge branch 'main' of git@gitlab.example.com:vinc/vinc_course
|\  
| * b6a59e9 [IMP] vinc_course: mô tả README
* | 7b05493 [IMP] vinc_course: thêm trường học phí
|/  
* 518a39d [ADD] vinc_course: README

To avoid the question every time you can set a default: git config --global pull.rebase false (merge), pull.rebase true (rebase) or pull.ff only (accept fast-forward only, the most cautious). Agree on one with your team.

Cleaning up remote branches

Once a branch is merged, delete the copy on GitLab as well. git push origin --delete <branch> removes the remote branch; colleagues still hold the old memory of it, so they run git fetch --prune to tidy up. A local copy with that name remains and must be deleted separately with git branch -d.

$ cd ../vinc_course_binh
$ git push origin --delete feature/course-level
To git@gitlab.example.com:vinc/vinc_course.git
 - [deleted]         feature/course-level
$ cd ../vinc_course
$ git fetch --prune
From git@gitlab.example.com:vinc/vinc_course
 - [deleted]         (none)     -> origin/feature/course-level
$ git branch -a
  feature/course-level
* main
  remotes/origin/main

Common beginner mistakes

  • A push is rejected. Do not rush to force it. Run git pull (or fetch and look), resolve, then push again as above.
  • Using git push --force to get it over with. A forced push overwrites colleagues' commits on the remote. If you truly must (say after rebasing your own branch) use --force-with-lease: it refuses when the remote holds commits you have not seen. Never force onto a shared branch such as main.
  • Pasting the private key into GitLab. Paste only the contents of the .pub file (it starts with ssh-ed25519). If a private key leaks, generate a new pair and delete the old key from GitLab.
  • Assuming origin/main is always current. It is only as fresh as your last fetch; fetch before comparing or deciding to merge.

Summary

  • The remote (origin) is the central repo; origin/main is a memory on your machine, fresh only after fetch.
  • ED25519 SSH key: the public key goes to GitLab, the private key stays on your machine.
  • clone gets the repo; push -u sends a branch the first time; fetch looks first; pull = fetch + merge.
  • Rejected and divergent mean history has split: fetch, integrate, then push; avoid --force.

You now have branches on GitLab. But in a company hardly anyone merges directly with a command: they open a merge request so colleagues review the code before it reaches the main branch. That is the subject of part 5.

Frequently asked questions

What is the difference between fetch and pull? ▾
git fetch only downloads new commits from the remote and updates the origin/... branches, leaving the branch you work on alone. git pull is git fetch followed by integrating the result into the branch you are on. Fetch first to see what is coming, then integrate.
Why is my push rejected (fetch first)? ▾
Because the remote already has commits your machine lacks, usually a colleague who just pushed to the same branch. Run git pull (or fetch then merge), resolve any conflict, then push again. Do not use --force to get past it.
Should I use SSH or HTTPS with GitLab? ▾
Both work. SSH uses a key pair so you do not enter credentials on every push or pull; HTTPS asks for credentials when connecting. Most teams choose SSH with an ED25519 key for regular work machines.
What does -u do in git push -u origin main? ▾
-u (--set-upstream) remembers that the local branch tracks the branch on origin. Afterwards a plain git push and git pull are enough, and git status tells you how many commits you are ahead or behind the remote.
