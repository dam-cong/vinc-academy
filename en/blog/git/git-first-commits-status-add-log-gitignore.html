Git First Commits: status, add, diff, log and .gitignore

Part 2 runs the daily Git loop on the vinc_course module: read git status, tell git diff from --staged, write tidy commits, review them with git log and keep unwanted files out with .gitignore.

Updated: October 16, 2026 11 min read Vinc Academy Team

In short

Day to day you repeat one loop: edit files → git status → git diff → git add → git commit. This part runs that loop on the vinc_course module: reading the symbols of git status -s, telling git diff from git diff --staged, writing commits in Odoo's [TAG] module: style, reviewing them via git log and git show, and using .gitignore so __pycache__ and odoo.conf never reach the repo.

The daily loop on the vinc_course module

Suppose you have just built the module skeleton below (file contents as in the Odoo series). The repo has been git init-ed but has no commits yet, so git status lists everything as untracked: Git sees the files but is not following them.

vinc_course/
├── __init__.py
├── __manifest__.py
└── models/
    ├── __init__.py
    └── course.py
from odoo import fields, models


class VincCourse(models.Model):
    _name = 'vinc.course'
    _description = 'Khóa học'

    name = fields.Char(required=True)

Use git add . to stage everything and then commit. That is fine for the very first time, but from now on make it a habit to read git status before add . so you do not drag junk files along.

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	__init__.py
	__manifest__.py
	models/

nothing added to commit but untracked files present (use "git add" to track)
$ git add .
$ git status -s
A  __init__.py
A  __manifest__.py
A  models/__init__.py
A  models/course.py
$ git commit -m "[ADD] vinc_course: khung module và model vinc.course"
[main (root-commit) a79a9aa] [ADD] vinc_course: khung module và model vinc.course
 4 files changed, 17 insertions(+)
 create mode 100644 __init__.py
 create mode 100644 __manifest__.py
 create mode 100644 models/__init__.py
 create mode 100644 models/course.py
$ git log --oneline
a79a9aa [ADD] vinc_course: khung module và model vinc.course

The first line of the message ([ADD] vinc_course: ...) follows a convention common in Odoo repositories; part 10 covers it in depth. For now just remember: -m gives a one-line message, and each commit should do exactly one thing.

Reading git status -s

The full git status is friendly to newcomers, but the short form -s (--short) is much quicker on a large project. Each line has two symbol columns: the left one is the state in staging, the right one the state in the working tree.

ShownMeaningNext step
?? fileNew file Git is not trackinggit add if it belongs, otherwise add it to .gitignore
A  fileNew file already stagedReady to commit
 M fileEdited on disk but not stagedgit diff to review, git add to stage
M  fileModified and stagedReady to commit
 D fileDeleted in the working treegit add or git rm to record the deletion

Seeing what changed: git diff and git diff --staged

These two are easy to mix up. git diff (no flags) compares the working tree with staging, meaning changes that have not been added yet. git diff --staged (a synonym of --cached) compares staging with the latest commit, meaning exactly what the next commit will contain. Let us add an hours field to the model and watch:

$ echo "    hours = fields.Integer(string='Số giờ')" >> models/course.py
$ git status -s
 M models/course.py
$ git diff
diff --git a/models/course.py b/models/course.py
index 86951c7..781c9a6 100644
--- a/models/course.py
+++ b/models/course.py
@@ -6,3 +6,4 @@ class VincCourse(models.Model):
     _description = 'Khóa học'
 
     name = fields.Char(required=True)
+    hours = fields.Integer(string='Số giờ')
$ git add models/course.py
$ git status -s
M  models/course.py
$ git diff
$ git diff --staged
diff --git a/models/course.py b/models/course.py
index 86951c7..781c9a6 100644
--- a/models/course.py
+++ b/models/course.py
@@ -6,3 +6,4 @@ class VincCourse(models.Model):
     _description = 'Khóa học'
 
     name = fields.Char(required=True)
+    hours = fields.Integer(string='Số giờ')
$ git commit -m "[IMP] vinc_course: thêm trường số giờ"
[main ef00810] [IMP] vinc_course: thêm trường số giờ
 1 file changed, 1 insertion(+)

How to read it: a line starting with + was added, - was removed, and the @@ line gives the position in the file. Notice the second git diff prints nothing: every change is already in staging, so disk and staging no longer differ. A good habit before each commit is to run git diff --staged as a last self-review, like rereading an email before sending it.

Reading history: git log and git show

$ git log --stat --oneline
ef00810 [IMP] vinc_course: thêm trường số giờ
 models/course.py | 1 +
 1 file changed, 1 insertion(+)
a79a9aa [ADD] vinc_course: khung module và model vinc.course
 __init__.py        | 1 +
 __manifest__.py    | 7 +++++++
 models/__init__.py | 1 +
 models/course.py   | 8 ++++++++
 4 files changed, 17 insertions(+)
$ git show --stat HEAD
commit ef00810db8c3ba15ee2751bb6e570d7e13495d19
Author: Nguyễn Văn An <an.nguyen@example.com>
Date:   Mon Oct 12 11:06:00 2026 +0700

    [IMP] vinc_course: thêm trường số giờ

 models/course.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline -n 1
ef00810 [IMP] vinc_course: thêm trường số giờ

git log lists commits from newest to oldest; --oneline shrinks each to one line, --stat adds a summary of the files changed and -n 1 limits how many commits are shown. git show prints the details of one commit (by default HEAD, the latest): author, time, message and changes.

CommandWhat it does
git log --onelineOne line per commit: short hash + title
git log -p -- đường/dẫnDetailed changes for a single file
git log --author="An"Filter by author
git log --since="1 week ago"Filter by time
git show <mã>Details of any commit

.gitignore: keeping junk and secrets out of the repo

When you run Odoo, Python generates __pycache__ folders, the server writes log files, and you may have an odoo.conf holding admin_passwd. None of these belongs in the repo: junk clutters history, and a password that reaches GitLab is seen by many people. A .gitignore file at the repo root lists name patterns Git will ignore:

$ git status -s
?? models/__pycache__/
?? odoo.conf
?? odoo.log
$ printf "__pycache__/\n*.pyc\n*.log\nodoo.conf\n.venv/\n" > .gitignore
$ git status -s
?? .gitignore
$ git check-ignore -v odoo.conf models/__pycache__/course.cpython-312.pyc
.gitignore:4:odoo.conf	odoo.conf
.gitignore:1:__pycache__/	models/__pycache__/course.cpython-312.pyc
$ git add .gitignore
$ git commit -m "[ADD] vinc_course: .gitignore"
[main e945725] [ADD] vinc_course: .gitignore
 1 file changed, 5 insertions(+)
 create mode 100644 .gitignore

git check-ignore -v shows which rule blocks which file (the first column is file:line:pattern), which is handy when you wonder why a file never shows up in status. Remember to commit .gitignore itself so the whole team shares the rules.

PatternMatches
*.pycEvery file ending in .pyc
__pycache__/Directories named __pycache__ (the trailing / matches directories only)
odoo.confA file of that name at any depth
!keep.logA leading ! negates: do not ignore this file
# ghi chúA line starting with # is a comment

A starter .gitignore for an Odoo project

PatternWhy ignore it
__pycache__/, *.pycAuto-generated Python bytecode that differs per machine
.venv/The virtual environment (part 1 of the Python series): rebuildable from requirements.txt
odoo.conf, .envHold passwords and API keys; commit a sample odoo.conf.example instead
*.logServer logs: large and constantly changing
.idea/, .vscode/Each person's own editor settings

What a good commit looks like

Git does not force any message on you, but six months later you will thank (or blame) that message when you hunt for why a line exists. Odoo's Git guidelines suggest a title of roughly under 50 characters, a body that explains the reason for the change rather than just listing actions, and avoiding vague titles like “bugfix” or “improvements”. A few comparisons on our module:

AvoidPrefer
update[IMP] vinc_course: thêm trường số giờ cho khóa học
fix bug[FIX] vinc_course: không cho tạo hai khóa trùng mã
sửa nhiều thứSplit into separate commits, one job each

A practical rule: if you cannot describe a commit in one sentence without the word “and”, it probably does two jobs and should be split by running git add file by file. When you need several lines, drop the -m flag so Git opens the editor you chose in part 1 (core.editor): the first line is the title, then a blank line, then the description.

Renaming and deleting files properly

Git does not store “rename” as a separate operation; it compares content and recognises that a file moved. Still, git mv and git rm put the change straight into staging, saving a git add. Odoo's guidelines add a warning: when moving files (the [MOV] tag), do not change their content at the same time, or Git may lose track of the file's history.

$ git mv README.md README.rst
$ git status -s
R  README.md -> README.rst
$ git commit -m "[MOV] vinc_course: đổi README.md thành README.rst"
[main 2cf6824] [MOV] vinc_course: đổi README.md thành README.rst
 1 file changed, 0 insertions(+), 0 deletions(-)
 rename README.md => README.rst (100%)
$ git log --oneline --follow -- README.rst
2cf6824 [MOV] vinc_course: đổi README.md thành README.rst
a232969 [ADD] vinc_course: README

The R symbol stands for rename. The --follow flag of git log follows the file across the rename, so you still see the earlier history of README.md.

Common beginner mistakes

  • Added .gitignore but the file still shows M. .gitignore only applies to files that are not yet tracked; a file committed earlier stays tracked. The gitignore documentation points to git rm --cached to stop tracking while keeping the file on disk. Here it is with an odoo.conf committed by mistake at the start:
$ printf "odoo.conf\n" > .gitignore
$ echo "db_name = vinc" >> odoo.conf
$ git status -s
 M odoo.conf
?? .gitignore
$ git rm --cached odoo.conf
rm 'odoo.conf'
$ git add .gitignore
$ git status -s
A  .gitignore
D  odoo.conf
$ git commit -m "[FIX] vinc_course: bỏ odoo.conf khỏi repo"
[main 527fefc] [FIX] vinc_course: bỏ odoo.conf khỏi repo
 2 files changed, 1 insertion(+), 1 deletion(-)
 create mode 100644 .gitignore
 delete mode 100644 odoo.conf
$ git status -s
  • Deleting a committed password is not enough. The delete is just a new commit; the old content stays in history. If the secret was pushed to GitLab, rotate that password or key at once, then ask an admin to deal with the history.
  • git commit -a does not take new files. The -a flag only stages tracked files (modified or deleted); the documentation states files Git has not been told about are not affected. In the example, NOTE.md still shows ?? after the commit:
$ echo "# ghi chú" > NOTE.md
$ echo "y = 2" >> models.py
$ git commit -am "[IMP] vinc_course: sửa models"
[main 264ae18] [IMP] vinc_course: sửa models
 1 file changed, 1 insertion(+)
$ git status -s
?? NOTE.md
  • git add . without looking at status. You easily sweep temp files, database dumps or screenshots into a commit. Run git status -s first, then git add specific files or folders.

Summary

  • The loop: edit → status → diff → add → commit.
  • git diff shows unstaged changes; git diff --staged shows what will be committed.
  • git log --oneline and git show read the history.
  • .gitignore only affects untracked files; if you committed by mistake use git rm --cached.
  • A password that entered history must be changed, not just deleted.

You can now commit along a straight line. But teamwork means several things in parallel: one person edits the model while another builds a report. The next part introduces branches so each task gets its own path, then merging to bring them back together.

Frequently asked questions

How do git diff and git diff --staged differ? ▾
git diff compares the working tree with staging, meaning changes not yet added. git diff --staged (or --cached) compares staging with the latest commit, meaning exactly what the next commit will contain.
Why does a file still show in git status after I add it to .gitignore? ▾
.gitignore only affects files Git is not tracking yet. For a file committed earlier, run git rm --cached file_name and commit to stop tracking it while keeping the file on disk.
Does git commit -a include new files? ▾
No. The -a flag only stages files that are already tracked and were modified or deleted. New files (shown as ?? in git status -s) still need git add first.
Should I commit odoo.conf? ▾
Not if it holds secrets such as admin_passwd or connection details. Put odoo.conf in .gitignore and commit a sample like odoo.conf.example without secrets.
