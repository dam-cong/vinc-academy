Git Rebase: Tidy History and the Golden Rule for Teams

Part 8 shows how rebase differs from merge: update a branch with git rebase main, combine small commits with rebase -i and autosquash, resolve rebase conflicts and follow the golden rule: never rebase what is shared.

Updated: October 16, 2026 13 min read – views Vinc Academy Team

In short

Rebase “rewrites” a branch's commits so they sit on top of the latest tip of another branch, giving a straight, tidy history. This part uses git rebase main to update a feature branch, git rebase -i to combine small commits (fixup, squash, reword), --autosquash to fold small fix commits automatically, resolves conflicts during a rebase (where ours and theirs swap) and covers the golden rule: never rebase commits that are shared. Every command ran for real on the vinc_course repo.

What rebase is and how it differs from merge

In part 3 you saw that merge joins two branches with a merge commit, preserving the “split then join” history. rebase does it differently: it takes your branch's own commits, sets them aside, moves the branch to the new tip of the target and then replays each commit on top. The result is a single straight line of history, as if you had started from the new tip all along.

The thing to remember most: a replayed commit is no longer the old commit. The changes are the same but the parent differs, so the hash is new (F1' and F2' in the diagram). That is why rebase is only safe on commits nobody else builds on.

mergerebase
HistoryHas a merge commit; the moment of joining is visibleStraight, no merge commit
Old commitsKeep their hashesRecreated with new hashes
Use it whenJoining shared branches; keeping a recordTidying your own branch before review

Updating a feature branch with rebase

Suppose you work on the price branch with three messy commits (one “wip”, one “fix typo”) and have pushed it as a backup. Meanwhile main gained a README commit, so your branch is behind. The graph shows the two lines splitting:

$ git switch -c feature/course-price
Switched to a new branch 'feature/course-price'
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm trường học phí"
$ echo "# wip" >> models/course.py
$ git commit -qam "wip"
$ echo "# sửa lỗi gõ" >> models/course.py
$ git commit -qam "fix typo"
$ git push -q -u origin feature/course-price
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ echo "# vinc_course" > README.md
$ git add README.md
$ git commit -qm "[ADD] vinc_course: README"
$ git push -q
$ git switch feature/course-price
Your branch is up to date with 'origin/feature/course-price'.
Switched to branch 'feature/course-price'
$ git log --oneline --graph --all
* eeb11a2 [ADD] vinc_course: README
| * cffbf1a fix typo
| * 394aee0 wip
| * 4815c9b [IMP] vinc_course: thêm trường học phí
|/  
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course

Run git rebase main from the feature branch. Git replays each commit after the README commit; the graph is now one straight line and all three commits have new hashes:

$ git rebase main
Rebasing (1/3)
Rebasing (2/3)
Rebasing (3/3)
Successfully rebased and updated refs/heads/feature/course-price.
$ git log --oneline --graph
* 5ab820d fix typo
* de07295 wip
* 371e622 [IMP] vinc_course: thêm trường học phí
* eeb11a2 [ADD] vinc_course: README
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course

A practical note: a rebase without textual conflicts can still introduce logic errors, because your code now runs on top of your colleagues' new work. Re-run the tests or a trial module upgrade (-u vinc_course) before you push.

Because the commits changed hash while GitLab still holds the old ones, a plain git push is normally rejected. For your own branch the right tool is --force-with-lease: it overwrites the remote branch but refuses if the remote has commits you have not seen, so it will not trample someone else's work:

$ git push
To git@gitlab.example.com:vinc/vinc_course.git
 ! [rejected]        feature/course-price -> feature/course-price (non-fast-forward)
error: failed to push some refs to 'git@gitlab.example.com:vinc/vinc_course.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
$ git push --force-with-lease
To git@gitlab.example.com:vinc/vinc_course.git
 + cffbf1a...5ab820d feature/course-price -> feature/course-price (forced update)

Combining small commits with interactive rebase

Review is easier when the branch tells a short story. git rebase -i main opens a list (in your editor) of the branch's commits, each line starting with a command. You change the first word and save; Git then executes from top to bottom:

CommandEffect
pickKeep the commit as is
rewordKeep the content, edit the message
editStop so you can change the commit's content
squashFold into the previous commit and combine both messages
fixupFold into the previous commit and discard its message
dropRemove the commit entirely

The lines starting with # editor: below are the list Git opened. We change pick on lines 2 and 3 to fixup so “wip” and “fix typo” melt into the first commit:

$ git rebase -i main
# editor: pick 371e622 [IMP] vinc_course: thêm trường học phí
# editor: pick de07295 wip
# editor: pick 5ab820d fix typo
Rebasing (2/3)
Rebasing (3/3)
Successfully rebased and updated refs/heads/feature/course-price.
$ git log --oneline --graph
* 16412cc [IMP] vinc_course: thêm trường học phí
* eeb11a2 [ADD] vinc_course: README
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git push --force-with-lease
To git@gitlab.example.com:vinc/vinc_course.git
 + 5ab820d...16412cc feature/course-price -> feature/course-price (forced update)

Three commits became one, and since it was rewritten you need --force-with-lease when pushing. If you know in advance which commit a small change fixes, create it with git commit --fixup; then rebase -i --autosquash puts the fix commit in the right place and turns it into fixup by itself (see the last line of the list):

$ echo "    level = fields.Char(string='Cấp độ')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm cấp độ"
$ echo "# thiếu dấu" >> models/course.py
$ git commit -q --fixup HEAD -a
$ git log --oneline -n 3
e12996a fixup! [IMP] vinc_course: thêm cấp độ
01b13bf [IMP] vinc_course: thêm cấp độ
16412cc [IMP] vinc_course: thêm trường học phí
$ git rebase -i --autosquash main
# editor: pick 16412cc [IMP] vinc_course: thêm trường học phí
# editor: pick 01b13bf [IMP] vinc_course: thêm cấp độ
# editor: fixup e12996a fixup! [IMP] vinc_course: thêm cấp độ
Rebasing (3/3)
Successfully rebased and updated refs/heads/feature/course-price.
$ git log --oneline -n 3
f5dc751 [IMP] vinc_course: thêm cấp độ
16412cc [IMP] vinc_course: thêm trường học phí
eeb11a2 [ADD] vinc_course: README

GitLab also offers a squash option when merging a merge request, so many teams do not require interactive rebase. Even so, tidying your own branch is useful because you control each commit's message.

Conflicts during a rebase: “ours” and “theirs” swap

A rebase replays commits one by one so a conflict can arise at any step. The handling is as in part 6, but you finish with git rebase --continue instead of git commit. One source of confusion: according to the documentation, during a rebase ours is the already-rebased series starting from the target, and theirs is your working branch, so the sides are swapped compared with a merge. Example: main renamed the label to “Tổng số giờ” while your branch renamed it to “Số giờ học”:

$ git rebase main
Auto-merging models/course.py
CONFLICT (content): Merge conflict in models/course.py
Rebasing (1/1)
error: could not apply 5f72b8e... [IMP] vinc_course: đổi nhãn số giờ học
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
hint: Disable this message with "git config advice.mergeConflict false"
Could not apply 5f72b8e... [IMP] vinc_course: đổi nhãn số giờ học
$ git status -sb
## HEAD (no branch)
UU models/course.py
$ grep -n -A5 "<<<<<<<" models/course.py
9:<<<<<<< HEAD
10-    hours = fields.Integer(string='Tổng số giờ')
11-=======
12-    hours = fields.Integer(string='Số giờ học')
13->>>>>>> 5f72b8e ([IMP] vinc_course: đổi nhãn số giờ học)

The part after HEAD is main's version (the target), the lower part is your commit being replayed. We pick a combined label, then mark it resolved and let the rebase go on:

$ grep hours models/course.py
    hours = fields.Integer(string='Tổng số giờ học')
$ git add models/course.py
$ git rebase --continue
[detached HEAD aaf80fe] [IMP] vinc_course: đổi nhãn số giờ học
 1 file changed, 1 insertion(+), 1 deletion(-)
Successfully rebased and updated refs/heads/feature/hours-label.
$ git log --oneline --graph
* aaf80fe [IMP] vinc_course: đổi nhãn số giờ học
* fa3c870 [IMP] vinc_course: đổi nhãn tổng số giờ
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course

If it gets messy, git rebase --abort returns the branch exactly to how it was before the rebase; git rebase --skip skips the commit that is causing the conflict.

git pull --rebase: fetching without a merge commit

In part 4, when An had a local commit and Binh had already pushed, git pull --no-rebase created a merge commit named “Merge branch 'main' of …” just to join the two lines. If you prefer a straight history use git pull --rebase: Git fetches and then replays your local commits on top of the remote's new ones. Because your commit is not pushed yet, this is the safest kind of rebase:

$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm trường học phí"
$ git pull --rebase
From git@gitlab.example.com:vinc/vinc_course
   47905cb..4c7a4cb  main       -> origin/main
Rebasing (1/1)
Successfully rebased and updated refs/heads/main.
$ git log --oneline --graph
* b7faa54 [IMP] vinc_course: thêm trường học phí
* 4c7a4cb [ADD] vinc_course: README
* 47905cb [IMP] vinc_course: thêm trường số giờ
* 847d6e3 [ADD] vinc_course: khung module và model vinc.course
$ git push
To git@gitlab.example.com:vinc/vinc_course.git
   4c7a4cb..b7faa54  main -> main

No merge commit appears, and the git push afterwards goes through cleanly because your history now continues straight from the remote's. This is also what a team chooses when it sets pull.rebase true.

The golden rule: never rebase what is shared

The Git manual is blunt: rewriting commits your colleagues already build on is risky, because everyone downstream ends up repairing their history by hand. Practical rules for a team:

  • Rebase freely your own feature branch, before or during a merge request.
  • Never rebase main, release branches or any branch someone else is working on.
  • After rebasing your own branch push with --force-with-lease, never bare --force.
  • To make git pull rebase instead of merge: git config --global pull.rebase true (agree with your team, as in part 4).

Common beginner mistakes

  • A plain push is rejected after a rebase. That is normal because the hashes changed (see the push above). Use --force-with-lease on your own branch; if someone else shares the branch, stop and talk first.
  • Rebasing a shared branch and force-pushing. Colleagues who pull will see duplicated commits or odd conflicts. If you did it, tell the team right away and use the reflog (part 7) to restore the old state.
  • Mixing up “ours” and “theirs”. During a rebase, git restore --theirs takes your version, the opposite of a merge. Read the resulting file instead of trusting the flag name.
  • Forgetting you are in the middle of a rebase. git status says rebase in progress; finish with --continue or bail out with --abort rather than committing at random.

Summary

  • Rebase replays a branch's commits on a new tip for a straight history; commits get new hashes.
  • rebase -i with fixup/squash/reword/drop tidies a branch; --autosquash handles --fixup commits.
  • Conflicts during a rebase: fix, git add, git rebase --continue; “ours” and “theirs” are swapped.
  • Only rebase your own branch; push again with --force-with-lease.

Frequently asked questions

How does rebase differ from merge? ▾
Merge joins two branches with a merge commit and keeps the history that split. Rebase replays your branch's commits on the new tip of the target, giving a straight history, but those commits get new hashes.
When should I not use rebase? ▾
Do not rebase commits others have built on, such as main or a shared branch. The Git manual warns it leaves everyone downstream repairing their own history. Rebase your own branch freely.
Why must I push --force-with-lease after a rebase? ▾
Because rebase changes the commits' hashes, the remote copy is no longer an ancestor of your branch and a normal push is rejected. --force-with-lease overwrites but refuses if the remote has commits you have not seen, which is safer than --force.
How do squash and fixup differ in rebase -i? ▾
Both fold a commit into the one before it. squash keeps and combines both messages for you to edit; fixup discards the folded commit's message. Use fixup for small corrections such as wip or fix typo commits.
