Git Undo: restore, reset, revert and reflog Explained

Part 7 shows how to pick the right Git undo command: restore for files, commit --amend, reset with its three flags, revert for pushed commits and reflog to rescue lost commits, all run for real on the vinc_course repo.

Updated: October 16, 2026 13 min read Vinc Academy Team

In short

Every kind of mistake has its own undo command; choosing the right one matters more than remembering many. Edited the wrong file: git restore. Staged by mistake: git restore --staged. Unpushed commit: amend it or use git reset (--soft, default --mixed, --hard). Pushed commit: git revert. Lost a commit: git reflog. This part runs each command on the vinc_course repo so you see exactly what is lost and what stays.

Pick the command by “where am I”

The trick is to find which of the three areas from part 1 holds the mistake, then rewind from there. One more deciding question: has the commit been pushed to GitLab? An unpushed commit lives only on your machine so you may rewrite it freely; a pushed commit belongs to the team, and rewriting history confuses everyone else.

SituationCommandWhat is lost?
Edited a file by mistake, not addedgit restore <file>The uncommitted changes of that file (unrecoverable)
Added too muchgit restore --staged <file>Nothing; the file keeps its changes
Wrong message or missing file in the latest commitgit commit --amendThe old commit is replaced by a new one (only if unpushed)
Drop unpushed commitsgit reset --soft / --mixed / --hard HEAD~NDepends on the flag, see the table below
Pushed commit that must be undonegit revert <commit>Nothing; adds a new commit
Lost commits after reset or branch deletiongit reflogThis is the rescue tool

Undoing uncommitted changes: git restore

git restore <file> returns the file on disk to what staging holds (or to the latest commit if nothing is staged). Remember: restored uncommitted changes cannot be recovered, because Git never stored them. git restore --staged only pulls the file out of staging; the changes stay in the file, so it is perfectly safe:

$ echo "# lỡ tay" >> models/course.py
$ git status -s
 M models/course.py
$ git restore models/course.py
$ git status -s
$ echo "# lỡ tay" >> models/course.py
$ git add models/course.py
$ git status -s
M  models/course.py
$ git restore --staged models/course.py
$ git status -s
 M models/course.py
$ git restore models/course.py

To bring back a file from an older commit add --source: git restore --source=HEAD~2 models/course.py puts the file as it was two commits ago (still an uncommitted change, so you can look and then decide).

Fixing the latest commit: git commit --amend

Mistyped the message or forgot a file? Do not add a “fix typo” commit. --amend replaces the latest commit with a new one with the corrected content. The hash changes, meaning it is a different commit; that is why you should amend only before pushing:

$ echo "# vinc_course" > README.md
$ git add README.md
$ git commit -m "[ADD] vinc_corse: README"
[main 87e323f] [ADD] vinc_corse: README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ git commit --amend -m "[ADD] vinc_course: README"
[main f7f143d] [ADD] vinc_course: README
 Date: Mon Oct 12 11:20:00 2026 +0700
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
$ echo "Module quản lý khóa học." >> README.md
$ git commit -qa --amend --no-edit
$ git log --oneline -n 2
b7b55df [ADD] vinc_course: README
47905cb [IMP] vinc_course: thêm trường số giờ
$ git show --stat --oneline HEAD
b7b55df [ADD] vinc_course: README
 README.md | 2 ++
 1 file changed, 2 insertions(+)

Dropping unpushed commits: git reset

git reset <commit> moves the current branch to that commit. Three flags decide the rest (per the documentation): --soft leaves both staging and the working tree untouched; --mixed (the default) updates staging to match the new commit and leaves the working tree; --hard overwrites the working tree as well. Try it with the price and level commits:

FlagHEAD / branchStagingWorking tree
--softmoves backkeptkept
--mixedmoves backmatches new HEADkept
--hardmoves backmatches new HEADoverwritten
 
$ echo "    price = fields.Float(string='Học phí')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm học phí"
$ echo "    level = fields.Char(string='Cấp độ')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm cấp độ"
$ git reset --soft HEAD~1
$ git status -s
M  models/course.py
$ git log --oneline -n 2
907ebca [IMP] vinc_course: thêm học phí
b7b55df [ADD] vinc_course: README

--soft puts the dropped commit's changes back into staging (M in the left column), handy when you want to combine or rewrite commits. Commit again and try --mixed: the changes become unstaged:

$ git commit -qm "[IMP] vinc_course: thêm cấp độ"
$ git reset HEAD~1
Unstaged changes after reset:
M	models/course.py
$ git status -s
 M models/course.py

Finally --hard: it moves the branch and also wipes the changes from the working tree (grep counts 0 because the level line is gone):

$ git commit -qam "[IMP] vinc_course: thêm cấp độ"
$ git reset --hard HEAD~1
HEAD is now at 907ebca [IMP] vinc_course: thêm học phí
$ git status -sb
## main
$ grep -c level models/course.py
0

Rescuing “lost” commits: git reflog

The commit that reset --hard just dropped has not really vanished: Git records every HEAD movement in the reflog. Find the HEAD@{n} entry from before the mistake and move the branch back to it. According to the git config documentation, reflog entries are kept for 90 days by default (30 days for entries no longer reachable from any branch), so rescue early:

$ git reflog -n 3
907ebca HEAD@{0}: reset: moving to HEAD~1
9f21257 HEAD@{1}: commit: [IMP] vinc_course: thêm cấp độ
907ebca HEAD@{2}: reset: moving to HEAD~1
$ git reset --hard HEAD@{1}
HEAD is now at 9f21257 [IMP] vinc_course: thêm cấp độ
$ grep -c level models/course.py
1
$ git log --oneline -n 2
9f21257 [IMP] vinc_course: thêm cấp độ
907ebca [IMP] vinc_course: thêm học phí

These two ways of counting are easy to mix up. HEAD~1 and HEAD~2 count back through the branch's commit history (parent, grandparent). HEAD@{1} counts back through the reflog, meaning where HEAD stood at earlier moves, including commits no longer on the branch. So after a reset --hard, HEAD~1 takes you further back while HEAD@{1} takes you back where you were.

Reversing a pushed commit: git revert

Once a commit is on GitLab, do not reset and force-push: others already have it. Use git revert, which makes a new commit whose effect is the reverse. History stays intact and anyone who pulls receives the fix:

$ git revert --no-edit HEAD
[main ddec0fc] Revert "[IMP] vinc_course: thêm cấp độ"
 Date: Mon Oct 12 14:08:00 2026 +0700
 1 file changed, 1 deletion(-)
$ git log --oneline -n 3
ddec0fc Revert "[IMP] vinc_course: thêm cấp độ"
9f21257 [IMP] vinc_course: thêm cấp độ
907ebca [IMP] vinc_course: thêm học phí
$ grep -c level models/course.py
0

To revert a merge commit you must say which parent counts as the “mainline” with -m 1 (the --mainline option in the documentation), usually the main side. Reverting a merge is the standard response when a merge request already in main breaks the staging environment.

Two more common situations

Committed on main by mistake (mentioned in part 3). Keep the work by creating a branch at the current commit, then move main back. Done in this order it is safe and no commit is lost:

$ echo "    code = fields.Char(string='Mã')" >> models/course.py
$ git commit -qam "[IMP] vinc_course: thêm mã khóa (lẽ ra phải ở nhánh riêng)"
$ git branch feature/course-code
$ git reset --hard HEAD~1
HEAD is now at ddec0fc Revert "[IMP] vinc_course: thêm cấp độ"
$ git log --oneline --graph --all --decorate -n 4
* 7bfb9cd (feature/course-code) [IMP] vinc_course: thêm mã khóa (lẽ ra phải ở nhánh riêng)
* ddec0fc (HEAD -> main) Revert "[IMP] vinc_course: thêm cấp độ"
* 9f21257 [IMP] vinc_course: thêm cấp độ
* 907ebca [IMP] vinc_course: thêm học phí

Cleaning untracked files. git clean deletes untracked files; always run -n (dry run) first to see what it would remove, because files deleted this way are not in the reflog:

$ echo "x" > tam.txt
$ git clean -n
Would remove tam.txt
$ git clean -f
Removing tam.txt
$ git status -s

A safety net before anything risky

The reflog is the last net, but there is a cheaper way never to need it: before a command you are unsure about (reset --hard, rebase, clean), create a backup branch at the current position. A branch is only a pointer so it is instant, and if all goes well you delete it. If something breaks, move the working branch back to the marked spot:

$ git branch backup/truoc-reset
$ git reset --hard HEAD~1
HEAD is now at 9f21257 [IMP] vinc_course: thêm cấp độ
$ git log --oneline -n 1
9f21257 [IMP] vinc_course: thêm cấp độ
$ git reset --hard backup/truoc-reset
HEAD is now at ddec0fc Revert "[IMP] vinc_course: thêm cấp độ"
$ git log --oneline -n 1
ddec0fc Revert "[IMP] vinc_course: thêm cấp độ"
$ git branch -d backup/truoc-reset
Deleted branch backup/truoc-reset (was ddec0fc).

This habit is especially valuable in release week, when pressure is high and typos are easy. Together with always reading git status and git log --oneline before undoing anything, it turns the “scary” commands into everyday operations.

Common beginner mistakes

  • git reset --hard with work in progress. It wipes uncommitted changes and the reflog cannot save them because Git never stored them. In the example below the unfinished line vanishes completely; the reflog only records the HEAD movement, not file content:
$ echo "# việc dang dở" >> models/course.py
$ git reset --hard HEAD
HEAD is now at ddec0fc Revert "[IMP] vinc_course: thêm cấp độ"
$ grep -c dang models/course.py
0
$ git reflog -n 2
ddec0fc HEAD@{0}: reset: moving to HEAD
ddec0fc HEAD@{1}: reset: moving to HEAD~1
  • Amending or resetting a pushed commit and force-pushing. Others already pulled the old commit, so their history diverges from the remote and work gets lost easily. For pushed commits use revert.
  • Mixing up restore and reset. restore works on files, reset moves the branch. If you only want to discard one file, avoid reset --hard because it touches every file.
  • Panicking over a “lost” commit. Stop, run git reflog and find the hash; while it is still in the reflog you can get it back with git reset --hard <hash> or git switch -c rescue <hash>.

Summary

  • Not committed: restore (files) and restore --staged (staging).
  • Unpushed commit: --amend or reset (--soft keeps staging, --mixed keeps files, --hard wipes all).
  • Pushed commit: revert; never rewrite shared history.
  • Lost a commit: git reflog (90 days by default), which cannot save changes that were never committed.

You can now fix mistakes safely. The next part is the operation many people fear yet every team uses: rebase, to tidy history before opening a merge request, and the golden rule that keeps it from ever causing harm.

Frequently asked questions

What is the difference between git reset and git revert? ▾
git reset moves the branch back to an older commit, rewriting history, so use it only before pushing. git revert adds a commit with the reverse effect and leaves history intact, so use it for pushed commits.
How do git reset --soft, --mixed and --hard differ? ▾
All three move the branch back. --soft leaves staging and the working tree alone; --mixed (the default) updates staging to match the new commit but keeps the files; --hard overwrites the working tree too, losing uncommitted changes.
How do I recover a commit after git reset --hard? ▾
Run git reflog to find the HEAD@{n} entry from before the reset, then git reset --hard HEAD@{n} or git switch -c new-name <hash>. Reflog entries are kept for 90 days by default, but changes that were never committed cannot be rescued.
When may I use git commit --amend? ▾
When the latest commit has not been pushed. Amend creates a different commit (the hash changes), so if you already pushed, others hold the old commit and you would have to force-push; in that case use git revert or a follow-up commit.
